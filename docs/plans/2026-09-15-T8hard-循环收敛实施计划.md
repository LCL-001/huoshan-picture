## 现状：两套循环的差异与四处协议缺口

### 两套循环的差异（`BaseAgent.run()` vs `BaseAgent.runStream()`）

| 环节 | `run()`（本轮退役） | `runStream()`（保留，成为唯一入口） |
|---|---|---|
| 入参校验失败 | 抛 `RuntimeException` | 发一条 `answer` 事件 + `complete()`（**不发 `[DONE]`**） |
| 每步产出 | `String stepResult`，累积成 `"Step N: …"` 文本返回 | 读 `lastStepKind` 字段分流：`tool` → `step`（think+tool 两帧）、`answer` → `answer` |
| 取消（`stopped`） | 不检查 | 每轮检查，置位则提前退出并直接 `complete()` |
| 达最大步数 | 结果串追加 `Terminated: Reached max steps (N)` | `answer` 帧"执行结束：达到最大步骤 (N)" |
| 卡死终止 | 结果串追加 `Terminated: Agent stuck in a loop` | `answer` 帧"检测到循环，智能体已终止" + **提前 `[DONE]`** |
| 步骤异常 | `catch` → 返回 `"执行错误，Error: …"` | `catch` → `answer` 帧"执行错误，Error: …" + `[DONE]` |
| 收尾 | `cleanUp()` | maxSteps 帧 → metrics（若有）→ `[DONE]` → `complete()`；`finally` 与三个回调各自再 `cleanUp()` |

### 四处缺口（读代码实测，T8-b/T8-c 逐条用测试钉住）

1. **受保护字段旁路**：`lastStepKind` / `lastThinkText` / `lastToolNames`（`BaseAgent:62-64`）由 `ReActAgent.step()` 与 `ToolCallAgent.think()/act()` 写入、由循环读出（`BaseAgent:191-199`）。`step()` 返回的 `String` 不带分类信息，所以"这一步是过程步还是最终回答"只能靠这条可变旁路——抽不出干净的消费者接口，也测不准。
2. **卡死路径双发 `[DONE]`**：`BaseAgent:208` 在卡死终止时先发一次 `[DONE]` 再 `break`，而 `break` 之后仍会走尾部 `BaseAgent:231` 的 `[DONE]`。前端与代理都在第一帧就收手，所以**今天不可见**，但协议上一条流发了两个终止帧。
3. **校验失败流不以 `[DONE]` 收尾**：`BaseAgent:165-172` 发一条 `answer` 就 `complete()`。代理的 `relay()`（`AiAssistantProxyManager:160-188`）读到 EOF 而未遇 `[DONE]` → 返回 false → `sendErrorAsAnswer`（`:122-124`）**再补一条** `answer`"图库助手响应意外中断，请重试" ⇒ 这条路径上用户会看到两条回答。生产端点在入口就校验 `message`，所以只在异常路径可达；但它证明"每条流以 `[DONE]` 结束"这个代理赖以为生的不变量今天并不成立。
4. **失败/超时文本进气泡且重复多轮**：`ToolCallAgent.think()` 的 `catch`（`:161-165`）把异常写成一条 `AssistantMessage`（`STEP_ERROR_PREFIX + 原始异常消息`）并 `return false`，**但不置 `FINISHED`** ⇒ 循环继续；而每轮的 assistant 文本完全相同，`isStuck()`（`duplicateThreshold=2`，`BaseAgent:67`）约 3 轮后触发卡死终止。综合效果（**读代码推定，T8-c 第一步先用复现测试证实，规则 12**）：一次 provider 超时最终在气泡里出现 **2-3 段原始异常文本** + 一句"检测到循环，智能体已终止"，而 `T6.1` 实测的超时形态是 `WebClientResponseException`（HTTP 200）包裹 `TimeoutException`（`docs/decisions.md` 2026-09-14 R3 行）——即用户读到的是厂商报错原文。

### 两处观察（本轮不修，记账）

- `runStream()` 用 `CompletableFuture.runAsync`（`BaseAgent:162`）= `ForkJoinPool.commonPool`，并行度≈核数-1；一次 50s 的对话会占住共享池线程。改专用池属运维口径变更，不在本任务。
- metrics 帧与 `event` 同层扁平：`sendEvent()`（`BaseAgent:288-296`）把 `data` 与 `"event"` 合进同一个 Map，所以 `runSummary()` 里出现 `event`/`kind`/`name`/`content` 会污染帧。当前**无生产者**（全仓 `runSummary()` 零覆盖），属潜伏项。

## 目标设计

### 1. 事件模型（新包 `com.lcl.myaiagent.agent.event`）

协议定义收在一个文件里，避免"协议散在类里"：

```java
/** 引擎 → 消费端的事件协议（T8-hard 显式化）。字段名即帧契约，改动必须同步前端与代理测试。 */
public sealed interface AgentEvent {
    record Step(String kind, String name, String content) implements AgentEvent {} // kind: think | tool
    record Answer(String content) implements AgentEvent {}
    record Metrics(Map<String, Object> values) implements AgentEvent {}
    record Error(String content) implements AgentEvent {}   // T8-c 才启用；不纳入则先不加
    record Done() implements AgentEvent {}
}

/** 事件消费者（受保护字段通道的替代品）：循环只认这个接口，不关心消费端是 SSE 还是收集器。 */
public interface AgentEventListener {
    void onEvent(AgentEvent event);
}
```

`SseAgentEventListener implements AgentEventListener`：把事件翻成 SSE 帧写进 `SseEmitter`——`Step/Answer/Metrics/Error` → `send(JSON Map, APPLICATION_JSON)`（Map 里补 `"event"` 字段），`Done` → `send("[DONE]")` 后 `complete()`；写失败（`IOException`）时回调 `Runnable onClientGone` 置 `stopped`（替代今天 `sendEvent` 里偷偷改状态的做法）。

### 2. `step()` 直接产出事件，字段通道收编

- `BaseAgent`：`public abstract String step()` → **`public abstract List<AgentEvent> step()`**（一步可以产出多帧：think + tool）。
- `ReActAgent.step()`：删掉三个受保护字段的初始化与写入；think=false → `List.of(new Answer(最后一条消息文本))`；think=true → 返回 `act()` 的结果；异常 → 见 T8-c。
- `ToolCallAgent.act()`：`String` → `List<AgentEvent>`；工具步返回 `List.of(new Step("tool", String.join("、", names), results))`（think 文本取自**本类自己的** `toolCallChatResponse`，不再跨层写字段）；`askHuman` / `doTerminate` 仍按今天语义返回 `Answer`（"提问面向用户，按最终回答渲染"这条口径不变）。
- 删掉 `lastStepKind` / `lastThinkText` / `lastToolNames` 三个受保护字段（收编完成的判据：全仓 grep 这三个名字零命中）。
- **保留但说明**：`ToolCallAgent.toolCallChatResponse`（`think()` → `act()` 的同一步交接，私有、循环不碰）；`runSummary()`（metrics 的扩展点，见「需用户拍板 3」）。

### 3. 单一循环 `runLoop`，`runStream` 变薄壳

```java
public SseEmitter runStream(String userPrompt) {          // 签名不变 ⇒ 两个控制器零改动
    SseEmitter emitter = createEmitter();                 // 见下方"缝"
    emitter.onError(...); emitter.onTimeout(...); emitter.onCompletion(...);   // 回调行为不变
    CompletableFuture.runAsync(() -> runLoop(userPrompt,
            new SseAgentEventListener(emitter, () -> this.stopped = true)));
    return emitter;
}

protected void runLoop(String userPrompt, AgentEventListener listener) {  // 唯一循环，可同步驱动（测试用）
    // 校验 → 事件 + Done（每条路径都以恰好一个 Done 结束）
    // while (currentStep < maxSteps && state != FINISHED && !stopped) { step() → 逐条 onEvent；isStuck → 收尾 }
    // 尾部：maxSteps 帧 → metrics（若有）→ Done；catch → Error/Answer + Done；finally cleanUp()
}
```

**不变量（T8-b 逐条断言）**：① 每条流以**恰好一个** `Done` 结束，且它是最后一帧；② 除 `[DONE]` 外每帧都是带 `event` 字段的 JSON 对象；③ 字段名与语义与今天一致（只修缺口，不改语义）。

**缝（沿用仓内既有先例）**：`protected SseEmitter createEmitter()`——与后端 `AiAssistantProxyManager.createEmitter()`（`:75-77`）同一手法，测试覆写它返回记录型 emitter（`AiAssistantProxyManagerTest.RecordingSseEmitter` 已在用，覆写 `send(Object, MediaType)` 与 `send(Object)` 两个重载）。

### 4. `run()` 退役与调用方迁移

- 删除 `BaseAgent.run(String)`（`BaseAgent:91-141`）。
- 调用方全部是测试（实测）：`BaseAgentTest` 8 处改用**收集型监听器**（测试替身），断言从"返回字符串"改为"事件序列 + Answer 文本拼接"。
- **收集能力只存在于测试侧**，不进生产：`docs/plan.md` T6.1 口径已写明"若将来确实要非流式入口，在事件流之上做收集实现，而非保留 `run()` 本体"——本轮不新增任何生产收集入口。
- **`MyManusTest` 必须一起处置**：它 `@Resource` 注入一个**不存在的 bean**（`MyManus` 按请求新建，从不注册为 Spring bean），因此被门禁排除、从来没有真正跑过，且只 `assertNotNull`；删除 `run()` 会让**测试模块编译失败**（连带整条门禁红）。处置见「需用户拍板 2」。

### 5. 失败与超时的显式错误事件（T8-c，需拍板；设计先写下）

- 新增 `AgentExecutionException extends RuntimeException`（unchecked，携带 cause）；`ToolCallAgent.think()` 的 `catch` 改为**上抛**它（保留日志），不再把异常文本写进 messageList。
- `ReActAgent.step()` 的 `catch`：沿 cause 链判定——命中 `java.util.concurrent.TimeoutException`（流空闲超时形态，R3）或 `java.net.http.HttpTimeoutException`（连接/首包超时形态，T6.1 实测）→ `Error("助手响应超时，请重试")`；其余 → `Error("助手处理失败，请稍后重试")`；**并置 `state = FINISHED`**，让失败只产出一条错误事件、当轮结束（不再重复 2-3 轮）。
- 循环自身的 `catch`（`step()` 之外的意外）同样产出 `Error` + `Done`。
- 面向用户的文案固定；**原始异常只进日志**（不再把厂商报错原文送进浏览器）。
- 前端（唯一需要动前端的两处，约 15 行）：`utils/assistantSse.ts` 增加 `event === 'error'` → `handlers.onError(content)`；`pages/AssistantPage.vue` 的 `onError` 改为"有回答则追加、无回答则置为回答"（今天只在空回答时才显示，因为校验失败流曾被误判为断流；缺口 3 修好后这个保守判断可以去掉）。
