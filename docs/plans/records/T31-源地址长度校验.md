# T31 — 源地址长度前置校验

> 任务条目见 `docs/plan.md` T31；来源 = 独立 review（规则 13）的前置条件 ①-1，报告要点见 `docs/decisions/2026-09-18-review-batch-crawl.md`。功能讲解见 `docs/features/F3-批量抓取.md`。

## 问题（review 发现）

`picture.sourceUrl` 是 `varchar(1024)`、入库前无长度校验，而本机 `@@sql_mode` 含 `STRICT_TRANS_TABLES`（review 实测）⇒ 超长 URL 的 INSERT 直接报 `Data too long`。

放大效应来自 T28 的"入库阶段整批原子"：**30 张里只要 1 张源地址超长，整批回滚 + 30 个已转存 COS 对象全部补偿删除 + 接口 500**；而 Bing 同一搜索词返回同一批 URL，所以该搜索词**每次重跑都撞同一张，永久不可用**。单张路径则是"文件已转存 COS 才发现写不进库"，用户只看到"系统错误"。

## 改动

- `PictureServiceImpl`：新增常量 `MAX_SOURCE_URL_LENGTH = 1024`（注释里点明与 `backend/sql/add_picture_source_url.sql` 的列宽对齐）；在**单张与批量共用的 `preparePicture` 入口**加一行 `ThrowUtils.throwIf(...)` 抛 `PARAMS_ERROR / "来源地址过长"`。
- 位置选择说明：review 建议的落点（`uploadPicture` 的判重块）**只覆盖单张路径**——批量走的是 `uploadPictureByBatch → preparePicture`，绕开那里。放在 `preparePicture` 顶部则两条路径都覆盖，且都在**发起下载之前**：批量下这次失败只让该张按"单张失败"跳过，其余 29 张照常入库（比"整批 500"更好）。

## 未验证 / 说明

- **批量路径的超长 URL 未做端到端实测**：批量集成测试用 `@SpyBean` 替换了 `preparePicture`，所以那条路径上是替身在跑；本次校验与单张路径共用同一处代码（`preparePicture` 顶部），由单张路径的用例覆盖。真实批量下超长 URL 的行为（该张跳过、其余入库）由"逐张 try/catch + 同一处校验"推出，属论证。
- **prod 的 `@@sql_mode` 未确认**：本机实测含 `STRICT_TRANS_TABLES`（超长报错）；若 prod 是非严格模式则历史上会静默截断——校验在应用层，与 sql_mode 无关，这条只影响"修复前的行为描述"。
- 前端断言脚本仍只覆盖纯映射（见 F3「已知限制」），T31 未涉及前端。
