## 根因

恢复的额度判定读的是 **Java 快照**、写却是**无条件自增**：

```java
Space space = spaceService.getById(spaceId);                       // ① 读快照
if (nvl(space.getTotalCount()) + 1 > space.getMaxCount()) { ... }  // ② 在内存里判
transactionTemplate.execute(status -> {
    restoreTrashedById(id);
    spaceService.lambdaUpdate().eq(Space::getId, spaceId)
        .setSql("totalCount = totalCount + 1")                      // ③ 无条件加
        .setSql("totalSize = totalSize + " + picSize)
        .update();
});
```

两个并发恢复（或恢复与上传同时发生）各自读到同一个旧快照、一起通过 ②，然后各自执行 ③ →
空间计数越过上限。上传路径本来就是原子口径（`.apply("totalSize + {0} <= maxSize", …)` / `.apply("totalCount + 1 <= maxCount")`
进 WHERE），**恢复是唯一漏掉的那条**。

附带事实：`restoreTrashedById` 的 `WHERE id = ? AND isDelete = 1` 本来就保证"同一张图只会被恢复一次"
（所以"同图并发只回补一次"在修复前就是绿的，见红绿输出）；缺的是**槽位**上的原子判定——跨图并发时人人加一次。

## 修复

事务内两件事，配额条件写进 UPDATE 的 WHERE：

```java
transactionTemplate.execute(status -> {
    ThrowUtils.throwIf(getBaseMapper().restoreTrashedById(id) != 1, OPERATION_ERROR, "恢复失败");
    if (!accumulateSpaceQuota(spaceId, picSize)) {                 // 影响 0 行 = 额度不足
        throw new BusinessException(OPERATION_ERROR, restoreQuotaExceededMessage(spaceId, picSize));
    }
    return true;
});
```

- `accumulateSpaceQuota`：`.eq(Space::getId, spaceId)`
  `.apply("(maxCount IS NULL OR COALESCE(totalCount, 0) + 1 <= maxCount)")`
  `.apply("(maxSize IS NULL OR COALESCE(totalSize, 0) + {0} <= maxSize)", picSize)`
  `.setSql("totalCount = COALESCE(totalCount, 0) + 1")` + `.setSql("totalSize = COALESCE(totalSize, 0) + " + picSize)`。
  `maxCount / maxSize` 为空表示不限（沿用原语义），`COALESCE` 兜住历史 null。
- 条件不成立 = 影响 0 行 → 抛业务异常 → `transactionTemplate` 整笔回滚，记录仍在回收站、额度没有被多记。
- 文案：失败路径上 `restoreQuotaExceededMessage` 回读一次空间区分"数量触顶 / 容量触顶"，与旧文案逐字一致
  （`空间图片数量已达上限，无法恢复` / `空间容量已达上限，无法恢复`），另加兜底 `空间额度不足，无法恢复`。
  **判定不看这次回读**——两边万一不一致（例如刚被并发改过）只影响文案，不影响"该不该拒绝"。

## 测试手法（为什么是这两种）

1. **确定性交错**（`@SpyBean ISpaceService` 卡在 `lambdaUpdate()` 上）：把主线程当作"另一个并发请求"，在
   "被测请求读完快照、正要回补额度"这一瞬间用裸 SQL 占掉最后一个名额再放行。红/绿都不依赖线程调度——
   修复前它必然越限，修复后必然回滚。
2. **真并发**（5 线程同时恢复）：断言"恰好放行到上限、计数不越限、失败者仍在回收站"，线程怎么调度结果都一样。
3. 工作线程**必须各自绑定双登录态**（Spring Session 属性 + Sa-Token cookie）：两套登录态的读取都是线程本地的，
   而 T56 的写操作入口校验要求两者同属一人。

## 已知限制 / 未覆盖

1. **并发失败文案不区分"谁占了名额"**：只回"空间数量/容量已达上限"，用户可读性够用，不做更细的归因。
2. **上传路径的 `totalSize + {0} <= maxSize` 没有 NULL 守卫**（本仓空间创建时 maxCount/maxSize 必填，属理论面）：
   本次按 T57 范围**只改恢复路径**，未顺手改上传（规则 1）。如需统一口径，另开任务。
3. **压力只到 5 线程 × 2 名额**：不是压测，只覆盖"超过上限必须拒绝"的语义；更极端并发（几十线程）未跑。
4. **失败路径多一次空间回读**：只发生在额度不足时（成功路径比修复前少一次 `getById` 快照读）。
