# T32 记忆读写去 advisor 化 + 预算扩容（2026-09-27）

> 任务条目见 `docs/plan.md` T32；口径见 `docs/decisions.md` 2026-09-27 行（详情 `docs/decisions/2026-09-27-memory-explicit-rw.md`）。
> 本文件是实施记录与证据（写定后不再编辑）。

## 起因（用户两条）

1. 简历口径"上下文窗口 4096"与所选模型（1M 上下文）不匹配——把窗口扩到合理大小并重测。
2. F12 记录的"重复 3 份"低估了实际情况：advisor **每一轮**都会注入一次上下文，ReAct 循环每轮重提整段 messageList，重复是逐轮发生的；要求"不使用 advisor"解决。

## 根因核实（Spring AI 1.1.2 源码，`MessageChatMemoryAdvisor`）

- `before()`：`memory.get(conversationId)` **全量读取** → 拼在请求消息**前面** → 再 `add(conversationId, 请求里最后一条用户消息)`。
- `after()`：把本次响应的 assistant 消息写回。
- 与本引擎的叠加效应：循环每轮重提整段 messageList ⇒
  - **注入侧**：第 k 轮提示词 = 记忆视图（含本轮已入库的 user/assistant 行）+ messageList（同样的行 + 工具响应）——同一段上下文出现两份，且随轮数增长；
  - **写回侧**：同一条用户消息每轮被 `add` 一次（第 1 轮写的是下一步提示，第 2 轮起写原始提问）——入库靠指纹去重兜住（实测 3 份是短会话取样），提示词侧没人兜。

语义变化（都有意为之）：

- agent 内部提示（下一步提示/卡死提示）**不再入库**——think() 的既有注释本来就说"拼入请求但不持久化"，是 advisor 的回写让它意外入库；前端历史渲染不受影响（这些行本来就被 `ChatHistoryAssembler.isInternalPrompt` 过滤），历史数据里的旧行仍被过滤。
- 用户隔轮重复同一句提问，第二遍**会**进记忆（旧去重把它丢了）；回放里该问题出现两次，与真实对话一致。
- 一次运行内提示词不再随记忆重读而中途变形（advisor 时代第 k 轮的注入视图会因中途压缩而变）；前缀在运行开始固定。
