# T34 — 图片列表缓存失效按空间切分（Redis 版本号按 scope）

> 任务条目见 `docs/plan.md` T34；功能讲解见 `docs/features/F4-图片列表多级缓存.md`。用户拍板的边界：**只改 Redis 版本号，本地 Caffeine 层保持全清**（不做键级/epoch 失效）。

## 问题

`doClearPictureListCache` 每次只 `INCR` 一个全局版本号 `huoshantuku:listPictureVOByPage:version`，于是**任何一次图片写入都把所有列表缓存一起作废**——写某个空间的一张私图，会让热门公共图库以及所有无关空间的列表缓存立刻失效，接下来每个键都要抢锁回源重建。列表接口是最高频的读路径，这是持续存在的无谓负载。

功能本身是对的（过失效不会出错），问题是粒度：失效范围远远大于实际影响面。

## 为什么可以按空间切

1. **查询的 scope 两两不相交**：`spaceId` 非空查该空间；`spaceId` 为空时被强制 `nullSpaceId=true`，只查"无空间"的公共图库。不存在跨空间的查询结果，所以"失效一个空间不会漏掉另一个空间该看到的变化"。
2. **图片的空间归属创建后不可变**：编辑接口的 DTO（`PictureEditRequest` / `PictureUpdateRequest`）根本没有 `spaceId` 字段；替换图片时不传就继承原图、传了不一致直接拒（`PictureServiceImpl.java:253-264` 的"空间 id 不一致"）；批量编辑在选图时就按 `.eq(Picture::getSpaceId, spaceId)` 过滤。

两条合起来 ⇒ **一次写入最多影响一个 scope**，不需要预留"图片换空间要同时失效新旧空间"的后手。

## 改动

- `PictureServiceImpl`：
  - 版本号 key 从全局常量改为**按 scope 拼接**：`cacheVersionKey(scope)` → `huoshantuku:listPictureVOByPage:version:{scope}`。刻意**不设 TTL**——计数器过期归零会让上一世代的旧 key 重新可达。
  - 新增 `cacheScopeOf(Long spaceId)`：`null` → `CACHE_SCOPE_PUBLIC`（字面量 `"public"`），否则空间 id 字符串。**读路径与写路径共用同一处推导**，避免两侧口径漂移。用字符串而非 `0` 表示公共图库，是为了不可能与"空间 id 恰好是 0"撞 scope。
  - `clearPictureListCache(scopes)` / `doClearPictureListCache(scopes)`：逐个 scope `INCR`，之后仍然 `invalidateAll()` 一次。`invalidateAll()` 的调用次数不变（T28 的"批量只清一次"契约保持），广播报文也不必带 scope——本地层全清，对端不需要知道是哪个空间。
  - 8 处写路径各自传自己的 scope，归属表见功能文档。其中 `updatePicture` / `editPicture` **必须取 `oldPicture.getSpaceId()`**：新实体是按 DTO 拷的，`spaceId` 恒为 null，拿它推导会把空间图库错算成公共图库。

## 测试设计要点

- 隔离测试断言的是**行为**（`@SpyBean` 数 `loadFromDb` 调用次数），不是 Redis key 的字面形状：改动实现细节不会误伤断言。
- 该测试**刻意不 mock** `PictureListCacheInvalidator`（`PictureBatchUploadIntegrationTest` 是 mock 的）。若 mock 掉，本地层不会被清，两次调用都命中 L1，`loadFromDb` 永远是 1 次，用例失去意义。
- 每条查询用唯一 `searchText` 造冷 key，不与其它用例或本机正在运行的实例互相干扰；`spaceId` 为空时不会走空间权限校验，`request` 可传 `null`。

## 负向控制（未做，列出为什么）

- **没有**单独造"空结果缓存（60s TTL）"的用例：空/非空只影响 TTL 长度，不影响版本号与失效路径，测它对本次改动没有增量信息。
- **没有**为 `applyAiTags` 的跨 scope 去重写集成用例：它复用同一个 `clearPictureListCache(Collection)` 入口，而该入口已由单空间路径覆盖；跨 scope 的差异只在"传几个 scope"，纯函数的去重集合无法在不拉起 AI 打标链路的情况下单独断言。属于覆盖缺口，记录在此。
