## 问题

`ToolCallAgent.act()` 识别出 prepare 工具返回的"待确认操作"载荷后，只把 `AgentEvent.Confirmation` 放进本步事件列表，
**没有**改状态；`BaseAgent.runLoop` 的 while 以 `state != FINISHED` 为条件，于是必然再执行一步 `think()`（再调一次主模型）。
全循环实测：该 prepare 载荷下主模型被调用 **5 次**（跑到 `maxSteps`），并可能再生成一张卡片、多发收尾 Answer 帧。

边界澄清：确认门本身是 Redis 原子单次消费 + 用户/会话绑定，同一 operation 不会被执行两次；URL 导入另有 `sourceUrl` 按空间判重兜底。
所以这不是"重复写入"漏洞，而是"循环结构允许不确定行为 + 白烧额度"的缺陷。

## 改动

- 引擎 `ToolCallAgent.act()`：算出 `confirmations` 后非空则 `setState(AgentState.FINISHED)`（置于 doTerminate / askHuman 分支之后、返回事件之前）。
  循环随即退出，`runLoop` 的收尾不变量（每条流恰好一个 `[DONE]`）不变。
- 前端 `AssistantPage.vue`：确认卡片"确认执行 / 取消"按钮加 `:disabled="running"`（纵深防护；根治在引擎侧）。
