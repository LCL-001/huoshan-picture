## 病根

`gateContextMessages()` 从历史尾部往前扫，**只按角色配额停**（USER ≤2、ASSISTANT ≤1），**没有窗口**：

```java
for (int i = history.size() - 1; i >= 0; i--) {
    if (users >= 2 && assistants >= 1) break;
    ... 丢弃拒绝话术行；按角色塞进 picked ...
}
```

只要配额凑不满，循环就一路向前翻。最典型的触发形态是**连续拒绝轮**：拒绝话术行（`OUT_OF_SCOPE_REPLY`）被丢弃，
助手配额一直空着（`assistants` 还是 0，`break` 条件不成立），于是继续往前够，把**很早以前的助手回答**也拖进门卫输入——
那段文本与"最新一条请求"范围判定毫无关系，正是 T46 要修的"历史污染"，只是换了个来源。

即：T46 设计的 A1' 明写了"取最近至多 4 条历史"，实现只做了角色封顶。本任务把它补上。

## 修复

**先在原始历史上截窗，再在窗口内过滤**（先截窗、后过滤，顺序不能反——反过来就等于先过滤再想办法凑配额）：

```java
List<Message> history = getHistoryContext();
int from = Math.max(0, history.size() - SCOPE_CONTEXT_MAX_ROWS);   // 最近至多 4 条
List<Message> window = history.subList(from, history.size());
List<Message> picked = new ArrayList<>();
int users = 0, assistants = 0;
for (int i = window.size() - 1; i >= 0; i--) {
    if (users >= SCOPE_MAX_USER_ROWS && assistants >= SCOPE_MAX_ASSISTANT_ROWS) break;
    ... 丢弃拒绝话术行；角色封顶；每条 truncate 500 ...
}
```

越窗的行一律不看：**凑不满就凑不满，不再向前翻**。T46 的 USER 锚点与 T44 结果事实行可见性不变（它们本来就在最近几条里）。

## 已知限制 / 未覆盖

1. **窗口是硬边界，越窗的锚点找不回来**：追问若依赖 4 条以外的上下文（例如"刚才那个批量编辑"但此后又聊了 5 条以上），
   门卫看不到锚点、可能 fail-closed 误拒。这是 T46 设计 A1' 的既定取舍（窗口换稳定），本轮不调窗口大小（4 是设计值）。
2. **窗口按"条数"计，不按"轮数"**：4 条 ≈ 2 轮问答；一条超长文本也只算 1 条（字数另有 500 字截断兜底）。
3. **只覆盖门卫输入**：正式助手侧的历史视图（`FlowWindowBasedChatMemory` 的压缩窗口/预算）不受本改动影响，两套窗口口径不同（一个是"分类上下文"，一个是"对话记忆"）。
4. **未做真机复测**（见上节），也未在真实模型上验证"连续拒绝轮"这一具体触发形态——单测用固定历史复现了它，但没有真机证据。
