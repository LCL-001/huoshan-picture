# T33 循环检测重写为双信号滑窗（2026-09-27）

> 任务条目见 `docs/plan.md` T33；口径见 `docs/decisions.md` 2026-09-27 行（详情 `docs/decisions/2026-09-27-loop-detection-dual-signal.md`）。
> 本文件是实施记录与证据（写定后不再编辑）。

## 起因

用户指出重复检测实现有问题，要求给修改方案并参考成熟开源方案。调研结论（详见 decisions 详情）：现有 `isStuck()` 忠实照抄 OpenManus 的"assistant 文本全局计数"，三类缺陷 + 一个终止文案缺陷；业界共识是"工具调用指纹为主信号、滑窗/连续计数、步数硬边界兜底"。用户拍板方案 2（工具签名 + 文本双信号滑窗），不做 2b（执行前阻断）。

## 旧实现的四个问题（均有代码指证）

1. **盲区**：`isStuck()` 取"最后一条 ASSISTANT 消息"，文本为空直接 return false——纯工具决策行文本常为空（`act()` 的"空则不发思考帧"注释为证），"同工具同参数反复调用"这条最常见的死循环完全检测不到。
2. **误报**：全局计数口径——最后一条文本在**整段历史**出现 ≥2 次即判卡死，不同上下文合法重复的短句累计 3 次就误判。
3. **漏报**：精确等值匹配，措辞微差（多一个句号、数字不同）就漏。
4. **终止成本与双 answer**：`duplicateThreshold=2` + `MAX_STUCK_COUNT=3` ⇒ 同一文本约出现 5 次才强停（20 步预算白烧约 1/4）；本步已产出最终回答（state 已 FINISHED）时仍补发"检测到循环，智能体已终止"，跟在真回答后面。

## 实施（BaseAgent 单文件，未动 ToolCallAgent/ReActAgent）

- `loopSignature(Message)`：assistant 子序列的循环签名——工具调用步 = `tool|名|规范化参数`（一次多调用按序拼接），纯文本步 = `text|文本`；空文本且无工具调用的决策行无签名。带文本的工具决策行**按工具签名判**（文本是修辞变化，重复的动作才是循环信号）。参数规范化 = Jackson 重序列化去空白差异（键序重排不归一，可接受漏报）。
- `isStuck()`：取签名序列**最近 4 步滑窗**（`STUCK_WINDOW=4`），同签名出现 ≥ `duplicateThreshold`(2) 次（含当前）判卡死。滑窗防误报：间隔 ≥4 步的重复不触发。
- `handleStuckState()`：`MAX_STUCK_COUNT` 3 → 2——第 1 次纠偏（注入"观察到重复响应…"提示，只进下一轮请求不入库）、第 2 次强停；删除恒假的 nextStepPrompt 拼接（think() 每轮消费后置空，拼接永远得到裸提示）。
- `runLoop`：检测加 `state != FINISHED` 前置——本步已给出最终回答就不再检测，真回答后面不再跟"检测到循环"。

调研对照（写入 decisions 详情）：OpenManus（源头同款缺陷）/ LangGraph·OpenAI Agents SDK·CrewAI（只做步数硬边界，内容检测交自定义终止条件）/ Strands（工具指纹滑窗 + **执行前阻断**——2b 即此，暂不做）/ Inngest（连续 3 次同工具）/ OpenFang（SHA-256 序列模式检测，抓交替循环，20 步对话场景罕见不做）/ spring-ai-alibaba `LoopAgent`（按条件重复的编排算子，不同类问题）。
