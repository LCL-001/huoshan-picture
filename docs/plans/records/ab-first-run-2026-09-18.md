# A/B 分进程压测首次实跑（2026-09-18）

> 上游口径：`backend/jmeter/README.md`（压测单一事实源）§6.2。
> 运行器：`backend/jmeter/scripts/run-ab-staircase.ps1`；对比脚本：`backend/jmeter/scripts/compare-ab.py`。

## 一句话

DB 路径与缓存路径**首次**按分进程口径实跑（各 20/50/100 三档、每档 300 秒、6 个独立 JVM），
合计 **688,024 个被测样本、错误率全 0.0%**；缓存路径在 100 线程档聚合 **705 QPS**，是 DB 路径（401 QPS）的 **1.76 倍**。

## 复跑方式（可复跑）


- 运行顺序固定：`DB-t20 → Cache-t20 → DB-t50 → Cache-t50 → DB-t100 → Cache-t100`，每个组合一个独立 JVM。

| 运行 | 被测 p95 | health 基线 p95 | tag_category 基线 p95 | net p95（减最慢基线） | net p95（只减 health） |

## 关键发现

1. **缓存路径的收益在饱和档才显著**：同并发吞吐比 20 档 1.26×、50 档 1.33×、**100 档 1.76×**
   （705.1 / 401.2 QPS）；100 档 mean 134.5ms vs DB 236.7ms。
2. **DB 路径的拐点在 50 线程附近**：50→100 档 QPS 只 +17.0% 而 p95 +131.3%——继续加线程只涨延迟。
   缓存路径 50→100 档 QPS 仍 +55.1%，但 p95 已 +88.9%，同样开始抬头。
3. **`tag_category` 不再是纯静态基线**（T5 起该接口查词表）：DB-t100 那次它的 p95 是 **348.3ms**，
   与同运行的 health（161.0ms）差 2.2 倍。作为"最慢基线"被减掉后，100 档算出
   `DB net p95 35.7 < Cache net p95 47.4` 的**反向结论**；只减 health 时结论相反（Cache 64.0 / DB 223.0），
   与直觉和 20/50 档的趋势一致。**100 档的 net 列应视为失真**。
4. **机器级排队会抬高"空跑"成本**：health 基线 p95 从 20 档的 93.0ms 涨到 100 档的 174.0ms。
   100 档的延迟里含有整机排队，不能全额记到接口头上（与 README §5.1 的口径一致）。
5. **两次路径对比的净收益（可信档）**：20 档 p95 差 3.2ms、50 档差 **34.0ms**（减 health 口径），
   方向与旧 v3 的 35ms 同量级——旧数字的**量级**被这次分进程实跑印证，但旧数字是"同运行并发"口径，
   仍以本文件的 A/B 口径为准。

## 方法学限制（本次运行）

本次是**背靠背**跑的：运行器当时没有组间冷却。实测每轮周期 **308–310 秒**，而被测线程组本身跑 300 秒
（各轮 `statistics-ab-uncooled/*.json` 的写入时刻：13:48:47 / 13:53:54 / 13:59:02 / 14:04:10 / 14:09:19 / 14:14:29），
即两组之间只有约 **8 秒**空窗——而这 8 秒里还包含上一轮的 HTML 报告生成、`statistics.json` 拷贝、
下一个 JMeter JVM 启动与预热线程组。**服务端从未排空。**

叠加路径顺序固定为 `DB, Cache`：**缓存那一轮总是继承一台刚被压了五分钟的机器**。偏置方向对缓存不利，
故本次"缓存胜出"的结论偏保守、可采信；但若将来出现相反结果，必须先排除这个顺序偏置。

运行器已于同日后加 `-CooldownSeconds`（默认 60，见 README §6.2）；含冷却的一轮实测两组间隔 40 秒
（16 秒加载 + 20 秒冷却 + 收尾）。
