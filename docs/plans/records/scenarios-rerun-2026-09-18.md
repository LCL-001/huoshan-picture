# v3 单场景重跑（2026-09-18）——登录 / 登录态两组的台阶

> 计划：`backend/jmeter/lincode-loadtest-v3.jmx`（该日有两处采样器调整，见 `backend/jmeter/README.md` §3）。
> 原始统计：`backend/jmeter/statistics/report06-login-*.json`、`report07-auth-*.json`（各 3 个，入库）。
> 仪表盘：`backend/jmeter/reports/report06-*/`、`report07-*/index.html`（不入库）。

## 一句话

把两个单场景组的台阶按历史档位重跑（登录 5/10/20、登录态 5/20/50，各 300 秒），
**6 次运行合计 244,934 样本、错误率全 0.0%**；
其中最值钱的一条是**修掉了历史批次里一个被带偏的结论**：登录 10 线程档当时吞吐反而下降，重跑后是一条干净的饱和曲线。

## 复跑命令（可复跑）

```powershell
cd backend\jmeter
# 登录组（TG2），每档一条，只开 TG2
jmeter -n -t lincode-loadtest-v3.jmx -Jt1=0 -Jt3=0 -Jt2=5  -Jdur=300 `
  -JTEST_ACCOUNT=<账号> -JTEST_PASSWORD=<口令> -l reports\report06-login-5.jtl  -e -o reports\report06-login-5
# …… -Jt2=10 / -Jt2=20 同理

# 登录态组（TG3），只开 TG3
jmeter -n -t lincode-loadtest-v3.jmx -Jt1=0 -Jt2=0 -Jt3=5  -Jdur=300 `
  -JTEST_ACCOUNT=<账号> -JTEST_PASSWORD=<口令> -l reports\report07-auth-5.jtl  -e -o reports\report07-auth-5
# …… -Jt3=20 / -Jt3=50 同理
```

前置条件与混合场景一致：线上叠加 **`prod,test`**（关验证码与登录限流）、一个线上库里的**普通用户**账号；
**跑完把 profile 改回 `prod` 并重启**。

## 关键发现

1. **历史批次的登录 10 线程档是个异常值。** 当时 5→10 档吞吐**下降**（14.75 → 11.35）、延迟翻 2.6 倍，
   会让人读成"10 线程最惨、20 线程反而好了"（非单调）。重跑后是干净的单调曲线：
   **QPS 14.21 → 18.30 → 20.10，平均延迟 347 → 538 → 979ms** —— 线程翻 4 倍吞吐只涨 41%，
   延迟涨 2.8 倍。**引用登录的容量结论请用重跑批次。**
2. **TG3 的聚合 QPS 不能跨批次比**：采样器从 5 个变成 6 个（§3 把空间列表移了进来），
   每轮迭代更重，同样的 300 秒里轮次更少（约 −28%）。逐采样器看延迟只高 10–20%，
   来源是每轮多一个请求带来的额外争用。**结论本身不变**：吞吐随线程近线性增长（55.6 → 217.9 → 490.3 QPS），
   延迟几乎不动（88.6 → 90.3 → 100.3ms）——鉴权层（Sa-Token 校验 + Spring Session 取用户，两次 Redis 读）
   在 50 线程以内不是瓶颈。
3. **两次运行的前置条件一致**（同账号、同 `prod,test`、同 300 秒），所以差异可归因于采样器集合与运行状态，
   而不是方法差异。

## 未决 / 待办

- **跑完必须把服务端 profile 改回 `prod` 并重启**（`prod,test` 期间登录无限流）。
- 被测机器配置（核数 / 内存 / 带宽）仍未记录。
- **Redis 残留**：本次 6 档共约 15,800 次登录（TG2 三档 4,267 + 5,493 + 6,030，TG3 每线程建会话 75 次），
  每次登录在 Redis 留一个 7 天 TTL 的 Sa-Token 令牌键；连同当日混合场景的 2,699 次，
  一天累计约 1.9 万个键（几 MB，不写 MySQL）。需要清理时按 `satoken:login:token:*` 前缀删。
