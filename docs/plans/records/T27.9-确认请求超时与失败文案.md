## 交付

- **确认请求解除客户端超时**（`frontend/src/api/assistantController.ts`）：`confirmAssistantOperation` 的 axios 调用改为 `{ timeout: 0 }`——confirm 在服务端**同步**执行（URL 入库逐条下载 + COS 转存，上限 20 条，单条就有 5s connect + 10s read 预算），全站默认的 10s 会让客户端先超时、卡片谎报失败而后端仍在写入；确认是单次消费的幂等动作，等待即可，与对话流（EventSource 无客户端时限）同一取舍。
- **失败文案分型**（`frontend/src/utils/assistantFormat.ts` 新增纯函数 `describeAssistantConfirmFailure`）：后端业务拒绝（用户安全文案）→ `确认未完成：<文案>`；传输失败（axios 超时/网络中断，按 `isAxiosError` 识别）与未知错误 → 固定提示"确认请求中断或超时：操作可能已在后台执行，请先到空间里查看结果，不要重复提交"。axios 英文原文（`timeout of 10000ms exceeded`）不再可能出现在用户文案里。
- `AssistantPage.vue` 的卡片失败行改走该纯函数；顺带删掉不再可达的 `CONFIRM_FAILURE_FALLBACK`（旧逻辑下 `e.message` 恒非空，它永远走不到）。

- **环境**：本机 backend 8123（`local,test`）+ 引擎 8124（`local`）+ 前端 5173；真实 MySQL/Redis/COS 与真实模型 `mimo-v2.6-flash`；冒烟账号 + 专属空间（额度 100MB）。
- **脚本路径**（探针脚本与命令见 `docs/evidence/2026-09-29-confirm-gate-smoke.md`）：登录 → 取票 → SSE（模型 `listSpaces` → `prepareUrlImportPictures`，`confirmation_required` 帧带 operationId/digest/summary）→ confirm **11743ms**、6/6 成功 → 空间里 6 张 webp（COS）。**确认耗时越过了 10s——旧前端必在此处谎报失败而后端已写入，这条 P2 由此从"推断"变成"实测"。**
- **浏览器路径**：真实卡片出现（"待确认：按 URL 入库 / 目标空间 id：… / 入库 URL：6 条"）→ 点"确认执行" → ~2s 进入"确认中" → **14235ms** 后卡片渲染"入库完成：成功 6 / 6 条"，**没有"确认未完成"、没有 timeout 文案**（截图见对话记录，不可复跑——IAB 面板在长等待时会重载页面，卡片只在该次会话存在）。

- **顺带观察**：浏览器第 1 次会话因面板重载导致客户端断开时，代理按既有路径收尾（日志一条 `IOException 连接被中止` + 一次转发失败告警，无重复请求、无 500 外泄）；这是 R4 家族的"客户端已断开"形态在真机上的旁证，但 R4/R7 的时序本身仍以单测为准。

## 已知边界与未验证

- ~~真机多次导入未实测~~ → **已补做（见上）**：6 条直链两次确认实测 11743ms / 14235ms。单条耗时由外网下载与 COS 转存决定，换网络/图片大小数字会变；20 条上限下的最坏值仍无实测（按单条 5s connect + 10s read 预算推算可达分钟级）。
- **不限时意味着服务端挂死时卡片会一直停在"确认中"**：没有逃生按钮，用户可刷新页面（卡片不重建、操作由 TTL 作废）；比"谎报失败"更接近事实，故本轮接受。彻底解是把 confirm 做成异步（202 + 轮询），本轮不做。
- 断言里的"源码级守卫"用正则匹配 `timeout: 0`：格式化调整会误报，属有意的显式守卫（改代码时连带改断言）。
