# T27.9 记录 — 确认请求超时与失败文案（独立 review P2-1）

> 2026-09-29 完成。起因为 `docs/decisions/2026-09-29-review-write-gate.md` 的 ①-1（用户当日拍板"先做一二"）。生效口径见 `docs/decisions.md` 2026-09-29 行。commit `68a2338`。

## 交付

- **确认请求解除客户端超时**（`frontend/src/api/assistantController.ts`）：`confirmAssistantOperation` 的 axios 调用改为 `{ timeout: 0 }`——confirm 在服务端**同步**执行（URL 入库逐条下载 + COS 转存，上限 20 条，单条就有 5s connect + 10s read 预算），全站默认的 10s 会让客户端先超时、卡片谎报失败而后端仍在写入；确认是单次消费的幂等动作，等待即可，与对话流（EventSource 无客户端时限）同一取舍。
- **失败文案分型**（`frontend/src/utils/assistantFormat.ts` 新增纯函数 `describeAssistantConfirmFailure`）：后端业务拒绝（用户安全文案）→ `确认未完成：<文案>`；传输失败（axios 超时/网络中断，按 `isAxiosError` 识别）与未知错误 → 固定提示"确认请求中断或超时：操作可能已在后台执行，请先到空间里查看结果，不要重复提交"。axios 英文原文（`timeout of 10000ms exceeded`）不再可能出现在用户文案里。
- `AssistantPage.vue` 的卡片失败行改走该纯函数；顺带删掉不再可达的 `CONFIRM_FAILURE_FALLBACK`（旧逻辑下 `e.message` 恒非空，它永远走不到）。

## 已知边界与未验证

- **真机多次导入未实测**：修复依据是超时配置与代码路径的最坏值，不是实测耗时分布——建议部署前用一次 5~10 条 URL 的导入确认（验收项已写入 plan T27.9 与 review 报告）。
- **不限时意味着服务端挂死时卡片会一直停在"确认中"**：没有逃生按钮，用户可刷新页面（卡片不重建、操作由 TTL 作废）；比"谎报失败"更接近事实，故本轮接受。彻底解是把 confirm 做成异步（202 + 轮询），本轮不做。
- 断言里的"源码级守卫"用正则匹配 `timeout: 0`：格式化调整会误报，属有意的显式守卫（改代码时连带改断言）。
