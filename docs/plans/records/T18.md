  - **背景与证据（2026-09-15 核实）**：`OpenAiChatModel.Builder` 不设模板就用 `RetryUtils.DEFAULT_RETRY_TEMPLATE`（字节码 `getstatic` 确认）= `maxAttempts(10)` + `retryOn(TransientAiException, ResourceAccessException)` + `exponentialBackoff(2s, ×5, 封顶 180s)`，9 段退避合计约 **1142s（≈19 分钟）**，远超引擎 emitter 的 300s ⇒ 用户看到的是裸断连（T8-d 实测）。生效版本为 spring-ai-openai **1.1.2**（`dependency:tree`；本机 Maven 本地库在 `D:\develop\Maven\...\maven_repo`，不在 `~/.m2`），`OpenAiChatModel.Builder.retryTemplate(...)` 在 1.1.2 上存在。另核实：**引擎没有任何流式模型调用**（全仓 main 无 `ChatClient.stream()`，助手主循环与看图都是阻塞 `.call()`），`RetryTemplate.execute` 只出现在 `internalCall` 的 lambda 中 ⇒ **默认重试覆盖全部生产模型调用**，故 R1（取消不关闭上游，仅流式路径适用）当前**不可达**（另记 decisions 订正）。
  - ① **重试有界**：自定义 `RetryTemplate` 接到两个模型上——总预算 45s（`TimeoutRetryPolicy`）+ 尝试 ≤4 次（`SimpleRetryPolicy`）+ 同现状两类异常 + 退避 500ms 起指数增长、4s 封顶（`CompositeRetryPolicy` 组合，`optimistic=false`）。效果：秒失败（连不上/5xx）≈4 次、总 <5s；慢失败（单次就 60s）⇒ 45s 预算在首次尝试后即到期、不再重试 ⇒ 总 ≈60s。**不用 `RetryUtils.SHORT_RETRY_TEMPLATE`**（它只是把退避换成固定 100ms，仍是 10 次尝试，对"每次 60s 才超时"的形态无效）。
  - 验收：单测——重试（模板参数有界 + 总预算真的会截断 + 两个模型都挂上了它 + 非重试异常只试一次）、看图（峰值并发恰为 4、结果保序、单张超时只降级该张、单张失败不连坐、登录态失效按波跳过并如实报"剩余未尝试"）+ 门禁绿 + 负向控制（池改 1 → 并发断言红；摘 `retryTemplate` → 预算断言红）

  - **新发现（同批实测，2026-09-15，挂账不修，超出 T18 文件范围）**：**MCP 服务（8127）不可达时，图库助手的每一次对话都会在"装配工具"这一步整条失败**——栈顶为 `McpSyncClient.listTools` ← `HuoshanAssistantController.chat:107`（`mcpToolCallbackProvider.getToolCallbacks()` 的首次连接），实测 **20.1s** 后回 HTTP `50000 系统内部异常`（JSON，**连 SSE 流都没有**），前端只能看到"助手连接中断"。T9 的设计（"服务没起也不该拖垮引擎启动，首次调用时才连"）只覆盖了 **Bean 不存在**（`AI_MCP_CLIENT_ENABLED=false`）这一种；Bean 在、服务不可达时没有降级路径。对照实测：同一镜像下加 `--spring.ai.mcp.client.enabled=false` 起，同一次对话 3.95s 正常出 `error` 帧 ⇒ 变量只有这一个。日志 `%TEMP%\t18-mcp-on.log`。**收口方向**（未拍板）：把 `getToolCallbacks()` 的结果按"失败即空数组"降级（沿用既有"少一个工具照常开对话"口径），或把 MCP 初始化改成显式健康探测后再挂。
    - **语义复核（本次实测；临时探针落在 `ai/agent/target/probe/`，不入库、`mvn clean` 即消失）**：`TimeoutRetryPolicy` 在 `open()` 时取 `System.currentTimeMillis()` 记起点（反编译 `TimeoutRetryPolicy$TimeoutRetryContext` 确认：`start` 在构造时取一次墙钟，`isAlive()` 与之作差），`CompositeRetryPolicy(optimistic=false)` 在**每次尝试前后各咨询一次**，退避序列固定 `×2`（500→1000→2000）。因 `Thread.sleep` 只会比请求的**更晚**返回，**唯一脆弱的是"必须通过"的那次预算检查**——"必须在预算外"的那次只会被延迟放大。
    - **先红（确定性复现，不需要造负载）**：在重试回调里注入固定延迟即可重放该故障。旧参数（800/500，余量 300ms）实测 `0ms→2 次`、`400ms→1 次`、`700ms→1 次`；另在重负载下（非注入；4 个 JVM × 64 自旋线程，16 核机）48 次里 **15 次**退化成 1 次，极端负载（自旋线程数远超核数）下还出现过 1 次 **0 次**（线程在"首次预算检查"之前就被拖延超 800ms，回调一次都没跑到）。**同时订正旧记录的方向**：本文件 T19 条目与 `F12` 原有措辞记的是 `expected: 2 but was: 3`，但按上述语义"3 次"要求累计退避 <800ms（数学上不可达），只能由**墙钟回拨**解释（预算参照墙钟而非单调钟）；单调钟下真实可复现的偏差是**变少（1 次）**，不是变多。
    - **后绿**：新参数 = 预算 **2500ms** + 首次退避 **1000ms** + 上限 10 次 ⇒"第 2 次尝试前仍在预算内"留 1500ms 余量，"第 3 次尝试前已超预算"天生有 500ms 余量（延迟只会让它更超）。同注入实测：`0ms→2`、`400ms→2`、`1400ms→2`。代价：该用例 1.5s → 约 3s（整个类 9.4s → 10.7s）。
