## 验证了什么

- **型号与图片能力**（2026-09-28 读厂商文档）：官方"图片理解"页「支持的模型列表」写明"当前支持 `mimo-v2.6-flash`、`mimo-v2.6-pro`、`mimo-v2.6-pro-ultraspeed` 和 `mimo-v2.5`"；`mimo-v2.6-flash` 模型页的规格写明输入模态是**文本、图像、视频、音频**、1M 上下文。→ 视觉那组可以同换，看图打标与后端 AI 打标不会失去图片能力。
- **协议面零改动**：官方示例仍是 `base_url=https://api.xiaomimimo.com/v1` 与 `extra_body={"thinking":{"type":"disabled"}}`，与既有 `base-url` / `extra-body` 口径一致；鉴权仍走 Spring AI 默认的 `Authorization: Bearer`。**本次没有改任何 Java 代码。**
- **入库残留搜索**：改完后全仓（排除 `target/`）搜 `mimo-v2.5`，只剩四处，全部为有意保留：两处测试夹具字面量（见下）、`ai/agent/.../application-local.yaml:14`（新注释里引用旧口径）、以及历史文档（`docs/decisions/**`、`docs/plans/records/**`、`docs/handoff/**`，按"不可变"不回填）。

## 没改什么（有意为之）

- **两处测试夹具**：`ai/agent/.../FlowWindowBasedChatMemorySummaryModelTest:146`（`properties.getAssistant().setModel("mimo-v2.5")`）与 `backend/.../AiVisionTagApiTest:33`（`MODEL = "mimo-v2.5"`）。它们不读生产配置、不构成行为依赖（前者是摘要模型接线的探针值、后者是构造请求用的常量），改它只会制造无意义 diff。
- **线上 prod**：型号由服务器环境变量 `AI_OPENAI_MODEL` / `AI_OPENAI_VISION_MODEL` 决定，本次只改入库默认值——对"环境变量已设"的 prod 无行为影响。线上要换须改环境变量并重启引擎，验收点见 `deploy/prod-checklist.md` §3。
- **历史详情与记录文件**：`docs/decisions/2026-09-15-topic02.md`、`2026-09-16-dashscope-decoupling.md`、`docs/plans/records/**`、`docs/handoff/**` 里的 `mimo-v2.5` 是被取代时期的历史事实，不回填。

## 没验证什么（明确的缺口）

- **没有真机冒烟**：`ai/agent` 的单测全部与型号无关（型号只是配置值），因此**"换成 v2.6 后助手照常工作"这件事没有任何自动化或真机证据**。现有全部真机证据都在 `mimo-v2.5` 上取得（带工具的多轮调用、搜图入库 18.6s、智能整理 53.4s、看图建议），换型号后需重跑才算同口径验收。已在 F12 顶部加了一行醒目提示，指向本条。
- **验收点（未执行）**：起引擎后日志应出现 `model=mimo-v2.6-flash ... extraBodyKeys=[thinking]`；再问一句会触发工具调用的话，确认 `tool` 帧照常、无 `error` 帧。
- **速度对比**：无数字。`-flash` 定位是高效推理、预期比 `mimo-v2.5` 快，但未实测，不做承诺。

## 负向控制（本任务未做）

本任务是配置值替换，没有可"注入故障"的逻辑分支，因此没有负向控制用例。它唯一的自动化护栏是"入库文件里不再出现旧型号"这一条人工复查（上面的残留搜索），未固化成脚本。
