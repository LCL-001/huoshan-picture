# 档 2 用户可见 MVP（T10 + T11）实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 AI 助手"用户能用"——图库 backend 新增代理端点（服务间 API key + 凭据组透传 satoken/Spring Session + SSE 流转发），图库前端新增助手界面（入口 + 对话面板 + SSE 步骤折叠条）。验收：登录后在界面里对话、折叠条逐步可见，观察到的数据来自用户真实凭据。

**Architecture:** 两条新增链各自独立，引擎侧**零改动**：

1. **代理链（backend，T10）**：`AiAssistantController`（`GET /api/ai/assistant/chat`）→ 自身登录门槛（Spring Session `getLoginUser`）→ 从**浏览器请求**取出两把凭据（`satoken` 头/ Cookie / query 三处任一，`SESSION` 会话 id 取自 `request.getSession(false)`）→ `AiAssistantProxyManager` 用 JDK `HttpURLConnection` 打引擎 `GET /api/ai/huoshan/chat`（带 `X-Internal-Api-Key` + `satoken` 头 + `Cookie: SESSION=…`）→ 逐帧中继 SSE 回 `SseEmitter`。
2. **前端链（T11）**：`routes`/菜单入口 → `AssistantPage.vue`（对话面板）→ `utils/assistantSse.ts`（`EventSource` 封装，消费引擎事件协议）→ `components/assistant/StepTimeline.vue`（`a-collapse` 步骤折叠条）。

**Tech Stack:** 后端 Java 17 / Spring Boot 2.7.6（`SseEmitter`、JDK `HttpURLConnection`、`@ConfigurationProperties`、`MdcThreadPoolExecutor`）；前端 Vue 3 / TS / Ant Design Vue（原生 `EventSource`、`a-collapse`）。**不新增任何依赖**。

**实现口径说明（相对任务文本的补充/差异，需在 decisions.md 记录）:**

1. **代理不校验两把凭据是否属于同一用户**——decisions.md 2026-09-14 B 落地条已定口径："引擎**不**自行校验两把是否属于同一用户，交由**图库**判定（不一致时回 `SPACE_NOT_LOGIN`）"。代理同理：它只做"取出并原样转发"，不在第二处复刻授权判断（也避免自建 Sa-Token 解析与图库判定口径漂移而误拒）。不一致的后果是工具层结构化错误 `{"error":true,"code":40102,…}` 由模型转述给用户——可见、可诊断，档 2 接受。
2. **代理只做"存在性"fail-closed，不做身份判定**：session 缺失 → 40100；`satoken` 缺失 → 40100（消息区分"请先登录"与"登录态不完整，请重新登录"）。存在性检查与身份判定分离，与引擎侧"缺任一把在入口即拒 40000"同构。
3. **`/ai/**` 不进 `SaTokenConfigure` 拦截路径**，端点内显式 `userService.getLoginUser(request)` 拿登录态。理由：Sa-Token 拦截器与注解只在注册路径上生效，不注册则 `@SaCheckLogin` 会**静默失效**（比不写更危险）；显式调用与 `SpaceAnalyzeController` 等既有写法一致，且避免给 SSE 端点套一层注解拦截的不确定性。**本端点因此不依赖 Sa-Token 的 token 解析做门槛，只把 token 当"要转发的原料"**。
4. **SSE 转发选型：`SseEmitter` + JDK `HttpURLConnection` + 专用有界守护线程池**（设计文档 L110 留的"实施时定"在此定）。备选与否决理由：Spring `WebClient` 需新增 webflux 依赖（backend 目前零 webflux）；OkHttp `EventSource` 需新增直接依赖，而仓内 `okhttp-2.7.5` 只是 COS SDK 的传递依赖（2.x 太老，按 AGENTS 规则 14 不该被直接使用）；hutool `HttpRequest` 已在栈内但流式读取语义不如 `HttpURLConnection` 直白。**结论：零新增依赖**——`HttpURLConnection` 的 `getInputStream()` 逐行读即可，`setConnectTimeout/setReadTimeout` 一处给全两把超时。
5. **上游错误与代理侧失败都转成可见的 `answer` 事件 + `[DONE]`**（不引入新的 SSE 事件类型，不给引擎加契约）。三类：① 上游返回非 SSE（`Content-Type` 非 `text/event-stream`，即引擎的 401/40000/50000 JSON 错误）→ 取其 `message` 合成一条 `answer`；② 连接/读取超时、IOException → 合成 `answer` 写"助手引擎暂时不可用"；③ 正常流 → 逐帧原样中继，遇 `[DONE]` 即 `complete()`。理由：`EventSource` 读不到 HTTP 状态码与错误响应体（且本仓 `GlobalExceptionHandler` 恒回 HTTP 200），不做这一步前端只会看到"连接断开"而无任何原因；这也是"前端错误渲染"在档 2 能验收的最小闭环（引擎侧真正的错误事件语义仍挂账）。
6. **客户端中断即断开上游**：`emitter.onCompletion/onError/onTimeout` 触发时 `HttpURLConnection.disconnect()`。这是**代理侧**的上游（引擎），连接句柄在我们手里，能干净关掉；与 decisions.md 挂在档 2 之后的 R1（**引擎侧** provider 连接因 `Flux.cache(0)` 取消不断开）不是同一回事，不要混为一谈。
7. **凭据只在请求生命周期内存流转**：不落库、不进日志、不进 MDC；`log.info` 只记 `userId` 与 `chatId`，**永不打印 token / 会话 id**。
8. **前端用原生 `EventSource`（GET）+ `withCredentials: true`，并在 `[DONE]`/`onerror` 里显式 `close()`**。理由：引擎端点是 GET（天然适配 `EventSource`）；`EventSource` 的信号是 Cookie（开发态 5173→8123 同站不同端口，`SESSION`/`satoken` 双 Cookie 自动携带，`CorsConfig` 已 `allowCredentials(true)`）；**不能复用 `request.ts` 的 axios 实例**（`timeout: 10000` 会掐断长连接，且浏览器端 axios 无流式响应形态）。**`close()` 是必须的**：`EventSource` 在连接正常结束（EOF）与出错时都会**自动重连**，不显式关闭就会把同一 `message` 重发一遍（重跑一次 agent，重复调工具）——这条约束代码注释里写明。
9. **对话串由前端生成 `chatId` 并跨轮复用**（`crypto.randomUUID()`，存 `sessionStorage`，配"新对话"按钮重置）；轮内多轮记忆由引擎按 `chatId` 派生 `conversationId` 承载。"新对话"即换 `chatId`，旧会话记忆留存但不再续聊。
10. **不做防抖/并发控制以外的限流**：同一页面同时只允许一条流（发送中禁用输入与发送按钮），"停止"按钮 `close()` 当前流。跨页面/跨用户的多流并发由线程池上界（64）兜住，被拒时 `completeWithError` 让请求响亮失败，不静默挂住。

- [ ] **Step 2: 专用线程池**

`ThreadPoolConfig` 新增 `aiAssistantExecutor`：SSE 转发线程会被一次对话**占满整个生命周期**（最长 300s），放进 `async-task-` 或 `picture-upload-` 都会把它们饿死；用 `SynchronousQueue` + 上界 64 直接拒绝（不给队列，避免长任务堆积到看不见）。沿用 `MdcThreadPoolExecutor`（traceId 透传到转发线程）与守护线程命名惯例。

```java
@Bean(name = "aiAssistantExecutor")
public ExecutorService aiAssistantExecutor() {
    // SSE 转发线程按对话时长占用（最长 300s），必须与短任务线程池隔离；
    // 用 SynchronousQueue + 上界 64：不排队，超限直接拒绝（由调用方完成错误响应），避免长任务静默堆积
    MdcThreadPoolExecutor executor = new MdcThreadPoolExecutor(
            0, 64, 60L, TimeUnit.SECONDS,
            new SynchronousQueue<>(),
            new ThreadFactory() {
                private int count = 0;
                @Override
                public Thread newThread(Runnable r) {
                    Thread thread = new Thread(r);
                    thread.setName("ai-assistant-" + (++count));
                    thread.setDaemon(true);
                    return thread;
                }
            },
            new ThreadPoolExecutor.AbortPolicy());
    log.info("AI 助手转发线程池初始化完成，最大线程数: {}", 64);
    return executor;
}
```

### Task 2: 代理转发管理器（T10-b）

**Files:**
- Create: `backend/src/main/java/com/lcl/yunpicturebackend/manager/ai/AiAssistantProxyManager.java`

职责：把一个"已鉴权 + 已有凭据"的请求转成一条 SSE 流。核心实现（关键片段）：

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class AiAssistantProxyManager {

    /** 与引擎 BaseAgent 的 SseEmitter 超时对齐 */
    private static final long EMITTER_TIMEOUT_MS = 300_000L;

    private final AiAssistantProperties properties;
    private final ObjectMapper objectMapper;

    @Resource(name = "aiAssistantExecutor")
    private ExecutorService executor;

    /**
     * 打开一条到引擎的 SSE 流并以 SseEmitter 回给浏览器。
     * 凭据只在本次调用内流转，不落库、不进日志。
     */
    public SseEmitter chat(String message, Long userId, String chatId, String satoken, String sessionId) {
        String baseUrl = requireConfigured(properties.getEngineBaseUrl(), "图库助手引擎地址未配置");
        String apiKey = requireConfigured(properties.getInternalApiKey(), "图库助手引擎密钥未配置");
        SseEmitter emitter = new SseEmitter(EMITTER_TIMEOUT_MS);
        AtomicReference<HttpURLConnection> upstream = new AtomicReference<>();
        // 客户端关流/出错/超时：断开上游（代理侧上游由我们掌控，能干净关掉）
        emitter.onCompletion(() -> closeQuietly(upstream));
        emitter.onError(e -> closeQuietly(upstream));
        emitter.onTimeout(() -> closeQuietly(upstream));
        try {
            executor.execute(() -> forward(emitter, upstream, baseUrl, apiKey, message, userId, chatId, satoken, sessionId));
        } catch (RejectedExecutionException e) {
            emitter.completeWithError(e);
        }
        return emitter;
    }
}
```

`forward(...)` 的要点（按顺序，全部落在同一个方法或私有子方法里，不嵌套三层以上）：

1. 拼 URL：`{baseUrl}/ai/huoshan/chat?message={URLEncoder.encode(message, UTF_8)}&userId={userId}[&chatId={urlencoded}]`；
2. 开 `HttpURLConnection`：GET、`setRequestProperty("X-Internal-Api-Key", apiKey)`、`setRequestProperty("satoken", satoken)`、`setRequestProperty("Cookie", "SESSION=" + sessionId)`、`setRequestProperty("Accept", "text/event-stream")`、`setConnectTimeout/setReadTimeout`（由 `Duration` 转毫秒）；`upstream.set(conn)`；
3. 取状态码：`200` 且 `Content-Type` 含 `text/event-stream` → 走中继；否则读 `getErrorStream()`（`401` 用错误流，`200` 但 JSON 也要读输入流）→ 合成一条 `answer` 错误事件；
4. 中继循环：`BufferedReader` 逐行读；`data:` 前缀行累积为一条事件（多行用 `\n` 连接，符合 SSE 规范）；空行=事件结束 → `payload.equals("[DONE]")` 则 `emitter.complete()` 并退出，否则 `emitter.send(payload, MediaType.TEXT_PLAIN)`；
5. `catch (IOException | RuntimeException)`：合成 `answer` 错误事件 + `[DONE]` + `complete()`（**不要**让异常静默吞掉，也不要上抛到已返回的 emitter）；
6. `finally`：断开连接。

合成的错误事件（单一出口，便于测试断言）：

```java
private void sendErrorAsAnswer(SseEmitter emitter, String text) {
    try {
        Map<String, Object> payload = new LinkedHashMap<>();
        payload.put("event", "answer");
        payload.put("content", text);
        emitter.send(objectMapper.writeValueAsString(payload), MediaType.TEXT_PLAIN);
        emitter.send("[DONE]", MediaType.TEXT_PLAIN);
    } catch (IOException ignored) {
        // 流已断：客户端已走，无需再补救（这里不是"吞错误"，是对已废弃连接的正常收尾）
    } finally {
        emitter.complete();
    }
}
```

同时提供 `String upstreamMessage(String body)`：从引擎的错误 JSON 里取 `message`（`objectMapper.readTree`，失败则截断原文兜底），用于把引擎的 `40100/40000/50000` 转成人能读的一句话。
