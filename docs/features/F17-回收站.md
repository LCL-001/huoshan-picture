# F17 图片回收站

> 覆盖任务：docs/plan.md T50（后端）、T51（保留期清理）、T52（前端）。
> 口径：docs/decisions.md 2026-10-12「图片回收站口径」。设计与已知限制见本文件。
> 相关：删除语义变更同时影响普通图库页面（`PictureList` / 图片详情 / 管理端图片管理）的删除按钮。

## 一句话

单张删除不再立即销毁，而是先进**回收站**（保留 30 天）：期间可随时**恢复**（回到原空间，名额回补），到期由定时任务**自动彻底删除**（含 COS 原件与缩略图）；也可手动**彻底删除**。**只做图片、只回原空间**——删空间仍是现状的永久级联（整个空间连同图片一起消失，不进回收站）。

## 怎么用

- 入口：左侧栏「回收站」（登录后可见，`/recycle_bin`）。
- 列表：缩略图、名称、所属（空间 id 或「公共图库」）、大小、删除时间；分页。
- 单张操作：**恢复** / **彻底删除**；也可勾选多张后「恢复选中」「彻底删除选中」（单次最多 50 张）。
- 恢复会逐张复核：原空间已不存在、或空间数量/容量已达上限时，该张失败并在提示里说明原因（其余张不受影响）。
- 「彻底删除」不可撤销（同时清 COS）；「恢复」不牵动审核状态。
- 可见范围：**管理员**看全部；**普通用户**只看「公共图库本人上传的 + 自己拥有的空间 + 有 `picture:delete` 权限的团队空间」里的。

## 怎么实现

### 关键文件

### 核心流程

```
删除：checkPictureAuth(picture:delete) → UPDATE isDelete=1, deleteTime=NOW()（事务内）+ 扣空间名额 + 清列表缓存
      ✗ 不再删 COS（恢复后还要用）
恢复：逐张 checkPictureAuth(picture:delete) → 原空间在？（checkPictureAuth 查不到空间会抛 40400 → 提示"原空间已不存在"）
      → 事务内 restore(isDelete=0, deleteTime=NULL) + 回补名额（**配额条件写在 UPDATE 的 WHERE 上**，影响 0 行即额度不足 → 整笔回滚）→ 清列表缓存
彻底删：逐张 checkPictureAuth → 物理删行 → 按 URL 引用计数为 0 时清 COS → 清列表缓存
保留期：@Scheduled（默认 1h/次）→ selectExpiredTrash(deleteTime < now - retentionDays, limit) → 逐条物理删 + 清 COS
```

### 关键设计与理由

1. **COS 延迟清理是回收站的前提**：改前 `deletePicture` 删库即清 COS，若沿用，恢复出来的记录会指向已被删除的对象。现在 COS 只在「彻底删除 / 保留期到期」时按引用计数为 0 才清（复用既有 `cleanupPictureFile`）。代价是回收站里最多多留 `retention-days` 天存储。
   - **引用计数的口径（T55）**：把**存活行 + 回收站内可恢复行**（`isDelete=1` 且 `deleteTime` 不为空）都算引用，走裸 SQL `PictureMapper#countUrlReferences`——全局逻辑删除会给 Wrapper 查询自动补 `isDelete=0`，用 `lambdaQuery` 数会把回收站里的引用漏掉，导致同 URL 的另一张图被误清 COS、恢复后成死链。空间/用户级联的永久删除（无 `deleteTime`、不可恢复）不计入引用。`cleanupPictureFile` 是彻底删除、过期清理、替换、回滚补偿四条路径的唯一出口；**删空间级联**（`SpaceServiceImpl.cleanupRemovedPictures`）不是它的出口，但共用同一计数口径（`IPictureService#countUrlReferences`），避免同样的误清（T55 补记）。
2. **`deleteTime` 是"是否在回收站里"的唯一判据**：删空间时级联软删的图片**不带** `deleteTime`（MyBatis-Plus `remove(wrapper)` 不走我们的裸 SQL），因此天然不进个人回收站、也不会被保留期任务扫到——这正是"只做图片、不做空间级回收"的落点。
3. **读已删行必须裸 SQL**：全局逻辑删除（`@TableLogic` + `mybatis-plus.global-config`）会给所有 `BaseMapper`/Wrapper 查询自动补 `isDelete=0`；回收站列表/恢复/彻底删只能自己写 SQL。这是本仓第一处自定义 mapper SQL。
4. **恢复要回补名额，且配额判定必须原子（T57）**：删的时候已经扣了 `totalCount/totalSize`，N 天后空间可能已被填满——恢复因此逐张校验 `maxCount/maxSize`。但这道校验**不能**"先读空间快照、再在内存里判断、然后无条件加"：两个并发恢复（或恢复与上传同时发生）会各自读到同一个旧快照一起通过，各加一次把计数加超上限。正确做法是把配额条件写进 `UPDATE` 的 WHERE（与上传路径同口径）：影响 0 行即"额度不足"，抛异常让"恢复记录 + 回补名额"这**同一个事务**整笔回滚——记录留在回收站，额度也没有被多记。失败文案由失败路径上的一次空间回读给出（**只影响文案**，不影响该不该拒绝）。
5. **归属过滤在服务端、不看请求参数**：列表按登录用户算出可见空间集合（拥有 + 有 `picture:delete` 的团队空间）+ 公共图库本人上传；管理员看全部。避免"传别人 spaceId 越权枚举"（与 T3.1 的对象级鉴权口径一致）。
6. **逐张结果、一张失败不连坐**：恢复/彻底删都返回 `List<PictureTrashResultVO>{pictureId, ok, message}`；前端按成功/失败分别提示。
7. **写操作先校验双登录态同属一人（T56）**：删除/恢复/彻底删除三个写操作在逐资源 RBAC 之前，先经 `LoginSessionValidator#requireConsistentLogin` 要求 Spring Session 与 Sa-Token space 会话都存在且登录 id 一致，不一致回 `40102`（「空间登录态已失效，请重新登录」）。原因：注解鉴权按 Sa-Token 判定、服务层执行按 Spring Session 判定，两边不一致时注解保护会落空；且改密/登出只清一侧时，被盗的另一侧凭据仍能操作。读接口（回收站列表等）不在此校验内。

## 已知限制

1. **只做图片回收站**：空间级/用户级回收站不做（spec「不做的事」）。删空间/删用户仍是永久级联，其图片不进回收站、也不会被保留期任务处理。
2. **不进回收站的两条删除路径**：① 删空间级联；② `PictureAiTagManager` 等内部路径不涉及删除。回收站只覆盖 `/picture/delete`（普通图库页面与管理端图片管理共用的那个单张删除）。
3. **恢复只回原空间**：回收站内不支持改归属（跨空间移动不做）。
4. **回收站内的图片不参与 AI 助手工具**：助手只读工具走的是普通查询（自动过滤 `isDelete=0`），看不到回收站内容。
5. **列表可见范围是"能删的"而不是"删过的"**：团队空间里拥有 `picture:delete` 的成员能看到该空间所有人删的图片（不区分删除者）；这是刻意的（与删除权限口径一致），若产品要"只看自己删的"需另加条件。
6. **保留期任务单轮上限 200 条**：`BATCH_LIMIT=200`，积压很多时分多轮清（每小时一轮）；任务无分布式锁，多实例会并发扫同一批（`purgeTrashedById` 带 `isDelete=1` 条件，重复执行不会误删，只是多打一次日志）。
7. **前端未做浏览器人工验收**：只过了 `type-check`/`eslint` 与既有检查脚本；`/recycle_bin` 的真实点击（勾选、批量恢复/彻底删、失败提示）待人工过一遍。
8. **`deleteTime` 为空的历史软删行不会自动清理**：本功能上线前已被 `isDelete=1` 的图片（含删空间级联的）没有 `deleteTime`，保留期任务不会碰它们；历史残留的清理仍是独立事项（见 plan.md 未决区）。
9. **COS 存储成本**：回收站期间（默认 30 天）原件 + 缩略图都留着；量大时需按 `retention-days` 调小。
10. **恢复的"上限"文案不区分是谁占了名额**：并发下失败者只回"空间数量/容量已达上限"，指不出是另一个请求刚占的——用户可读性够用，不做归因。另：**上传路径**的配额条件（`totalSize + {0} <= maxSize`）没有 `IS NULL` 守卫，本仓空间创建时这两列必填、属理论面；T57 按任务范围只改了恢复路径，未顺手统一（观察，未改）。
