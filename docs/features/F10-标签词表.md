# F10 标签词表（T5，2026-09-14）

## 是什么

把原来硬编码在 `PictureController.listPictureTagCategory` 里的 9 个标签 + 5 个分类搬进数据库表 `tag`（全局词表，不按空间拆），并让图片编辑动作反过来"喂养"词表：编辑图片写入的标签/分类会自动注册进词表并累加使用次数。

这是 AI 助手一期（F11）的地基：T7 的 visionTagger 视觉打标工具会把这张表的词条注入提示词，要求 AI"优先复用已有标签，词表缺了才提议新标签，新标签由图库自动注册"——没有受治理的开放词表，AI 自由打标会把前端标签筛选脏数据化。

## 怎么用

- **前端/调用方**：`GET /api/picture/tag_category` 返回结构不变，仍是 `PictureTagCategory{tagList, categoryList}` 两个字符串列表（前端标签筛选无感），数据源从硬编码变为查表（按 id 升序，与种子顺序一致）。
- **编辑图片**：`/picture/edit`（单编）与 `/picture/edit/batch`（批编）写入的 tags/category 会同事务注册进词表——已有词 usageCount +1，新词自动注册且 usageCount 起始 1。一次编辑调用每个词只计 1 次，不随批编图片数放大。
- **词表查询（服务内部）**：`ITagService.listNamesByType(TagTypeEnum)` 按类型取词条；`upsertVocabulary(names, type)` 做 upsert（空白词跳过、去重）。
- **新环境部署**：按顺序执行 `backend/sql/create_table.sql` 与 `backend/sql/create_tag_table.sql`（后者幂等可重复执行，含种子数据）。

## 怎么实现

- **表**：`tag(id, name, type, usageCount, createTime, updateTime, isDelete)`，`UNIQUE KEY uk_name_type(name, type)` 保证同类型词条唯一，`INDEX idx_type` 支撑按类型查询。列名沿用库内 camelCase 约定（设计文档速写为 usage_count）。
- **词表服务**：`TagServiceImpl.upsertVocabulary` —— 先对每个词做原子自增 `UPDATE ... SET usageCount = usageCount + 1`（存在即命中，无需先读后写）；未命中再 INSERT（usageCount=1）；并发首插撞唯一键时捕获 `DuplicateKeyException` 退化为自增。全程无自定义 SQL，纯 MyBatis-Plus API。
- **动态化**：`PictureController.listPictureTagCategory` 改为调 `tagService.listNamesByType`，`PictureTagCategory` 结构一字未动。
- **编辑接线**：批编 `editPictureByBatch` 本有 `@Transactional`，upsert 插在图片列表判空早退之后（没有图被改就不计使用）；单编 `editPicture` 原先无事务，因"词表 upsert 与图片更新同事务"的要求补加 `@Transactional(rollbackFor = Exception.class)`，upsert 在 updateById 成功后、清缓存前执行——任一环节失败整体回滚。
- **实体/枚举**：`Tag`（`@TableLogic` 逻辑删除）、`TagMapper`（BaseMapper + 空 XML 骨架，随 `@MapperScan` 自动注册）、`TagTypeEnum(TAG/CATEGORY)`。

## 怎么验证

- **集成测试** `TagVocabularyIntegrationTest`（3 用例，随全量回归跑本地 MySQL）：
  - `seedMigratedAndTagCategoryDynamic`：9 标签 + 5 分类种子全部经 `/tag_category` 动态返回，结构逐字段兼容；
  - `batchEditUpsertsVocabularyAndCounts`：批编带已有词 + 新词 + 分类 → 已有词计数 +1、新词注册且 usageCount=1、新词立即可见于 `/tag_category`；
  - `upsertSkipsBlankAndDeduplicates`：空白词跳过、同词去重只计 1 次。
- **全量回归**：`mvn -B test` 65 用例全绿（62 存量 + 3 新增）；门禁口径（无 MySQL/Redis 纯单测 13 用例）不受影响。
- **手工冒烟**：启动 backend 后 `GET http://localhost:8123/api/picture/tag_category`，应返回词表内容；编辑一张图打上新词后再查，新词出现且计数为 1。

## 已知限制

- **usage_count 只加不减**：把图片标签从 A 改成 B，A 的计数不回收。词表治理一期口径"只增改不删"，删除/回收留后续。
- **词表无管理端点**：一期没有增删改词表的接口，词表靠编辑动作自然生长 + SQL 手工维护；也没有逻辑删除入口——由于 uk_name_type 含已删行，一旦逻辑删除某词条，同名词条无法重新注册。
- **`/picture/update`（管理员编辑）未接词表**：spec 范围只点名单编/批编两处。
- **`/tag_category` 每次查表、无缓存**：匿名轻查询，量小；有压力后再议加缓存。
- **单编路径的 upsert 接线**由编译 + 全量回归覆盖（集成测试走批编路径直调同一 upsert 方法，satoken 登录态模拟成本高，未做单编端到端用例）。
- **批编计数口径**：早退路径（选中的图片不属于该空间/不存在）不写词表、不计数——词被真正写入图片才算"使用"。
- 排障记录：本任务集成测试曾红在"海报计数断言"，根因是测试辅助方法把词条类型硬编码为 tag（与连接池/事务无关），修复为按类型查询后全绿——记于此避免后来者被误导。
