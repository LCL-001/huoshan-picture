# F18 接口限流（注解式）

> 覆盖任务：docs/plan.md T49。
> 口径：docs/decisions.md 2026-10-12「接口限流口径」。
> 与既有频控的关系：本功能是**统一机制**，不替换 `UserServiceImpl` 里既有的邮箱验证码/登录失败频控与扩图每日配额——那些保持不变。

## 一句话

给**会调外部付费服务或可被用户滥用**的端点加一层固定窗口限流：方法上标 `@RateLimit`，切面用 Redis 计数，窗口内超额度返回 **42900「请求过于频繁，请稍后再试」**。**不做全站 blanket 限流**（spec「不做的事」）——只打在点名的那些端点上。

## 怎么用

- 对**调用方**：正常使用无感；短时间内超过额度时会收到 42900 与提示文案（前端按 `message` 展示）。
- 对**开发**：新端点要限流，就加 `@RateLimit(key=..., limit=..., windowSeconds=...)`；边界守卫测试 `RateLimitCoverageGuardTest` 会断言点名的端点都带着注解。
- 对**运维**：总开关 `app.rate-limit.enabled`（默认 `true`）；压测/联调可用 `--app.rate-limit.enabled=false` 关闭。

## 怎么实现

### 关键文件

| 层 | 文件 | 职责 |
|---|---|---|
| 注解 | `annotation/RateLimit.java` | `key` / `limit` / `windowSeconds` / `dimension`（USER 默认，未登录退 IP） |
| 切面 | `aop/RateLimitAspect.java` | `@Around("@annotation(rateLimit)")`：INCR + 首次设 TTL → 超额度抛 42900 |
| 错误码 | `exception/ErrorCode.java` | 新增 `TOO_MANY_REQUESTS(42900, "请求过于频繁，请稍后再试")` |
| 配置 | `resources/application.yaml` | `app.rate-limit.enabled`（默认 true） |
| 打点 | `controller/{PictureController,AiAssistantController,FileController}.java` | 13 个端点标注解 |

### 核心流程

```
请求 → @Around 拦截
  总开关关？ → 直接放行
  非 Web 上下文？ → 直接放行
  key = huoshantuku:ratelimit:<注解key或类名.方法名>:<主体>
  主体 = USER 维度：Spring Session 里的登录用户 id（u<id>）；未登录退 IP（i<ip>）
  count = INCR key；count==1 时 EXPIRE windowSeconds（键存在但无 TTL 时补一个）
  count > limit → 抛 BusinessException(42900)
  Redis 异常 → 记 warn 后放行（fail-open）
```

### 关键设计与理由

1. **只打高成本/敏感端点，不做全站限流**：全站 blanket 限流会碰 SSE 长连接、静态资源与内部转发路径，误伤面大；点名的这些端点才是"会烧钱（扩图 / 视觉打标 / 以图搜图 / 大量 COS 写入 / LLM 代理）或可被滥用（助手对话与取票）"的。
2. **固定窗口 INCR + 惰性 TTL，不用 Lua**：与 `UserServiceImpl.incrWithWindow` 同口径。单纯 INCR 语义下"INCR 成功但 EXPIRE 没执行"的最坏结果是窗口被延长，不是超发；换 Lua 收益有限却多一处脚本要维护（且本仓 Redis 约束是 5.x，Lua 只是为原子性，这里不需要）。
3. **Redis 异常 fail-open**：限流是防护手段、不是业务正确性来源。Redis 抖动不该让整个站点 5xx（与既有 `incrWithWindow` 的 catch→null 同口径）。代价是 Redis 挂掉时限流失效——可接受。
4. **主体优先取登录用户、直接读 Session 而不是 `getLoginUser`**：`getLoginUser` 会 `getById` 查库，限流不该给每个请求加一次 DB 读；直接读 `USER_LOGIN_STATE` 会话属性即可，未登录再退 IP。
5. **命名空间前缀区分维度**（`u`/`i`）：避免"用户 id 恰好等于某 IP 字符串"这类撞键（理论上的）。
6. **边界守卫而非只靠单测**：注解被摘掉不会有编译错误，`RateLimitCoverageGuardTest` 用反射钉住 13 个端点都带 `@RateLimit(key=...)` 且额度为正（同一手法见 `PictureAiTagAdminGuardTest`）。

## 怎么验证

- **门禁（不依赖 MySQL/Redis）**：`RateLimitAspectTest` 6 例——窗口内放行且首次设 TTL；第 limit+1 次抛 42900 且不再放行；总开关关闭时**零 Redis 交互**；Redis 异常 fail-open；主体落在键里（登录用户 `u7` / 未登录 IP 兜底）；无 Web 上下文放行。
- `RateLimitCoverageGuardTest` 1 例——13 个端点覆盖。
- **负向控制（规则 12）**：① 边界改成 `count > limit + 1` → `RateLimitAspectTest.rejectsOverLimit` 红（1 条，恰好）；② 摘掉 `AiAssistantController.chat` 的注解 → `RateLimitCoverageGuardTest` 红并指名 `chat`。两者改回即绿。
- **全量**：backend 门禁与 `ai/agent` 门禁全绿（提交 `06770d6`）。
- **未做**：真机（浏览器/压测）验证限流触发，只由单测钉住语义。

## 已知限制

1. **固定窗口的边界效应**：窗口两端各来一批时瞬时可以通过接近 2×limit（固定窗口通病）。要平滑需滑窗/令牌桶，本功能不做。
2. **无频控「按接口总量」**：额度是"每主体每端点"，看不出全局压力；也没有告警。要有的话是监控侧的事（Prometheus 已有埋点基础）。
3. **IP 兜底的准确性**：`IpUtils.getClientIp` 依赖 `X-Real-IP`/`X-Forwarded-For`（生产由 nginx 写入）；直连或代理未注入时退 `remoteAddr`。限流场景影响有限。
4. **只覆盖点名的 13 个端点**：其它端点（如普通图片列表、空间分析）不限流；放大流量面要显式加注解（或改走全局方案，属另立决策）。
5. **额度是经验值**：10~60/分钟是按"正常人手速 + 留余量"定的，没有真实流量依据；上线后按实际误拦/滥用情况调。
6. **限流与既有频控并存**：邮箱验证码/登录失败频控、扩图每日配额仍在各自服务里，口径不完全统一（错误码也不同：那些用 50001）。本轮只做"新增统一机制"，未回头统一既有频控。
