## 一句话

档 3 实现"建议后批量改标签"和"搜图/给定链接按 URL 入库"；**2026-09-29 起写操作必须经确定性确认门**：助手生成待确认操作（卡片展示目标空间、数量与字段变化），用户确认后由后端按既存计划执行——模型提交计划 ≠ 用户授权，模型自然语言说"确认"不构成授权。查询、MCP `searchImage` 候选搜索与管理员 `visionTagger` 建议行为不变。

## 怎么用

当前可在助手对话框里直接请求：

- 查询自己的空间、图片与标签词表；
- 搜索图片素材并返回候选链接；
- **批量整理**：说清改哪个空间、哪些图、改成什么 → 助手生成"待确认：批量编辑图片"卡片 → 核对后点**确认执行**（或**取消**）→ 结果在卡片上就地展示；
- **URL 导入**（T41 起用户可见文案统一说"导入"——"入库"是内部术语，不上面；与图库页面 `UrlPictureUpload` 的"粘贴图片直链，点击提交即可导入"同一词汇）：把图片直链（也可来自 `searchImage` 候选）连同目标空间说清楚 → 生成"待确认：按 URL 导入"卡片（摘要两行：目标空间 id、图片直链 N 条）→ 确认后系统逐条下载并导入（额度照常扣减），卡片结果行是"导入完成：成功 N / M 条"；
- 管理员会话可让 `visionTagger` 看图并给标签/分类建议，落库同样走确认卡片。

取消只影响前端呈现（不发请求）；未确认的操作由后端短 TTL 自动过期作废，重新生成即可。卡片只在实时流中出现，刷新/回放后不重建（历史协议不含确认载荷），未确认的操作安全失效。

**历史验收场景（直接写形态，已退役）**：档 3 曾完成"逐张看图建议 → `batchEditPictures` 落标 → 回读复核"和"`searchImage` → `batchUploadByUrl` 入库"的端到端验证；这些实现基础已被确认门取代，直接写工具不复存在。

### 核心流程

**当前智能整理**：`listSpaces` → `getTagCategory` → `listPictures` → **`visionTagger`（一次最多 8 张，仅管理员会话，可选）** → `prepareBatchEditPictures` 生成待确认操作 → 用户在确认卡片确认 → backend 原子执行 `PictureService#editPictureByBatch`。
**当前素材入库**：`listSpaces` → **`searchImage`（MCP，可选）或用户直接给链接** → `prepareUrlImportPictures` 生成待确认操作 → 用户确认 → backend 逐条走 `PictureService#uploadPicture`（下载 → COS 转存 → 落库 → 额度记账）。

历史档 3 链路曾在建议后直接调用 `batchEditPictures`、在搜图后直接调用 `batchUploadByUrl`；T27 第一阶段将其摘出装配，**T27.6 起彻底删除**，写入只能由确认卡片的"确认执行"触发。

### 关键设计与理由

1. **粗粒度工具（一步一批）**：图库的按 URL 上传是**单张**端点，"批量"在工具内部循环完成；打标也是工具内一次看完 N 张。这样 20 步预算够用，模型不必"一张一步"。
2. **看图不让模型搬 URL**：`visionTagger` 只收图片 id，自己经 `GET /picture/get/vo?id=` 取地址再送多模态模型——复制长 URL 是模型最易出错的环节，且图库那个端点会按图片归属再做一次空间权限校验。
3. **建议/计划与写入分离，写入只能由确认触发（T27.5–T27.8 确认门）**：`visionTagger` 只给建议；prepare 工具只提交计划（backend 零写库）。写入发生在 backend `confirm` 原子消费之后，执行的是**服务端保存的原始计划**——模型无法把自然语言"确认"变成写入，也无法生成或持有确认凭据；确认请求只带 operationId+chatId+digest，没有可替换的业务 payload（口径见 `docs/decisions.md` 2026-09-29 行与实施计划 T27.4 的"明确不采用"清单）。
4. **写类工具"如实上报"**：prepare 工具的成功只代表"计划已生成待确认"，返回里明说"未改动数据"；执行结果由确认卡片就地展示——批编如实说"已提交 N 张"（图库按"空间 + id"过滤，不属于该空间的 id **静默跳过**，不逐张确认），URL 入库逐条上报成功/未成功与原因（文案为后端用户安全口径）。
5. **没配视觉模型、或调用者不是管理员，就不挂 `visionTagger`**（后者是 T17）：宁可让模型看见"手上没有这个工具"，也不给它一个每次都报错的工具 / 一个它没资格用的工具。**为什么按角色裁**：打标已是管理员能力（公共图库那条走管理端 `F14` 的入口），普通用户在助手侧留着只读 `visionTagger` 与"只有管理员能打标"不一致（用户 2026-09-15 拍板摘掉）。**怎么传**：代理把自己登录用户的角色放进 `X-User-Role` 头（与 satoken / SESSION 同信道），引擎 `HuoshanAssistantSession.isAdmin` **fail-closed** 判定（缺失/未知一律当普通用户）；**这不是授权**——引擎校验不了该头，而工具只读且以调用者自己的凭据打图库 API，能力边界仍由图库服务端判。
6. **思考模式必须关（DeepSeek）**：带 `tools` 的请求每轮都必须回传 `reasoning_content`，而 Spring AI 的 OpenAI 客户端不认这个私有字段 ⇒ 开着必 400；通过新加的 `extra-body` 配置直通 `{"thinking":{"type":"disabled"}}`。
7. **回放剥掉工具痕迹**（T12 修复）：记忆只存 assistant 的 toolCall 决策行、不存工具响应行，回放必须去掉 toolCalls（否则严格校验的服务端直接 400）；折叠条读的是库里原样的元数据，不受影响。
8. **外部依赖不可用一律"少一个工具"，不让对话陪葬**（T19）：MCP 是**可选的**——没配连接或 Bean 不存在的时代码本来就少挂一个工具（T9），而 T19 把"服务在、但连不上"这一形态也归到同一条路上：解析失败 ⇒ 空数组 + warn，对话继续。**为什么加冷却**：一次失败要付 `request-timeout`（默认 20s）才返回，不冷却的话服务宕机期间**每次对话**都要白等一次；60s 冷却配合 single-flight，把同一实例的“白等”压到每个故障窗口一个在途探测：其余并发会话立即按无搜图工具降级、不排队。60s 从探测失败被确认后开始计算；若从服务恢复时刻计算，还需叠加当时在途探测的剩余超时。**为什么不动 `request-timeout`**：同一把尺也在约束真实的 `searchImage` 调用（要走 Pexels 网络），为省 20s 而误伤正常路径不划算。**为什么不做健康探测**：它自带一把超时尺、还要在装配前多打一次网络往返，行为不如"失败即降级 + 冷却"可预测（这一点是 AI 判定，用户只拍板了"做 MCP 降级"）。
