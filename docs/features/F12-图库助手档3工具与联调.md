## 一句话

图库助手从"只会读"变成"能整理、能入库"：看得懂图片内容并给出打标建议（`visionTagger`，**仅管理员会话**）、按建议批量落库（`batchEditPictures`）、按 URL 批量入库（`batchUploadByUrl`）、还能联网搜图再入库（MCP `searchImage`）——两条业务场景已在真机链路上跑通。

## 怎么用

在助手对话框里直接说要做什么（中文即可）：

- **智能整理**："我的空间叫 X，里面有几张图还没有标签和分类，帮我看看内容并打上标签。"
  → 助手会：列空间 → 拉图片清单 → **逐张看图**给建议（复用词表已有标签）→ 批量落标 → **回读清单复核** → 汇总回答。
  → **注意**：这条链里的"看图"要用 `visionTagger`，它**只在管理员会话里可用**（T17）。普通用户可以让助手列空间/图片、批量改标签、按 URL 入库，但不能让助手看图给建议——公共图库的看图打标走管理端的「AI 打标」入口（见 `F14-AI打标.md`）。
- **选图入库**："帮我找 3 张 mountain 主题的图，放进空间 X。"
  → 助手会：搜图（MCP）→ 批量按 URL 入库 → 回读清单确认 → 逐条报成功/失败。

助手**不会**做的事：删除任何东西（一期不注册删除类工具）；用户没明确要求时不动数据。

### 核心流程

**智能整理**：`listSpaces` → `getTagCategory` → `listPictures` → **`visionTagger`（一次最多 8 张，仅管理员会话）** → `batchEditPictures`（按图分别提交）→ `listPictures` 复核 → 回答。
**选图入库**：`listSpaces` → **`searchImage`（MCP）** → `batchUploadByUrl`（一次最多 20 条，逐条上报）→ 回答。

### 关键设计与理由

1. **粗粒度工具（一步一批）**：图库的按 URL 上传是**单张**端点，"批量"在工具内部循环完成；打标也是工具内一次看完 N 张。这样 20 步预算够用，模型不必"一张一步"。
2. **看图不让模型搬 URL**：`visionTagger` 只收图片 id，自己经 `GET /picture/get/vo?id=` 取地址再送多模态模型——复制长 URL 是模型最易出错的环节，且图库那个端点会按图片归属再做一次空间权限校验。
3. **建议与落库分离**：`visionTagger` 只给建议（返回里明说"尚未写入图库"），落库由 `batchEditPictures` 承担且要用户确认（或用户已明确要求）。
4. **写类工具"如实上报"**：图库批编只回一个布尔且按"空间 + id"过滤（不属于该空间的 id **静默跳过**），所以工具返回 `requestedCount`（提交了几张）而**不是**"改成了几张"，并带一句说明——联调里模型据此**自己回读清单复核**，说明这条口径真的被用上了。
5. **没配视觉模型、或调用者不是管理员，就不挂 `visionTagger`**（后者是 T17）：宁可让模型看见"手上没有这个工具"，也不给它一个每次都报错的工具 / 一个它没资格用的工具。**为什么按角色裁**：打标已是管理员能力（公共图库那条走管理端 `F14` 的入口），普通用户在助手侧留着只读 `visionTagger` 与"只有管理员能打标"不一致（用户 2026-09-15 拍板摘掉）。**怎么传**：代理把自己登录用户的角色放进 `X-User-Role` 头（与 satoken / SESSION 同信道），引擎 `HuoshanAssistantSession.isAdmin` **fail-closed** 判定（缺失/未知一律当普通用户）；**这不是授权**——引擎校验不了该头，而工具只读且以调用者自己的凭据打图库 API，能力边界仍由图库服务端判。
6. **思考模式必须关（DeepSeek）**：带 `tools` 的请求每轮都必须回传 `reasoning_content`，而 Spring AI 的 OpenAI 客户端不认这个私有字段 ⇒ 开着必 400；通过新加的 `extra-body` 配置直通 `{"thinking":{"type":"disabled"}}`。
7. **回放剥掉工具痕迹**（T12 修复）：记忆只存 assistant 的 toolCall 决策行、不存工具响应行，回放必须去掉 toolCalls（否则严格校验的服务端直接 400）；折叠条读的是库里原样的元数据，不受影响。
8. **外部依赖不可用一律"少一个工具"，不让对话陪葬**（T19）：MCP 是**可选的**——没配连接或 Bean 不存在的时代码本来就少挂一个工具（T9），而 T19 把"服务在、但连不上"这一形态也归到同一条路上：解析失败 ⇒ 空数组 + warn，对话继续。**为什么加冷却**：一次失败要付 `request-timeout`（默认 20s）才返回，不冷却的话服务宕机期间**每次对话**都要白等一次；60s 冷却配合 single-flight，把同一实例的“白等”压到每个故障窗口一个在途探测：其余并发会话立即按无搜图工具降级、不排队。60s 从探测失败被确认后开始计算；若从服务恢复时刻计算，还需叠加当时在途探测的剩余超时。**为什么不动 `request-timeout`**：同一把尺也在约束真实的 `searchImage` 调用（要走 Pexels 网络），为省 20s 而误伤正常路径不划算。**为什么不做健康探测**：它自带一把超时尺、还要在装配前多打一次网络往返，行为不如"失败即降级 + 冷却"可预测（这一点是 AI 判定，用户只拍板了"做 MCP 降级"）。

- **工具 schema 契约**：`pictureIdList` / `fileUrls` 必须发布为 JSON `array`（模型靠 schema 才知道传数组）——有断言。

## 已知限制

1. **会话记忆重复写入已于 2026-09-15 修复**：根因是 Spring AI 的 `MessageChatMemoryAdvisor` 每次调用都会把"请求里最后一条用户消息"再写一遍（我们的循环每轮重提整段 messageList，最后一条长期不变），实测同一条被写 3 次；现在记忆层按消息指纹（类型 + 文本 + 工具调用/响应 id）去重，真机重跑该会话 8 行各 1 份。**残留**：同一会话里用户问两遍**完全相同**的问题，第二遍不会进记忆（当轮模型仍看得到，跨轮次看不到）；另外每条 add 会全量扫一遍该会话的行，会话很长时属多余读（可优化）。
2. **MCP 搜图返回的是"逗号拼接的一整串"**，模型要自己拆成多条 URL。工具侧已剥包裹引号，但**不按逗号拆分**（URL 里的逗号合法，启发式拆分风险大于收益）：若模型把整串当一个 URL 传进来，会逐条失败而不是静默出错。
3. ~~**看图是逐张串行**（单次上限 8 张，每张数秒）~~ **2026-09-15 T18 收口**：改为**按波提交的有界并发 4**（波宽 = 并发度，波与波之间才检查登录态）+ **单张 45s 墙钟预算**（`future.get(45s)` 超时只降级该张、`cancel(true)` 收拾残局）+ 结果按输入顺序落位，与 backend `PictureAiTagManager` 的"层次一"同口径；引擎的 vision HTTP 超时仍是 120s，但已被单张预算罩住（预算先到）。**8 张从"最坏 8×120s"降到"最坏 2×45s"**，一步仍可能数十秒（MiMo 单张 10~15s、两波），折叠条该转圈还是转。**接口语义随之变化**：登录态失效的提前停止粒度由**逐张**变成**逐波**（并发下同波几张已经在飞），`note` 仍如实报"剩余 N 张未尝试"。旧文提到的并发先例补救说明保留于此：`ParallelSearchTool` 已于 2026-09-15 按 T13 顺带项删除（它是给本仓不存在的 DeepResearchAgent 写的死代码），要参考请从 git 历史取（`git show fdbcab7^:ai/agent/src/main/java/com/lcl/myaiagent/tools/ParallelSearchTool.java`，测试同名）。
4. **打标只建议、不自动落库**：用户没确认时助手应当先讲建议；若用户明确要求"打上去"，会直接落库（联调即此形态）。
5. **前端工具摘要认不出新载荷**：`assistantFormat.ts` 的 `summarizeToolResult` 覆盖的是档 1 三类只读载荷，新工具（看图/批编/入库）会退化成"已完成"（设计上 fail-soft，不报错）。要好看需在前端补摘要分支。
6. **批编的逐张结果不可知**：图库不回逐张结果，工具只能报"提交成功"；确认要靠再拉一次清单（模型在联调里自发做了）。
