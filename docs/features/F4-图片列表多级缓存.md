# F4 图片列表多级缓存（2026-09-28 补记，T34 已落地）

> 本文档按规则 9 补写：改动本功能前先有讲解。T34（失效按空间切分，2026-09-28）已落地，下文描述的是**改动后**的实现；改动前的形状（全局单版本号，任何一次写入作废所有列表缓存）在需要对照处单独说明。改动前的那一版讲解见 `git show c18ce17`。

## 是什么

图片列表接口的读缓存：本地 Caffeine（L1）+ Redis（L2）两级，目标是让"翻页看图库"这个最高频的读请求不必每次都查库、也不必每次都为同一个查询重复组装 VO。

写入侧不追求强一致：靠"**按 scope 分开的 Redis 版本号** + 本地清空 + 跨实例广播"做到**最终一致且有上界**——正常情况下失效是秒级的，最坏情况下由本地 TTL（5~10 分钟随机）兜底。

## 怎么用

- **入口**：`POST /api/picture/list/page/vo/cache`（`PictureController.java:229`），请求体是 `PictureQueryRequest`，返回 `Page<PictureVO>`。
- **前端消费方只有两处**：首页 `frontend/src/pages/HomePage.vue:103`（公共图库）与空间详情页 `frontend/src/pages/SpaceDetailPage.vue:203`（空间图库），接口定义在 `frontend/src/api/pictureController.ts:110-115`。
- **AI 助手不走这条路径**：引擎的 `ListPicturesTool` 打的是非缓存的 `/picture/list/page/vo`，与本功能无交互。
- **权限**（`PictureServiceImpl.java:779-788`）：`spaceId` 为空时强制 `reviewStatus=PASS` + `nullSpaceId=true`（普通用户只看已过审的公共图，且不会把空间图片混进公共列表）；传了 `spaceId` 则按空间显式判定查看权限（`checkSpaceViewPermission:942`，目标绑定，不依赖请求嗅探）。
- **缓存值不含"谁在看"**：`getPictureVOPage:674-697` 只填图片作者的 `UserVO`，`permissionList` 保持默认空列表，所以同一条缓存可以给所有有权限的用户复用。

## 怎么实现（T34 改动后）

### 失效的 scope

- 本功能按**空间**切分失效粒度，scope 只有两种取值：空间图库是该空间 id，公共图库是 `CACHE_SCOPE_PUBLIC`（字面量 `"public"`，`PictureServiceImpl.java:137`）。用字符串而不是数字，是为了让 `public` 不可能与"空间 id 恰好是 0"撞成同一个 scope（`PictureListCacheScopeTest` 钉住这一点）。
- 推导只有一处实现：`cacheScopeOf(spaceId)`（`:972-974`）。读路径从查询请求的 `spaceId` 推导、写路径从被写图片的 `spaceId` 推导，两侧共用，避免"读写口径不一致导致该失效的没失效"。
- 之所以能按空间切：**查询的 scope 两两不相交**（`spaceId` 为空时只查公共图库，不存在跨空间的查询结果），且**图片的空间归属创建后不可变**（编辑接口的 DTO 没有 `spaceId` 字段；替换图片时空间不一致直接拒，见 `:253-264` 的"空间 id 不一致"）——所以一次写入最多只影响一个 scope。

### 两级缓存

- **缓存键**：`hashKey = MD5(JSON(buildCacheKey(request)))`（`:791-793`）。`buildCacheKey`（`:914-933`）把影响结果的字段全部纳入：`spaceId`、`nullSpaceId`、`reviewStatus`、`category`、`tags`、`userId`、`name`、`introduction`、`searchText`、`picFormat`、`sortField`、`sortOrder`、`current`、`pageSize`。排序字段与分页参数必须参与，否则会串页。
- **L1**：单例 bean `pictureListLocalCache`（`CacheConfig.java:21-49`），`initialCapacity=1024`、`maximumSize=10000`、开启 `recordStats()`（命中率指标依赖）、**每条 5~10 分钟随机 TTL**（打散过期时间降低雪崩）；`expireAfterRead` 返回原 TTL，即读命中不延长寿命。本地 key 就是裸 `hashKey`（`:795`），**不按空间分片**。
- **L2**：`huoshantuku:listPictureVOByPage:{version}:{hashKey}`（`:805`），`version` 来自该 scope 的版本号 key（`cacheVersionKey`，`:981-983`）；TTL 正常结果 `300 + random(0,300)` 秒、空结果 60 秒（`:841-848`）。
- **读路径顺序**（`listPictureVOByPageByCache:774-880`）：L1 → 按请求的 scope 取版本号（`:804`）→ L2 → 分布式锁 → 双重检查 → 查库回填两层。L1 命中直接返回，**不会去读版本号**。
- **防击穿**：抢锁 `huoshantuku:lock:{hashKey}`（`:816-820`），value 用随机 UUID 并在释放时用 Lua 校验归属（`UNLOCK_SCRIPT`，`:149-151`），避免误删他人锁。拿不到锁的请求短暂等待后有限重试 5 次 × 50ms（`:865-877`），仍拿不到就报"系统繁忙，请稍后重试"（`:879`）——而不是返回空 `Page` 让前端误以为"没有数据"。
- **重建耗时监控**：`app.cache.rebuild-lock-ttl-seconds`（默认 30，`:178-185`）必须大于"查库 + 组装 VO + 序列化"的耗时上界；超过 `app.cache.rebuild-warn-ms`（默认 5000）打 WARN（`:851-859`），作为"重建变慢、锁 TTL 余量可能不够"的早期信号。刻意不做看门狗续期、不引 Redisson。

### 失效

- 版本号 key **按 scope 分开**：`huoshantuku:listPictureVOByPage:version:{scope}`（前缀 `:131`，拼接 `cacheVersionKey:981-983`）。`INCR` 该 scope 的版本号，让该 scope 所有旧版本 key **立刻逻辑失效**，旧 key 靠 TTL 自然过期——刻意不用 `KEYS` 通配符全库扫描（会阻塞 Redis）。
- `doClearPictureListCache(scopes)`（`:1020-1027`）：逐个 scope `INCR`，再清本实例本地缓存并广播。
- **本地层仍是全清**（`pictureListCacheInvalidator.invalidateAll()`）：本地缓存不按空间分片，且这是既定取舍——所以**广播报文也不必带 scope**，对端收到就清空自己整个 L1，不需要知道是哪个空间。
- **失效时机**：调用方在事务里时延到 `afterCommit`（`clearPictureListCache:988-1010`），避免"清缓存 → 并发请求回源读到未提交旧数据 → 旧数据写回缓存"的竞态。
- **触发失效的 8 处写路径**（都在 `PictureServiceImpl`），各自只失效自己影响的 scope：

| 写路径 | 位置 | scope |
|---|---|---|
| `uploadPicture` | `:356` | 这张图的 `finalSpaceId`（为空即 public） |
| `uploadPictureByBatch` | `:543` | public（批量抓取一律进公共图库） |
| `doPictureReview` | `:756` | 这张图所在空间 |
| `deletePicture` | `:1070` | 这张图所在空间 |
| `updatePicture` | `:1103` | `oldPicture` 所在空间（**不能**用新实体，见下） |
| `editPicture` | `:1147` | `oldPicture` 所在空间（同上） |
| `editPictureByBatch` | `:1398` | 请求指定的那一个空间（选图时已按 spaceId 过滤） |
| `applyAiTags` | `:1620` | 载入图片的**去重 scope 集合**（一次打标可能跨空间、也可能含公共图库） |

  其中 `updatePicture` / `editPicture` 的 scope **必须取旧记录**：新实体是按 DTO 拷贝的，而 DTO 没有 `spaceId` 字段，其 `spaceId` 恒为 null，拿它推导会把空间图库错算成公共图库，导致该空间的列表不刷新。
- **跨实例失效**：`PictureListCacheInvalidator` 先清本实例 L1（`invalidateAll()` 是本地同步调用），再向频道 `huoshantuku:channel:pictureList:invalidate`（`RedisPubSubConfig.java:23`）发广播；订阅方收到后同样清空自己的 L1，并跳过自己发出的报文（`instanceId = pid@host#随机后缀`，`:41-42`）。订阅容器由 `RedisPubSubConfig.java:30-40` 显式声明（Spring Boot 2.7 的自动配置不建监听容器）。广播报文只带"谁发的 / 哪条链路 / 时间戳"，不承载缓存内容与 scope——失效语义是幂等的全量清空。
- **埋点**：`PictureListCacheMetrics` 分别暴露 L1 与 L2 的 `cache.gets`（hit/miss，`layer` 标签区分 `caffeine` / `redis`）与 `cache.size`。两级都未命中才会查库，所以"回源占比"看 Redis 层 miss 比例。

## 怎么验证

- **纯单元（进 CI，无需 MySQL/Redis）**：
  - `PictureListCacheScopeTest`（4 用例，T34 新增）：`spaceId` 为空映射到 `public`、不同空间映射到不同 scope、`public` 不与任何数字空间 id 相撞、版本号 key 逐 scope 不同且保留既有前缀。
- **单测/集成测试**（需 MySQL/Redis，类名以 `IntegrationTest` 结尾，不进 CI）：
  - `PictureListCacheScopeIsolationIntegrationTest`（3 用例，T34 新增，**本功能的验收核心**）：写一个空间不得作废公共图库的列表缓存（用 `@SpyBean` 数 `loadFromDb` 调用次数，而不是断言 key 字面形状）；反向护栏——写公共图库自己的图必须失效公共图库的缓存（防"干脆什么都不失效"）；写 A 空间只自增 A 的版本号，`public` 与无关空间 B 纹丝不动。
  - `PictureListCacheInvalidationIntegrationTest`：广播能到达对端容器并清空对端本地缓存（自写 `awaitUntil` 轮询等待异步投递）；报文解析失败时按全量失效处理。
  - `CacheRebuildLockIntegrationTest`：并发请求下只有一个线程查库（防击穿锁生效）。
  - `PictureBatchUploadIntegrationTest:120`：批量上传 N 张只触发**一次** `invalidateAll()`（T28 的回归契约；逐张清缓存会让批量期间列表缓存被反复打穿）。
- **本地跑**：`cd backend && mvn -B test "-Dtest=PictureListCacheScopeTest,PictureListCacheScopeIsolationIntegrationTest,PictureListCacheInvalidationIntegrationTest,CacheRebuildLockIntegrationTest,PictureBatchUploadIntegrationTest" -DfailIfNoTests=false`。
- **指标**：Prometheus 查询形如 `rate(cache_gets_total{layer="caffeine",result="hit"}) / rate(cache_gets_total{layer="caffeine"})`；两级命中率对照可判断收益来自哪一层。
- **压测资产**：`backend/jmeter/`（含 `list-page-Cache-*.json` 统计），口径以其 README 为准。
- T34 的红绿输出与命令见 `docs/plans/records/T34-缓存失效按空间切.md`。

## 已知限制

- **多实例本地缓存脏读（spec 明确不做，不回退）**：本地缓存的 key 不带版本号，命中时不会去读 Redis，正确性完全依赖失效广播到达。Pub/Sub 是**至多一次**投递——实例重启、连接抖动、订阅尚未重建期间发布的报文**永久丢失**（无持久化、无 ack），该实例就会继续服务自己那份旧数据，直到条目 TTL（5~10 分钟）到期。口径是"最终一致且有上界"，不是强一致；spec 的"不做的事"里已明确排除，不翻案。
- **按空间切分把"过失效"换成了"精确失效"**：T34 之前任何写入都作废所有列表缓存，安全但代价高；现在每个写路径只失效自己那个 scope，**漏 bump 的 scope 会陈旧到 TTL**（5~10 分钟）——与"广播丢失"同一量级的失败模式，不会无界陈旧。风险点是 scope 分散在 8 处调用点，靠上面那张归属表 + `PictureListCacheScopeIsolationIntegrationTest` 与评审来守，没有编译期保证。
- **本地层仍全清，所以 L1 命中率没有提升**：这是既定取舍。收益只体现在"无关空间的请求不必回源查库、也不必去抢重建锁"（L2 仍命中），不是 L1 层面的提速。
- **用户资料变更不移除列表缓存**：缓存项里带图片作者的 `UserVO`，但改昵称/头像走的 `UserController.updateUser` / `editUser`（`UserController.java:188-234`）没有任何失效调用，所以作者改名后列表里的作者信息最多陈旧一个 TTL（5~10 分钟），或等下一次图片写入顺带刷掉。
- **回源旧快照被无条件回写**：四处 `localCache.put`（`:810`、`:829`、`:838`，以及抢锁失败重试路径的 `:874`）不带版本号、也没有守卫。若读线程读到了写线程提交**之前**的快照，而写线程在其后完成提交并清了缓存，读线程仍会把这份旧值写回 L1，之后一直服务到 TTL 到期。L2 不受影响——它写的是带版本号的 key，旧版本 key 已不可达。单实例即可复现（写路径不取重建锁，锁挡不住它），但窗口很窄。
- **广播的收敛上界只是 TTL**：除广播丢失外，还有"广播已处理但本地条目已被并发回源重新写回"这类竞态（见上一条），因此"秒级失效"是常态而非保证，兜底始终是 5~10 分钟 TTL。
- **端到端一致性没有 CI 保护**：所有相关测试类都以 `IntegrationTest` 结尾，被 CI 的 `-Dtest='!*IntegrationTest,...'` 排除，端到端行为只能本地或有 MySQL/Redis 的环境跑；CI 只守住 `PictureListCacheScopeTest` 这类纯单测不变量。
- **版本号 key 不能设 TTL**：计数器一旦过期归零，上一世代的旧 key 会重新变得可达，等于复活陈旧数据。当前 `INCR` 未设过期，是刻意为之。
- **旧全局版本号 key 会留下**：T34 之前的数据 key 是按全局版本号写的，改动后不再有人读它们，靠 TTL 自然消亡；升级时无需任何迁移或缓存清理动作，但 Redis 里会短暂同时存在两种版本号 key（`huoshantuku:listPictureVOByPage:version` 与 `...:version:{scope}`）。
- **缓存重建锁是自研单机锁**：不做看门狗续期、不引 Redisson。锁 TTL 一旦短于重建耗时，后续请求会再抢到锁并重复查库（双重检查只能减轻、不能消除）。当前靠"配置值留一个数量级余量 + 超阈值 WARN"来守，不是协议级保证。
