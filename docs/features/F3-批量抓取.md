# F3 批量抓取（Bing 图源，2026-09-18 补记）

> 本文档按规则 9 补写：改动本功能前先有讲解。T28（落库批量化）已落地，第三节描述的是**改动后**的实现；改动前的形状（逐张入库 + 逐张清缓存）在下面按需对照说明。

## 是什么

管理员输入一个搜索词，后端去 Bing 图片搜索结果里取原图地址、逐张下载并转存到自己的 COS，最后把成功的那些登记进图库公共图库。解决的是"给图库批量铺内容"的冷启动问题——人工一张张上传太慢。

图源是**外部站点**，不是自己的资产，所以整条链路按"尽力而为"设计：单张失败只跳过、不中断整批。

## 怎么用

- **入口**：前端 `/add_picture/batch`（`frontend/src/pages/AddPictureBatchPage.vue`，路由见 `frontend/src/router/index.ts`）；接口 `POST /api/picture/upload/batch`，`@AuthCheck(mustRole = ADMIN)` —— **仅管理员可用**。
- **请求体**（`PictureUploadByBatchRequest`）：`searchText`（搜索词，必填）、`count`（默认 10，**上限 30**，超出直接 400）、`offset`（默认 0）、`namePrefix`（不传则用 `searchText`）。
- **返回**：`BaseResponse<Integer>` = **成功入库的图片数量**；失败明细不在响应里，只进服务端日志。
- **前端行为**：接口是同步阻塞的，全局 10s 超时不够，该页单独放宽到 300s；请求超时被中断时页面提示"任务仍在后台执行，请勿重复提交"（后端不会因前端断开而停止）。结果卡片按"响应 → 展示状态"的纯函数（`frontend/src/utils/batchCrawlResult.ts`）渲染四种状态：有新增 = 成功（报数量）、**成功但 0 张 = 中性提示"没有新增图片：结果可能都已导入过，或该搜索词没有可用图片"**（T30 修正：此前 `data=0` 被当成失败，显示成"任务执行失败 / ok"）、超时被中断 = 后台执行中、业务码非 0 = 失败（描述用后端给的原因）。
- **命名**：第 i 张（1 起）命名为 `namePrefix + i`，序号按**解析出的原始位置**给，不因跳过而重排。管理员上传自动过审（`fillReviewParams`）。

## 怎么实现（T28 改动后）

- **抓页面**：`PictureServiceImpl.fetchBingSearchPage`（T28 从 `uploadPictureByBatch` 内联代码抽出）用 Jsoup 同步 GET `https://cn.bing.com/images/async?q=<搜索词>&first=<offset+10>&mmasync=1`，出站请求带 `traceId` 头便于与本地日志串链路；取页失败抛"获取页面失败"。抽成 `protected` 是为了让集成测试能 `@SpyBean` 替换掉外网请求（与 `loadFromDb` 同一做法）。
- **解析**：`BingImageParser` 按配置 `app.bing-image.*`（容器/条目选择器、元数据属性、URL 字段，见 `backend/src/main/resources/application.yaml`）解析原图地址，顺手去掉 URL 上的查询参数（同一张图的尺寸/裁剪参数会产生多个 URL）；容器缺失即抛错（判定改版），条目为空只告警返回空。
- **并行前过滤**：`filterDuplicateAndMissingUrls` 先按源地址做批内去重（保留首次出现的序号，命名前缀不因跳过而重排），再用一次 `IN` 查询拦掉**公共图库里已导入过**的源地址（判重列与口径见下条）——改动前是每张一次 `getByUrl`。
- **判重（T29）**：来源地址写进 `picture.sourceUrl`（URL 导入/批量抓取写入，文件上传为 null），判重是**"源地址 + 目标空间"**：同一空间内只导一次，跨空间、公共图库与空间之间互不影响，逻辑删除后可重新导入。替换图片时排除自身；用文件替换后会把旧源地址显式清空（MyBatis-Plus 的 `updateById` 不写 null 字段）。改动前的 `getByUrl` 拿源地址去比对 COS 地址（不同名空间）**永远命中不了**，已删除。
- **来源地址长度前置校验（T31）**：`sourceUrl` 是 `varchar(1024)`，超长 URL 在严格模式下 INSERT 会报 `Data too long`；因为入库是整批原子的，批量里只要一张超长就会把整批 30 张一起打掉。所以 `preparePicture` 入口（单张与批量共用、**发起下载之前**）按列宽 fail fast 抛参数错误"来源地址过长"——批量下这只是一次"单张失败"，其余照常入库。
- **并行（只做网络）**：`ThreadPoolConfig.pictureUploadExecutor`（核心 = CPU 核数、最大 = 2×、队列 100、`CallerRunsPolicy`），每张图一个 `CompletableFuture`；任务里只调 `preparePicture`（下载 + COS 转存 + 构造**未落库**记录），不写库、不清缓存。`preparePicture` 与单张上传共用（`uploadPicture` = `preparePicture` + 落库）。
- **`allOf` 之后批量落库**：`persistPicturesInBatch` 在**一个事务**里 `saveBatch`（本地 JDBC URL 带 `rewriteBatchedStatements=true`，驱动把 30 行合并成一条多值 INSERT），随后**只清一次**列表缓存。改动前是 30 个事务 + 30 次缓存失效。
- **失败处理**：单张下载/COS 失败仍被捕获成 `UploadResult`（成功/失败 + 错误信息）并只跳过该张；但**入库阶段整批原子**——任一行落库失败即整批回滚并抛错，同时把这一批已转存到 COS、已无记录引用的文件逐个补偿删除（`cleanupPictureFile` 按引用计数兜底）。

## 怎么验证

- **契约测试** `BingImageParserContractTest`：用固定样本 `backend/src/test/resources/bing/image-search-sample.html` 钉住 Bing 的 DOM 契约，改版在构建期就暴露（不用等线上抓 0 张）。
- **批量化集成测试** `PictureBatchUploadIntegrationTest`（6 用例，`@SpyBean` 替掉抓页与逐张下载，真 MySQL/Redis）：N 张只落一次库、只清一次缓存；批内重复源地址只存一份；单张下载失败不拖垮整批；入库失败整批回滚 + 三张已转存文件全部补偿删除；`Com_insert` 增量 = 1 证明 `rewriteBatchedStatements` 真的合并了 INSERT；同一搜索词重跑第二次返回 0（跨批次判重）。
- **判重集成测试** `PictureSourceUrlDedupeIntegrationTest`（7 用例）：同空间第二次被拒且第一次确实写下了 `sourceUrl`；跨空间与公共图库互不影响；逻辑删除后可重导；用同一源地址替换自己不被自己挡住；用文件替换后旧源地址被清空、同地址可重新导入；**超长源地址在下载之前就被拒**（断言 `CosManager` 零调用）。测试替身只换掉 HEAD 预检与下载两处网络行为，判重、COS 模板、事务、MySQL 全走真实链路。
- **单张路径回归**：`PictureReplaceQuotaIntegrationTest` 等存量用例跑在重构后的 `uploadPicture` 上（证明抽 `preparePicture` 没改行为）。
- **前端展示断言（T30）**：`cd frontend && npm run check:batch-crawl-result` —— 前端没有测试框架，沿用 `check:assistant-format` 的做法，用 esbuild 转译**真的** `batchCrawlResult.ts` 后断言 9 组用例（0 张不是失败、0 张不泄露后端原文 "ok"、1/30 张报数、成功但没带数量降级为 empty、业务码非 0 保留原因、错误缺 message 有兜底）。
- **手工冒烟**：以管理员登录 → `/add_picture/batch` → 填搜索词与数量 → 结果卡片显示"成功抓取并上传 N 张图片"，随后图片管理页可见。

## 已知限制

- **单次 ≤30、无真分页**：`offset` 只影响 Bing 请求的 `first` 参数，翻页语义由 Bing 决定，同一 `offset` 重复抓取会拿到高度重叠的结果（源地址相同的会被批内去重拦掉，表现为"成功数变少"）。
- **只能进公共图库**：`PictureUploadByBatchRequest` 没有 `spaceId`，批量路径永远按 `public/{userId}` 落盘、`spaceId=null`，不占空间额度也不校验空间权限。
- **失败明细不入库**：接口只回成功数量，哪几张失败、为什么失败只存在于日志里；前端也无法重试单张。
- **入库阶段整批原子（T28 的代价，已确认口径）**：入库失败时这一批 30 张的 COS 转存全部作废并删除，接口报错而不是回一个偏小的成功数。下载/COS 阶段的逐张隔离不受影响。
- **判重按"源地址"而不是"内容"（T29 口径）**：不同 URL 指向同一张图（不同 CDN / 不同站点）仍会各存一份；真正的内容级去重要靠内容哈希，本任务未做。
- **T29 之前导入的记录没有源地址**：`sourceUrl` 为 NULL 的历史行不参与判重，所以那些图**还会被重复导入一次**（这一次之后才会被记下并拦住）；源地址已丢失，无法回填。
- **`sourceUrl` 为空的记录**：文件上传（`MultipartFile`）不写来源地址，也就不参与判重——用文件重复上传同一张图仍会各存一份（要按内容判重需另做内容哈希）。
- **部署顺序**：`sourceUrl` 列是 T29 新增的，**prod 必须先执行 `backend/sql/add_picture_source_url.sql` 再部署新 jar**（后端没有 Flyway）；漏执行的报错面是 URL 导入/批量抓取（`Unknown column`），文件上传不受影响。步骤见 `deploy/prod-checklist.md` §2.1。
- **`rewriteBatchedStatements=true` 只加在本地与模板**：`application.yaml`（本地/默认 URL）已带，`application-prod.yaml` 未动，**prod 要等下次发布才生效**；生效前生产环境仍是"一个事务 + N 条 INSERT"，功能不受影响。
- **判重是"先查后插"，并发下仍可能各插一条**：判重靠查询而不是唯一约束（刻意不建唯一索引——逻辑删除的行会永久占住唯一索引），所以两个并发请求对同一源地址仍可能同时通过检查并各插一条。批量抓取是管理员点按钮、天然串行，风险主要在单张 `/picture/upload/url` 被并发调用时；真按内容/约束级去重需要唯一索引 + 逻辑删除的替代方案（物理删除或含 isDelete 的唯一键），属另开任务。
- **"0 张"无法区分原因**：结果卡片只能如实说"可能都已导入过，或该搜索词没有可用图片"——接口只回数量，不区分"被去重拦掉"与"抓取/下载失败"（失败明细只在日志里）。
- **`count` 只校验上界**：`count = 0` 或负数会被 `BingImageParser.parseImageUrls` 的 `count <= 0` 短路成空列表，接口回 0，前端按上面的文案显示"没有新增图片…"，实际是"根本没抓"（前端 `a-input-number` 的 `:min="1"` 是唯一兜底）。要收口就在同一个 `ThrowUtils` 后面补下界校验。
- **批量补偿不区分"回滚是否成功"**：入库失败后的补偿删除建立在"事务已回滚"这一假定上；极端情况下（连接在 ROLLBACK 之前断掉、回滚实际未生效）可能删掉仍被记录引用的 COS 对象，留下 404 图片。已有按 URL 引用计数的兜底（`cleanupPictureFile` 先数引用再删），概率极低；真要收口需读事务状态后再决定是否补偿。
- **回退旧 jar 会静默丢来源地址**：若 prod 执行完 DDL 又回退到旧 jar，旧实体字段列表里没有 `sourceUrl`，新上传/替换的记录不再写该列（列可空、无默认，旧代码不报错），这些行退化成"历史行"——不参与判重、会被重复导入一次，且地址已丢无法回填。读接口与文件上传不受影响（`map-underscore-to-camel-case=false`，多余列无害），回退本身安全。
- **前端断言只覆盖纯函数、不覆盖 axios 装配**：`npm run check:batch-crawl-result` 转译真实 `.ts` 后直接调用（9 组场景 15 条断言），而浏览器里真正传进去的是响应拦截器原样返回的 axios response 的 `.data`（`frontend/src/request.ts`）。"0 张文案"的正确性靠"纯函数 + 拦截器契约"两段保证，拦截器那一半由全仓 36 处同样的 `res.data.code` 用法与类型检查间接保证，**没有专门断言**。
- **抓取外站是 SSRF 面**："抓取类工具的 SSRF 面"按 `docs/decisions.md` 记为**缓解未修**（D1 回环收口后本机进程仍可利用）。
- **无重试、无自适应限流**：单张失败即放弃该张；并发度固定为线程池配置，不感知图源限流。
