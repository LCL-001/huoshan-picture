# F3 批量抓取（Bing 图源，2026-09-18 补记）

> 本文档按规则 9 补写：改动本功能前先有讲解。本次补记时点是 T28 开工前，第三节描述的是**改动前**的实现；T28 落地后该节同步为"并行只做下载 + COS，`allOf` 后一次批量入库"。

## 是什么

管理员输入一个搜索词，后端去 Bing 图片搜索结果里取原图地址、逐张下载并转存到自己的 COS，最后把成功的那些登记进图库公共图库。解决的是"给图库批量铺内容"的冷启动问题——人工一张张上传太慢。

图源是**外部站点**，不是自己的资产，所以整条链路按"尽力而为"设计：单张失败只跳过、不中断整批。

## 怎么用

- **入口**：前端 `/add_picture/batch`（`frontend/src/pages/AddPictureBatchPage.vue`，路由见 `frontend/src/router/index.ts`）；接口 `POST /api/picture/upload/batch`，`@AuthCheck(mustRole = ADMIN)` —— **仅管理员可用**。
- **请求体**（`PictureUploadByBatchRequest`）：`searchText`（搜索词，必填）、`count`（默认 10，**上限 30**，超出直接 400）、`offset`（默认 0）、`namePrefix`（不传则用 `searchText`）。
- **返回**：`BaseResponse<Integer>` = **成功入库的图片数量**；失败明细不在响应里，只进服务端日志。
- **前端行为**：接口是同步阻塞的，全局 10s 超时不够，该页单独放宽到 300s；请求超时被中断时页面提示"任务仍在后台执行，请勿重复提交"（后端不会因前端断开而停止）。
- **命名**：第 i 张（1 起）命名为 `namePrefix + i`，序号按**解析出的原始位置**给，不因跳过而重排。管理员上传自动过审（`fillReviewParams`）。

## 怎么实现（T28 改动前）

- **抓页面**：`PictureServiceImpl.uploadPictureByBatch` 用 Jsoup 同步 GET `https://cn.bing.com/images/async?q=<搜索词>&first=<offset+10>&mmasync=1`，出站请求带 `traceId` 头便于与本地日志串链路；取页失败抛"获取页面失败"。
- **解析**：`BingImageParser` 按配置 `app.bing-image.*`（容器/条目选择器、元数据属性、URL 字段，见 `backend/src/main/resources/application.yaml`）解析原图地址，顺手去掉 URL 上的查询参数（同一张图的尺寸/裁剪参数会产生多个 URL）；容器缺失即抛错（判定改版），条目为空只告警返回空。
- **并行**：`ThreadPoolConfig.pictureUploadExecutor`（核心 = CPU 核数、最大 = 2×、队列 100、`CallerRunsPolicy`），每张图一个 `CompletableFuture`，`allOf(...).join()` 等齐。
- **每张图**：并行任务里调的是**完整的** `uploadPicture(...)` —— URL 去重查询 → 下载 + COS 转存 → **独立事务** INSERT → **逐张**清图片列表缓存。因此 30 张 = 30 次去重查询 + 30 个事务 + 30 次缓存失效广播。
- **失败处理**：单张异常被捕获成 `UploadResult`（成功/失败 + 错误信息），不影响其它张；最后统计成功数返回。

## 怎么验证

- **契约测试** `BingImageParserContractTest`：用固定样本 `backend/src/test/resources/bing/image-search-sample.html` 钉住 Bing 的 DOM 契约，改版在构建期就暴露（不用等线上抓 0 张）。
- **手工冒烟**：以管理员登录 → `/add_picture/batch` → 填搜索词与数量 → 结果卡片显示"成功抓取并上传 N 张图片"，随后图片管理页可见。
- **T28 起**：新增 `PictureBatchUploadIntegrationTest`（mock `CosManager`、真 MySQL/Redis）覆盖落库次数、清缓存次数、批内重复 URL 与入库失败补偿。

## 已知限制

- **单次 ≤30、无真分页**：`offset` 只影响 Bing 请求的 `first` 参数，翻页语义由 Bing 决定，同一 `offset` 重复抓取会拿到高度重叠的结果（重叠部分被 URL 去重拦掉，表现为"成功数变少"）。
- **只能进公共图库**：`PictureUploadByBatchRequest` 没有 `spaceId`，批量路径永远按 `public/{userId}` 落盘、`spaceId=null`，不占空间额度也不校验空间权限。
- **失败明细不入库**：接口只回成功数量，哪几张失败、为什么失败只存在于日志里；前端也无法重试单张。
- **"已存在就不重复入库"的检查对抓取路径实际不生效**：`uploadPicture` 对 URL 输入会拿**源地址**去查 `picture.url`，而库里存的是 **COS 地址**（`host + 随机 key`），两者不同名空间，所以逐张 `getByUrl` 永远查不到。（该检查对"把自家 COS 地址当 `fileUrl` 传进 `/picture/upload/url`"是有意义的；对 Bing 源地址没有保护作用。）
- **同一批里重复的源地址会重复入库**：Bing 结果去参后常有重复的源地址，改动前会被下载两次、生成两个不同 key 的 COS 对象、入库两条内容重复的记录。（T28 处理：并行前按源地址做批内去重。）
- **逐张事务 + 逐张清缓存**：部分成功是常态（图源 404/超时/重复很常见）；30 张会触发 30 次缓存版本号自增与 30 次失效广播，批量执行期间列表缓存被反复打穿。（T28 处理：入库阶段批量化、缓存只清一次，代价是入库阶段整批原子。）
- **抓取外站是 SSRF 面**："抓取类工具的 SSRF 面"按 `docs/decisions.md` 记为**缓解未修**（D1 回环收口后本机进程仍可利用）。
- **无重试、无自适应限流**：单张失败即放弃该张；并发度固定为线程池配置，不感知图源限流。
