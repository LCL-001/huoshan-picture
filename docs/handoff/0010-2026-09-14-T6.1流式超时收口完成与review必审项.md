## review 必审项（交付方列出，不代表结论）

1. **空闲超时接在 `ExchangeFilterFunction` 上是否正确**：`ClientResponse.mutate().body(...)` 重建响应后，`statusCode` / `headers` / `cookies` / `request()` 是否都保住（Spring AI 的 4xx/5xx 错误处理依赖 `request()` 与状态码）；原响应体未被订阅是否有 DataBuffer 泄漏；客户端取消（SSE 断开）时 JDK 请求是否随之取消。
2. **这条 filter 的作用域是否过宽**：它对**该 WebClient 的每个响应体**生效（含非流式响应，若将来 Spring AI 用同一 WebClient 做别的事）。今天 `OpenAiApi` 的 `webClient` 只被 `chatCompletionStream` 用——请自行反查确认，而不是采信本句。
3. **与重试模板的交互**：空闲超时抛的是 `java.util.concurrent.TimeoutException`，是否真的不被 `RetryUtils`（仅 retryOn `TransientAiException`）重试；`chatCompletionStream` 内部是否有 `retryWhen` 会在超时后**静默重发起流**（那会表现为重复输出而非失败）。

## 一、必审 10 条逐条裁定

1. **空闲超时接在 `ExchangeFilterFunction` 上是否正确 —— 成立**（除"取消传递"一条，见 R1）
   - 响应元信息保住（源码）：`ClientResponse.mutate()` = `new DefaultClientResponseBuilder(this, /*mutate*/true)`（spring-webflux 6.2.17 `ClientResponse.java:218`）；该拷贝构造（`DefaultClientResponseBuilder.java:104-118`）复制 `strategies`、`statusCode`、`body=other.bodyToFlux(DataBuffer.class)`、`originalResponse`，并 `this.request = defaultClientResponse.request()`；headers/cookies 由 `getHeaders()/getCookies()`（`:147-175`）懒回退到原响应。**运行时旁证**：本会话两条探针的失败消息均为 `WebClientResponseException: 200 OK from POST http://127.0.0.1:<port>/a-silent/v1/chat/completions ...` —— 真实 URI 出现在异常文案里，说明 `request()` 确实穿过了 mutate。
   - 无 DataBuffer 泄漏：`body(Function)` 分支不调 `releaseBody()`（`:178-181`），原响应体只被包装、未二次订阅；`JdkClientHttpResponse.adaptBody`（`.doOnDiscard(DataBufferUtils::release)`）与 `DefaultClientResponse.body()` 各有一层释放兜底；connector 用的是非池化 `DefaultDataBufferFactory.sharedInstance`（`JdkClientHttpConnector.java:51`，本任务未改）——不存在 netty 式池化泄漏那一类问题。（**此条为源码级论证，未做内存计量。**）
2. **filter 作用域是否过宽 —— 今天不过宽（字节码反查）**：`javap -p -c spring-ai-openai-1.1.2.jar` 的 `OpenAiApi` 全类只有一处读 `Field webClient`（在 `chatCompletionStream` 内），`chatCompletionEntity` / `embeddings` 走 `restClient`。`OpenAiApi$Builder.webClientBuilder` 字段存在、`build()` 传给构造器，构造器对我们的 builder 先 `clone()` 再 `baseUrl/defaultHeaders/build()`；`DefaultWebClientBuilder` 拷贝构造复制 `filters`（`:144`）与 `connector`（`:146`），`build()` 取 `this.connector != null ? this.connector : initConnector()`（`:313`）——接线有效且显式固定为 JDK connector。残余（P3）：该 filter 对**该 WebClient 的每个响应体**生效，将来若有别的调用挪进同一 webClient 会连带套上流空闲超时。
3. **与重试模板的交互 —— 成立，且比交付方说法更强**：`OpenAiChatModel` 全类只有一处 `RetryTemplate.execute`，在 `lambda$internalCall$3`（阻塞路径）；`stream` / `internalStream` 及其全部 lambda 无 `RetryTemplate`、无 `retryWhen`，`OpenAiApi.chatCompletionStream` 的链（`post→uri→headers→bodyValue→retrieve→bodyToFlux→takeUntil→filter→map×2→windowUntil→concatMapIterable→flatMap`）也无 retry —— **流式路径根本没有重试**，超时不会被静默重发。（重试模板口径另见 R2。）
4. **"逐请求计时不误伤工具调用轮次" —— 成立（机制层已实测；真实 tool-calling 长流仍缺一条用例）**：实测两次 `stream()` 相隔 2500ms（>`timeout`=1s）均 `DONE`（探针 2 CASE E）。机制上每轮工具调用是独立 HTTP 请求、各带自己的响应体计时器；顶层装饰器会误杀的正是"请求之间"的时间，而请求之间不在任何计时器内。建议 T7/T8 补一条真实 tool-calling 流用例（P3）。
5. **一把尺的合理性 —— 可接受，但语义应写清（P3）**：三条超时合成一个语义"请求生命周期内任何一段连续无信号不超过 `timeout`"。逐段核对：建连 = `HttpClient.connectTimeout`；`JdkClientHttpConnector.setReadTimeout` → `HttpRequest.Builder.timeout`（`JdkClientHttpRequest.java:72-73`），该窗口**在响应头到达时结束**（`MultiExchange.responseAsyncImpl` 的 `cancelTimer()` 挂在 `exch.responseAsync()` 完成之后，而 `Http1Exchange.getResponseAsync` = `response.readHeadersAsync`）；响应体信号间隔 = 新加的空闲超时。副作用：这把尺同时是**首 token 前的等待上限**（流式端点一般立刻回头，但长思考推理模型会被同一把尺卡住），默认 `PT2M` 下可接受。另：负数在两条路径上处理不对称（`restClientBuilder` 只挡 `null`，`webClientBuilder` 挡 0/负）→ P3。

## 二、新发现（不在交付方 10 条内）

**R1（P1，需决策）客户端取消不关闭上游请求。**
- 实测（探针 2 / 3，仓库外 `%TEMP%\t61rev\`）：① 空闲超时在 1690ms 触发（`WebClientResponseException <- TimeoutException`）后，桩在随后 6 次、每次间隔 400ms 的写同一个 socket **全部成功**（约 2.4s），直到桩自己关闭才结束 → 上游 TCP 连接一直开着；② `Disposable.dispose()`（= T8 里客户端断开 SSE 的情形）同样：取消后桩继续按 200ms 写满 100 段（20s）全部成功；③ **裸 JDK 控制组**：`HttpClient.sendAsync(..., BodyHandlers.ofPublisher())` + `subscription.cancel()` → 桩**立刻**看到 `CLIENT FIN (EOF)`；④ 差异只有 `.cache(0)`：`JdkFlowAdapter.flowPublisherToFlux(body)` 直接取消 → 立刻 FIN，加 `.cache(0)` → 6 次迟写全部成功。
- 根因（字节码）：reactor-core 3.7.17 的 `Flux.cache(int)` = `replay(int).autoConnect()`；`autoConnect()` 只在首个订阅者到达时连接，最后一个订阅者取消时**不**断开上游。`cache(0)` 出自 spring-web 6.2.17 `JdkClientHttpResponse.adaptBody:107` —— **框架行为，非 T6.1 引入**（T6.1 之前连"客户端不再等待"都没有，所以危害被掩盖）。
- 影响：每次卡死 / 断开都会留下一条没有 FIN、且本侧无任何计时器兜底的**上游 TCP 连接 + 在途 provider 请求**（`HttpRequest.timeout` 只管到响应头，已核；JDK 对进行中的 exchange 无空闲上限，连接池默认无上限）。对 T8 最直接：用户关页面后上游仍会继续生成，token 成本照付，直到 provider 自己超时或写满窗口。
- 建议（请用户三选一后记 decisions）：(a) 接受 + 文档化，并用真实 provider 验证"provider 侧会自行中断"；(b) 起一个 spike 换到不被 `autoConnect` 包裹的响应体路径（reactor-netty 不在当前 classpath，属新增依赖决策）；(c) 作为 T8 的显式任务与验收（"客户端断开 → 上游请求必须终止"）。

**R2（P2）重试口径写错，且阻塞路径的失败上限远大于一个 `timeout`。** `RetryUtils.DEFAULT_RETRY_TEMPLATE` 字节码为 `maxAttempts(10)` + `retryOn(TransientAiException)` + `retryOn(ResourceAccessException)` + `exponentialBackoff(2s, ×5, cap 180s)`；`ResourceAccessException` 正是 RestClient 对 socket 读超时的包装 → **阻塞路径的读超时会重试**（本会话实跑日志亦见 `RetryUtils -- Retry error. Retry count:1`）。故 plan.md T6 现象行与 T6.1 已知限制①里的"仅 retryOn `TransientAiException`"不准确，"一次超时即失败"的隐含上限也不成立（默认 `PT2M` 下最坏是 10 次尝试 + 退避和，分钟级）。结论方向不变（流式路径无重试）。

**R3（P2）T8 拿到的不是裸 `TimeoutException`，而是状态码 200 的 `WebClientResponseException` 包裹。** 测试日志与本会话两条探针三处一致：`WebClientResponseException: 200 OK from POST <uri>, but response failed with cause: java.util.concurrent.TimeoutException: Did not observe any item or terminal signal within 400ms ...`（`DefaultClientResponse.createException`，文案含真实 URI）。T6.1 已知限制①的方向对，但 T8 若按异常类型 / 状态码分支会判错（状态码是 200）→ 须**沿 cause 链判超时**，建议写进 T8 计划。
