## 我认为最该被挑的 12 个点（自曝，请直接开火）

1. **门槛顺序**：票（门槛四）排在三个登录门槛**之后**。理由已记（登录过期仍回 40100；身份不一致不白烧票），但代价是：跨站攻击者的请求仍会先触发两次 Redis 读（Spring Session + sa-token 查询）才被拒。请判"最便宜的闸先落"是否更该优先，以及我的理由是否成立。
2. **错误码与文案的三态处理**：票"缺失"与"已用过"共用同一条文案 + `40300`（不区分），"票属别人"另给一条文案；而 `40102` 是空间维度的既有口径。请判：三态是否该统一、`40300` 是否比 `40100` 更贴（代码语义 vs 客户端处理）。
3. **票绑定 userId 是否必要**：攻击者即便拿到票也仍需受害者的 Cookie，所以绑定能防的只是"跨账号用票"这种理论场景。我按防御性绑定了（并因此多一条"别人的真票被拒"用例）。若判定多余，简化与保留的取舍请给结论。
4. **票失效时前端只看到"连接中断"**：`EventSource` 读不到 `40300` 响应体，前端**没有**"403 → 重新取票重试一次"的兜底。窗口很窄（取票后立刻建流，毫秒级），但标签页被挂起到恢复可能超出 60 秒 TTL。请判这是否算可接受的残留，还是该顺手补一次重试。
5. **票进 nginx access log**：票在 query 里，会进访问日志。我的论证是"60 秒 + 单次使用 ⇒ 泄漏无害"。请独立判这个论证，并看是否需要把"提问/票不进日志"提前到档 3 处理。
6. **票不转发给引擎**（关键性质，请独立验证）：`AiAssistantProxyManager.chatUrl` 只带 `message`/`userId`/`chatId`，票**只到 backend 代理为止**——这是"票不会污染引擎日志与引擎侧代码"的前提。我没为其加断言测试，请判是否该补一条。
7. **一条新集成用例有假红风险**：`rejectsChatWithoutTicketEvenWithRealCredentials` 断言 `REQUESTS==0`，而 0015 记过"先转发的用例会让下一个用例的 `REQUESTS==0` 断言假红（异步计数残留）"。JUnit 方法顺序不保证——请重复跑该集成类多次确认不抖，或判是否该改成更稳的断言方式。
8. **`requireTrustedCaller` 是行为保持式重构吗**：我抽出了门槛一~三给签发端点与对话端点共用。请看 diff：逻辑等价，但 **"AI 助手对话开始"日志的位置变了**——现在只有票也通过才会记（无票的 403 只剩 `GlobalExceptionHandler` 的 ERROR）。可观测性上这是变好还是变坏，请判。
9. **既有测试被批量改了调用形态**：5 条集成用例与 10 处单测调用现在都带一张**有效票**（否则会因票门槛而红）。请确认那些负向用例的拒绝**确实来自它要验的那道门槛**（而不是"顺带因为票不对"）——断言里查的是具体错误码，理论上成立，但值得逐条看。
10. **前端零测试网**：前端改动只有 `type-check`（净增 0）+ 一次浏览器人工验收，**没有自动化守护**"取票 → 建流"这个顺序。目前唯一的守护是类型（改回旧签名会编译报错）。请判这个兜底是否够。
11. **单次使用的并发原子性没做探针**：实现是 Lua `GET+DEL`（原子），但我**没做并发同票**实验（0014 的 `saturate.js` 那种）。请用并发请求打同一张票，验证"恰好一个成功、其余 40300"。

## 判据清单（建议逐条给结论）

1. **设计**：票机制是否真的堵住了 R5（而不是只堵住"当前这一种打法"）？把"攻击者读不到响应体"当安全边界是否成立（有没有旁路：CORS 配置、Referer、票的猜测空间、TTL 窗口、并发窗口）？
2. **边界**：票过期/失效/被复用/属别人/并发同票；`ticket` 为空串/超长/含特殊字符（我只测了 null 与编造值）；**Redis 不可用或超时**时（`consume` 与 `issue` 都没捕获 Redis 异常，会冒泡成 HTTP 500 走 `GlobalExceptionHandler`，前端则表现为"连接中断"）——请判这是否可接受。
3. **安全**：`POST /ticket` 自身是否 CSRF 安全（依赖两把 Cookie 的 `SameSite=Lax` 实际生效——建议用真响应头 `Set-Cookie` 核实，而不是只信 yaml）；票是否可能被日志/前端存储/引擎侧记录；`issuedTo` 解析失败按无效处理是否够。
4. **与 spec 一致性**：关键三行是否仍成立——引擎零改动（`git diff 36aa8af..HEAD -- ai/` 空）、"引擎端点只接受服务间 API key"未变、"凭据不落库不进日志"未变（**票不算凭据：它不是 satoken、不是会话标识**，但确实往 Redis 写了 60 秒的 `userId`——这算不算突破边界，请给判断）。
5. **规则合规**：是否越界改了计划外文件（对照 plan.md 立项时的"文件范围"）；先红后绿是否真实（4 失败 → 20/20，红的原因是否为"请求被照常转发"）；代码/文档是否分离提交。
