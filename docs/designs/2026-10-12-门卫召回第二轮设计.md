# 2026-10-12 门卫召回第二轮设计（T46）

> 字据（用户 2026-10-12 批准）。来源：`docs/decisions/2026-10-12-review-confirm-gate-and-scope-gate.md` 的 P1（F1）与 P2（F2/F3/F4）。
> 本文件写定后不再修改（勘误除外）；生效口径以 `docs/decisions.md` 为准。

## 背景：F1（P1）+ F2/F3/F4（P2）

规则 13 独立 review 实测并核对出范围门卫的结构性召回问题：

- **F1（P1）门卫看不见 USER 行**：`lastAllowedRoundContext()` 以 USER 行划轮，**只取该轮 AssistantMessage 的文本**；
  USER 行文本从不进输入。于是
  ① 用户原始请求（空间名、目标图片、操作类型）在 2+ 轮之前就丢了；
  ② **T44 的「操作结果」事实行（USER 角色）对门卫不可见**，还额外吃掉一个轮边界把窗口顶回更早。
  真机后果：一次**已完成**写操作的追问「刚才那个批量编辑完成了吗？结果怎么样」被判 out-of-scope 拒答，
  只有当轮重述空间名（「继续刚才对 T44 smoke space 空间图片的整理…」）才放行——召回实质是**词法级**的，直接与 T44 的初衷矛盾。
- **F2（P2）工具名信号生产恒空**：回放视图经 `MessageConverter.toReplayMessage` 剥掉 `toolCalls`（`new AssistantMessage(text)`），
  而门卫读的正是回放视图——`composeRoundContext` 里"（上一轮工具：…）"**永不出现**；对应单测用裸 memory，绿灯但不代表生产。
- **F3（P2）判定解析脆弱 + 能力枚举缺写操作**：首个 `IN_SCOPE|OUT_OF_SCOPE` 子串定生死（否定式前言会被首个 OUT_OF_SCOPE 否决）；
  `SCOPE_CAPABILITIES_EN` 未明写"批量编辑图片"，而对话主体恰是写操作。
- **F4（P2）1 轮窗口丢锚点**：与 F1 同源——追问依赖的锚点往往在更早的轮次。

## 改动（仅 `ai/agent/.../agent/HuoshanAssistantAgent.java` + 其测试）

### A1' 门卫输入窗口修订（**修订 T43 A1 的"USER 行不进输入"**）

`lastAllowedRoundContext()` → `gateContextMessages()`（返回消息列表）：

- 取 `getHistoryContext()`（回放视图：USER 行 + 非空 ASSISTANT 行）的**最近至多 4 条**；
- **丢弃**内容（trim）等于 `OUT_OF_SCOPE_REPLY` 的行——拒绝话术仍不进输入；
- **USER 行最多保留 2 条**（离当前最近的两条）、**ASSISTANT 行最多 1 条**；
- 每条文本截断 `SCOPE_CONTEXT_MAX_CHARS`（500）；
- 按原序作为 `UserMessage`/`AssistantMessage` 拼在 System 之后，再拼本轮消息（`getMessageList()`）。

为什么修订 T43 A1：T43 排除 USER 行是为了防"历史拒绝轮污染"，但代价是把**追问赖以成立的任务锚点**也一并排除了。
拒绝话术本身仍被排除；被拒轮的 **USER 请求文本**进输入是可接受的（它是上一轮的真实意图，且门卫只判"最新一条"的范围，前文仅作上下文）。
风险（长文本挤占窗口）由"至多 2 条 USER + 500 字截断"封顶。

### A2' 移除工具名死信号（F2）

删除从 `AssistantMessage.getToolCalls()` 收集工具名与 `composeRoundContext` 的工具名后缀（生产恒空，属死路径）。
测试改用**回放代表性**的 memory（assistant 行不带 `toolCalls`），不再假装该信号可用。
**不做**：恢复工具名信号（需给 agent 开"读原始行"缝隙 + 每轮多一次 DB 读），本轮不做。

### A3' 判定健壮化（F3）

- `SCOPE_CAPABILITIES_EN` 补写/编辑操作：`batch editing pictures (category / tags / name), importing images by URL`。
- `SCOPE_PROMPT` v2 → v3：写明"写与编辑操作在范围内"，并补一句
  "a follow-up that asks whether a previously prepared or confirmed change has finished is in scope"。
- `isInScopeDecision`（`SCOPE_PROMPT` 无关，纯解析）加**否定式前言守卫**：首个匹配若是 `OUT_OF_SCOPE`
  且其**紧邻前方**（回看约 16 字符）出现否定词（`not` / `is not` / `isn't` / `非` / `不是` / `不属于`），
  则跳过该次匹配、继续找下一个 token；否则沿用"首个 token 定生死"。
  `"OUT_OF_SCOPE，虽然后面想 IN_SCOPE"` 仍拒（首 token 前无否定词）；无 token 仍 fail-closed。

**保持**：fail-closed；拒绝话术与"门卫是语义策略、非授权边界"不变；`IN_SCOPE` 判定仍要求走模型分类（不加确定性短路）。

## 明确不做（记录理由）

- **关键词短路口**（省一次模型调用、硬保召回）：用户 2026-10-12 定"不加"——避免引入需维护的关键词表，保持机制单一。
- **恢复工具名信号**（读原始行）：需给 agent 开只读缝隙 + 每轮多一次 DB 读；值当性不足，本轮不做。
- 不改拒绝话术、不动 `BaseAgent` 循环与 backend/前端。
- spec 关键三行不改（"无关请求应简短拒绝并引导回能力范围"的边界保持，只提升 in-scope 追问召回）。

## 测试（先红后绿）

1. **新增**「写操作追问的锚点进输入」：memory = [`UserMessage` 原始请求, `AssistantMessage` "…现在生成待确认操作：", `UserMessage` "【系统记录】…批量编辑…提交 2 张。"] →
   断言门卫 Prompt 的 instructions 含原始请求文本与事实行文本、**不含**拒绝话术。
2. **替换** F2 旧测试为「门卫输入是回放代表性的」：assistant 行不带 `toolCalls` → 上下文来自文本、**不出现**"上一轮工具"字样。
3. **新增**「否定式前言不否决 IN_SCOPE」：`isInScopeDecision("This is not OUT_OF_SCOPE; it is IN_SCOPE") == true`。
4. **更新** T43 `scopeInputContainsOnlyLastAllowedRoundContext`（断言随 A1' 修订：拒绝话术不进、USER 锚点进）。
5. **保留**负向：非协议输出 fail-closed、首 token `OUT_OF_SCOPE` 拒、三类范围外请求拒。
6. **负向控制实测**：把窗口改回"只取 assistant 文本" → 用例 1 红。

## 验收

- 引擎门禁全绿；负向控制实测红。
- 真机复跑误拒形态：有先导写操作上下文时「刚才那个批量编辑完成了吗？」放行；范围外请求仍拒。
