# AI 扩图降级为维护态（T64 字据，2026-10-16）

> 本文件是 T64 的**字据 + 设计 + 验收**全文（对应 `docs/plan.md` T64 条目）。
> 生效口径记入 `docs/decisions.md` 一行，指向本文件；本文写定后除勘误不再改。

## 一句话

AI 扩图**保留在功能清单里、但默认不可用**：backend 加一道维护门闩（`app.outpainting.enabled`，默认 `false`），关闭时扩图入口一律返回维护提示且**不调百炼、不扣配额、不写幂等键**；前端弹窗据此显示"维护中"并隐藏生成按钮。恢复只需翻转环境变量，不需要前端重新发版。

## 现状：两个不可逆事实（都不可恢复）

| # | 事实 | 依据 |
|---|---|---|
| 1 | `image-out-painting` **已被百炼官方下线**，停止服务日 **2026-10-10** | 官方公告 [notice/118434](https://www.aliyun.com/notice/118434)（2026-07-10 发布）；机制见[模型下线说明](https://help.aliyun.com/zh/model-studio/model-depreciation) |
| 2 | 语义最接近的替代 `wanx2.1-imageedit`（`function=expand`）的 **500 张新人免费额度已于 2026-07-09 过期作废**，且**不支持补发、延期或重置**；同一实名主体重开账号也拿不到第二次 | 用户控制台截图（0/500 已用、状态「已过期」）；规则见[免费额度说明](https://help.aliyun.com/zh/model-studio/new-free-quota) |

附带事实：官方推荐的替代 `qwen-image-3.0` 是**指令式**图像编辑（`messages` + `prompt` + `size`），没有扩图参数；且该公告的「推荐替换」列对 `aitryon`、`facechain-generation`、`wordart-*` 等用途完全不同的模型**一律填同一个 `qwen-image-3.0`**，属批量兜底推荐，不是针对扩图的对口建议。

## 决定

**保留功能、降级为维护态，不再调用任何厂商图像模型。**

1. **门闩**：新增配置 `app.outpainting.enabled`（`${OUTPAINTING_ENABLED:false}`），与既有 `app.outpainting.daily-quota` 同命名空间。**默认 `false`＝维护态**，即不做任何部署动作即是安全状态。
2. **关闭时的服务层行为**（`PictureServiceImpl`）：`createOutPaintingTask` 与 `getOutPaintingTask` 的**第一件事**就是判门闩，关闭即抛业务异常并带维护文案——先于图片存在性校验、权限复核、幂等占位、配额计数。因此关闭态下：**零百炼调用**（不产生任何计费风险）、**零 Redis 触碰**（不占幂等键、不扣每日配额）。门闩放在权限校验之前是有意的：关闭时不给调用方任何"这张图存在/不存在"的探测信号。
3. **状态下发**：新增只读端点 `GET /picture/out_painting/status` → `BaseResponse<VOutPaintingStatusVO>{ available, message }`。**不含用户数据、无副作用、幂等**，故不加鉴权注解（该路径落在 `/picture/**` 注解可信区内，需要时可再加）。维护文案与异常文案**同源**（同一个常量），避免前端与后端各写一句。
4. **前端**（`ImageOutPainting.vue`）：打开弹窗时取状态；`available=false` 时展示 `a-alert` 维护通知并**隐藏「生成图片」按钮**（「应用结果」随结果为空自然不显示）。**取状态失败时不显示维护横幅**（维持现有界面），因为服务端门闩已经兜住；此时点击生成会拿到后端返回的维护文案——宁可少一次误报"坏了"，也不要把"能用的功能"显示成"维护中"。
5. **不删代码**：`AliYunAiApi`、请求/响应模型、幂等与配额逻辑**原样保留**，仅前面加门闩。这样恢复时改的是配置，不是代码。

## 为什么这么定

- **为什么不迁到 `wanx2.1-imageedit`**：它只保住"参数级扩图"语义，但一样要**按量付费 0.14 元/张**（免费额度已作废），同时还叠加三个新约束——仅北京地域、四方向参数由像素 offset 变扩展倍数（`top/bottom/left/right_scale`）、`angle`/`output_ratio`/`best_quality`/`limit_image_size` 全部不支持。为一个作品集演示功能引入"付费 + 地域锁定 + 能力缩水 + 再次被下线风险（它也是 2.1 代老模型）"，性价比不成立。
- **为什么不干脆删功能**：用户明确要保留。而且保留态的成本接近零——门闩默认关闭，既不产生调用也不产生费用，恢复只是翻一个环境变量。删掉再想加回来，是实打实的返工。
- **为什么默认 `false` 而不是 `true`**：默认值即部署后的行为。若默认 `true`，任何一次"忘了配环境变量"的部署都会**直接开始按量计费**。默认关闭 = 失败安全。
- **为什么加状态端点而不是前端写死文案**：写死意味着恢复要**前端重新构建 + 发版**；走端点则恢复只是后端配置变更。两处文案也因此同源。

## 不做什么

- 不删 `AliYunAiApi` 与扩图请求/响应模型，不改幂等键与每日配额算法本身。
- 不动 `docs/spec.md` 关键三行（目标里的"AI 扩图"仍在功能清单内，本次只是可用性状态变化）。
- 不引入新依赖、新进程、新数据表。
- 不为"恢复"预置任何自动化的厂商切换逻辑（真的恢复时另开任务，届时重新评估模型、地域与计费）。

## 验收（红绿口径）

1. **服务层单测（纯 Mockito、无 Spring 上下文）先红后绿**，至少覆盖：
   - 关闭时 `createOutPaintingTask` 抛业务异常且文案＝维护文案；
   - 关闭时 `verifyNoInteractions(AliYunAiApi)` 且**零 `StringRedisTemplate` 交互**（幂等键与配额都没被碰）；
   - 关闭时 `getOutPaintingTask` 同样被拦；
   - 开启时门闩不拦（既有路径不受影响）。
   - **负向控制**：把门闩判断挪到配额之后、或改成恒 `true`，测试须变红。
2. **既有集成测试** `OutPaintingTaskIdempotencyIntegrationTest` 补 `app.outpainting.enabled=true` 后仍全绿——它证的是"开启态"的幂等与配额语义没被本次改动破坏。
3. **前端**：`npm run type-check` 保持 0 错、改动文件 `npx eslint .` 干净；`check:assistant-*` 三项不破。
4. **浏览器真机**：本机起前后端，点开 AI 扩图弹窗 → 显示维护通知、无「生成图片」按钮、点击不产生任何任务创建请求（看后端日志无扩图调用、Redis 无扩图键）。

## 恢复路径（将来要做时）

1. 决定用哪个模型（届时重新评估：是否还免费、地域、参数能力），迁 `AliYunAiApi` 的端点与请求体——**这是另一个任务，需要新字据**；
2. 配 `OUTPAINTING_ENABLED=true` 并重启 backend；
3. 前端零改动（状态端点会自动回到 `available=true`）。

## 已知限制与未覆盖

1. **维护态下 `get_task` 也不可用**：门闩同时拦查询。理由是没有可用的创建入口就不会有新任务，而在途任务对应的模型已下线、查了也是失败。代价是**历史 taskId 无法再查询**——可接受（该能力本就没有持久化任务表，taskId 只在 Redis 里存活 1 天）。
2. **维护文案是后端常量、不是可配置项**：改文案要改代码。选它是因为"同一句话只有一个来源"，且本次已无频繁调整的需求；若将来需要按环境说不同的话，再提取为配置。
3. **本次不验证真实厂商调用**：门闩关闭态下不存在厂商调用路径，故"迁移到某模型后能否真的生成"**没有也不可能有证据**——这正是把"恢复"另立任务的原因。
4. **前端无单测框架**：本项目前端只有 `type-check`/`eslint`/三个 `check:*` 脚本，维护态展示的正确性由浏览器真机验收背书（规则 16：真机证据可复跑者写入 records）。
