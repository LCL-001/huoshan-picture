# 助手范围围栏开源调研（vibe-scout，2026-09-28）

> 起因：T36–T39 真机冒烟发现范围门卫"历史污染误拒"（同一 in-scope 祈使句在新会话通过、同会话积累 3 条固定拒绝轮后被误拒；被拒轮 USER 行已入库而 ASSISTANT 行缺位）。本文调研同类开源项目如何设定范围，为门卫改进（未来字据）找借鉴。**本文只记调研，不含生效决定。**

## 候选与结论表

| 项目 | 形态 | 范围设定方式 | 活跃度/License | 裁决 |
|---|---|---|---|---|
| NeMo Guardrails（NVIDIA） | 护栏框架 | 主题栏（Colang 主题流）+ 输入栏 self-check（**只喂当前一条用户消息**）+ 拒绝是对话流一等公民（`bot inform off topic` 有正式话术定义） | 极活跃，Apache-2.0 | **借鉴两点**（见下） |
| Dify | LLM 应用平台 | 内容安全 = `app.moderation.input/output` 两个扩展点（关键词表或内容安全 API）；主题范围 = 应用提示词的"约束"区（无独立分类器） | 极活跃，Apache-2.0 + 附加条款 | 借鉴"输入/输出两端独立审查点"的结构观 |
| Grafana Assistant（grafana-llm-app） | 产品内嵌助手（与我们同形态） | **系统提示词编排**：固定提示 + 可配置 rules 注入（tenant/user 级、带优先级）+ 当前视图上下文；无前置分类器，配工具集 + 底层 API 鉴权 | 活跃，Apache-2.0 | 借鉴"范围枚举单一来源、按租户注入"的思路（远期） |
| Discourse AI personas | 产品内嵌 bot | 范围 = 人设配置：system prompt + 工具白名单 + allowed groups（谁可用）+ 优先级；系统 persona 锁核心属性 | 活跃，GPLv2（借代码需谨慎） | 已对齐（我们已做工具裁剪 + 角色裁剪） |
| Onyx（原 Danswer） | 企业知识库问答助手 | **检索围栏**：强制先检索、答案必须出自索引文档并带引用，答不出就拒——数据边界即范围；许可证非标准开源标识 | 活跃，license 需核实 | 参考其"拒绝不可靠就不上线"的验收观；grounding 模式不适用（我们答平台操作而非文档） |

共性共识：① 固定拒绝话术是标配（REFUSAL_MESSAGE，不道歉不解释）；② 提示词围栏、检索围栏、工具裁剪、内容审查是**正交的四层**，各管一段；③ 主题围栏用独立的轻量分类调用与我们的 T25 方向一致——**分歧只在喂给分类器什么**。

## 裁决：借鉴（不引轮子、不推倒自研）

T25 门卫的骨架（独立分类 + 严格 token 协议 + fail-closed）与业界主流一致，缺陷在喂料。借鉴 NeMo Guardrails 两个机制点，落到我们的门卫改进字据：

1. **门卫输入瘦身**：NeMo 的 self-check 输入模板只有 `User message: {{ user_input }}` 一行——**护栏分类器绝不裸吃全量原始历史**。我们应改为"最新用户消息 + 受控的任务上下文摘要"（如上一轮的任务标记），至少**剥离历史中的固定拒绝文本与无回答轮**，杜绝"拒绝轮污染分类"闭环。
2. **拒绝是对话的一等公民**：NeMo 把 `bot inform off topic` 定义为对话流中的正式 bot 话术。被拒轮应补写一条固定话术的 ASSISTANT 行（历史与回放同源修复）——既消掉"孤立 USER 行"这个分类器噪音源，也修掉回放"用户问了、助手未答"的保真缺口。

不采纳：embedding 主题质心比对（NeMo 高级玩法，对我们的体量属过度设计，YAGNI）；引入 NeMo/Dify 本体（Python/平台生态，不合我们 Java/Spring AI 栈，且只需两个机制点）。

## 备注

- 范围措辞四处重复（SCOPE_PROMPT / SYSTEM_PROMPT / NEXT_STEP_PROMPT / 中文固定话术）的维护问题，可借 Grafana "rules 单一来源注入"思路在字据里一并收口，但属可选优化。
- 本调研结论在用户批准门卫改进立项（立字据）时，才转入 `docs/decisions.md` 生效口径。
