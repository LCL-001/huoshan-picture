# 2026-10-12 确认门收尾与结果回灌设计（T44 / T45）

> 字据（用户 2026-10-12 批准）。来源：2026-10-12 一轮只读审查提出的两条 P1。
> 本文件写定后不再修改（勘误除外）；生效口径以 `docs/decisions.md` 为准。

## 背景：两条 P1

### P1-1 生成确认卡片后 Agent 不定停

- 位置：引擎 `ToolCallAgent.act()`（确认载荷识别与事件组装处）、`BaseAgent.runLoop()` 的 while 条件。
- 现状：`act()` 识别出 prepare 工具返回的"待确认操作"载荷后，只把 `AgentEvent.Confirmation` 放进本步事件列表，
  **没有**改状态；`runLoop` 的 while 以 `state != FINISHED` 为条件，于是必然再执行一步 `think()`（再调一次主模型）。
- 后果：卡片之后行为不确定——模型可能只补一句"请确认"（本次实测的常见形态），也可能再次调用 prepare 生成第二张卡片；
  白烧步数与额度；多张卡片造成认知混乱。
- **边界澄清**：确认门本身是 Redis 原子单次消费 + 用户/会话绑定，同一个 operation 不会被执行两次；
  URL 导入另有 `sourceUrl` 按空间判重兜底。所以这不是"重复写入"的漏洞，而是"循环结构允许不确定行为"的缺陷。

### P1-2 确认执行结果不进引擎历史

- 位置：backend `AiAssistantController.confirmOperation`、引擎回放路径 `MessageConverter.toReplayMessages`。
- 现状：confirm 全程只与 backend 交互，不碰引擎；回放又丢掉 TOOL 行与空文本 assistant 决策行。
  于是下一轮模型只看到用户的原始请求与它自己那句"请确认"，**读不到"已执行成功"这一事实**，
  可能再生成 prepare、再要确认，或答"尚未完成"。
- 后果：前端卡片状态、backend Redis 状态、引擎模型上下文三者分叉。

## T45 设计：确认后确定性收尾

`ToolCallAgent.act()`：算出 `confirmations` 后，非空则 `setState(AgentState.FINISHED)`
（置于 doTerminate / askHuman 分支之后、返回本步事件之前）。循环随即退出；
`runLoop` 的收尾不变量（每条流恰好一个 `[DONE]`）不变。

- 用户可见变化：卡片帧之后不再有模型那句"请确认"文本——流在卡片后即收尾。卡片自带摘要，语义不丢（写进 F13）。
- 前端纵深防护：`AssistantPage.vue` 的"确认执行 / 取消"按钮加 `:disabled="running"`（真正的根治在引擎侧，前端只是兜底）。

## T44 设计：确认结果以引擎侧持久化事实回灌

**选型：引擎侧持久化事实**（用户 2026-10-12 定），而非"下一轮 /chat 一次性参数"。
理由：单一事实源、刷新/换页/换设备仍在、与既有只读历史端点对称；一次性参数方案会让结果在用户不再续聊时自然丢弃。

数据流：

1. 用户确认 → backend `confirm` 原子消费并执行既存计划 → 得到 `AiOperationResultVO`。
2. backend 生成模型面中文说明（`AiAssistantOperationManager.operationResultNote`），调引擎内部端点。
3. 引擎把一条 **USER 角色 + 哨兵前缀 `【系统记录】`** 的消息写入该会话记忆（`FlowWindowBasedChatMemory.add`）。
4. 下一轮聊天：`FlowWindowBasedChatMemory.get → MessageConverter.toReplayMessages` 保留 USER 行 → 模型读到该事实。
5. 前端历史：`ChatHistoryAssembler` 的前缀过滤（与 `NEXT_STEP_PROMPT` / 卡死提示同一条内部提示桶）→ 该行不出现，
   维持"回放无确认卡片"现状。

端点契约：

- `POST {engine}/ai/huoshan/conversations/{chatId}/operation-results?userId=<id>`，body `{"content":"..."}`。
- 鉴权：沿用既有 `HeadlessApiKeyInterceptor`（覆盖 `/ai/huoshan/**`，服务间 API key，fail-closed）——不新增鉴权机制。
- 归属：`HuoshanAssistantSession.owner(userId)` 校验 + `conversationId(owner, chatId)` 派生；只写该会话。
- 内容：由 backend 生成（可信、非用户原文），不含用户可控 payload。

为什么用 USER 角色而非 ASSISTANT：与既有"以 USER 角色入库的内部提示"同一模式——模型侧可见、前端侧按内部提示前缀过滤，
复用现成机制、改动面最小。SYSTEM 不可用（记忆实现只保留一条 system 行做人设）。

安全边界：新端点仅服务间密钥可调（与只读历史端点同信任模型："持密钥的调用方可信 + UUID 派生天然按用户隔离"）；
内容非用户原文；不新增数据表、不新增进程、不新增依赖。

尽最大努力语义：backend 记录失败只 `log.warn`，**绝不影响** confirm 的返回——结果回灌是旁路事实，确认与执行才是主路径。

## 测试

- T44：引擎端点单测（落 USER 行 + 前缀）、`ChatHistoryAssemblerTest`（前缀行不出现在前端视图）、
  `MessageConverterReplayTest`（前缀行**在**模型可见序列里）；backend `operationResultNote` 格式用例、
  控制器"成功后恰记录一次且记录失败不影响确认"用例。
- T45：新增 `runLoop` 全循环测试（prepare 载荷 → `callLlm` 恰一次 / 恰一张 Confirmation / 恰一个 Done / 终态 FINISHED），
  先红后绿；`act()` 用例补 `state == FINISHED` 断言。

## 明确不做

- 不改确认门安全设计（Lua 原子消费、凭据一致性、URL SSRF 防护）。
- 不在本轮纳入审查其余 P2（操作计划大小上限、缓存失效异常、editor 鉴权口径、历史响应体上限、扩图未知结果状态等）。
- 不做完整工作流状态机；只做到 `prepare → pending`、`confirm → executed / partial_failed` 能被下一轮读到。
