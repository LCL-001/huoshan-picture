## 一句话

给助手补两件体验层的事：① 会话列表 + 历史回看续聊（backend 索引表 + 引擎只读端点 + 前端侧栏）；② 失败以独立错误样式呈现（不再混进助手气泡）。

## 目标与非目标

目标：

- 刷新或换会话后能从侧栏找回历史会话，回看完整"轮 + 步骤折叠条"，并接着聊（引擎记忆按 chatId 天然延续）。
- 用户能分辨"助手说的话"与"出错了"。

非目标（v1 明确不做，后续另行立项）：

- 会话重命名 / 删除（已写进 spec 不做的事）；
- 工具摘要分支（原 T40）：计划期核实 `summarizeToolResult` 已覆盖 `visionTagger` / `searchImage` 且断言入库，无可做之事，撤销；
- AI 生成标题（引擎 `ConversationTitleService` 存在，日后可升级）；
- 客服/帮助问答、语义搜图、写确认门（T27.4～T27.7 按原计划另行推进）。

## 关键现状事实（设计依据，均已核实）

1. 引擎把图库对话存为 `chat_message` 行（一次运行 = 1 条用户行 + 每步 1 条助手行，T32 口径），`conversation_id` 是 `UUID.nameUUIDFromBytes("huoshan:<用户id>:<chatId>")` 的**确定性 UUID**——不可逆、表上无归属列。
2. 引擎自有用户的 `ConversationController`（`/conversations` CRUD + 消息回放）依赖引擎 session 登录，图库用户不可用；`HuoshanAssistantController` 类注释明确"headless 端点不做会话簿记（conversation 表 user_id 外键指向引擎 user 表）"。
3. `ChatHistoryAssembler.assemble()` 已能把 `chat_message` 扁平行组装成前端折叠条同构的 `ChatMessageVO`（轮 + steps：内部提示过滤、askHuman 还原、步骤内容截断 2000 字）。
4. 前端 `chatId = crypto.randomUUID()`（36 字符），存 sessionStorage；"新对话"换 chatId 后旧 chatId 前端不再记得——**列表数据必须由服务端给**。
5. F13 协议已定义 `event=error` 事件类型；前端目前把 error 帧当文本追加进气泡（F11 已知限制 2）。
6. backend `/ai/**` 不进 `SaTokenConfigure` 拦截，登录门槛在控制器显式 `getLoginUser`（`AiPathSaTokenGuardTest` 不变量守护）。

## 方案总览（索引放 backend，方案 A）

```
对话时（现状不动）：浏览器 → POST ticket → GET chat（四道门槛 → SSE 中继）
  backend 在门槛全过、建流前 → upsert ai_conversation(userId, chatId, 标题=首条消息截断)

回看时：
  浏览器 GET /api/ai/assistant/conversations → backend 查索引表直出列表
  浏览器 GET /api/ai/assistant/conversations/{chatId}/messages
    → backend 验索引归属（40400 零上游）
    → 引擎 GET /api/ai/huoshan/conversations/{chatId}/messages?userId=
       → 派生确定性 conversationId → 查 chat_message → ChatHistoryAssembler → 轮 + steps
```

为什么不在引擎列会话：归属信息只有 backend 有（见"关键现状事实"1/2）。方案 A 让"谁有哪些会话"住在用户身份旁边，引擎保持只读、零 DDL、不动遗留链路。

## 各层设计

### backend（T36 索引与列表、T37 透传、T39 error 帧）

- **新表 `ai_conversation`**：`id`（雪花）、`user_id`、`chat_id varchar(64)`、`title varchar(256)`、`create_time`、`update_time`、`is_delete`（跟随全库惯例）；唯一索引 `(user_id, chat_id)`，列表索引 `(user_id, update_time)`。SQL 脚本入 `backend/sql/`（命名跟随 `create_*_table.sql` 惯例）。
- **upsert（T36）**：`/api/ai/assistant/chat` 四道门槛全过、SseEmitter 建流前同步执行（单行、毫秒级；实测有抖动再异步化）。语义：行不存在 → insert（标题 = 该次 message 截断至 64 字）；已存在 → 只刷 `update_time`，**不覆盖标题**（标准聊天产品行为）。chatId 为空不记索引（不影响对话）。
- **列表端点（T36）**：`GET /api/ai/assistant/conversations?page=&pageSize=`（默认 20，按 `update_time` desc），返回 `[{chatId, title, createTime, updateTime}]`。门槛仅 `getLoginUser`（不调引擎工具，无需 satoken/ticket）。
- **读消息端点（T37）**：`GET /api/ai/assistant/conversations/{chatId}/messages`——① 显式登录；② 查索引行，无或不属于当前用户 → `40400 "会话不存在或无权访问"`（零上游）；③ 透传引擎（服务间密钥 + `userId` 取自登录态，**不收浏览器传的 userId**）。
- **代理 JSON 透传（T37）**：`AiAssistantProxyManager` 新增同步 GET 方法（`HttpURLConnection`，读超时沿用 30s 档）；引擎不可达/非 JSON → `BusinessException(50000, "引擎暂时不可用")`，走 axios 统一拦截提示。
- **error 帧合成（T39）**：代理侧三类合成失败（引擎返回非 SSE、连接/读取失败、流中断）由合成 `answer` 改为合成协议既有的 `error` 帧，仍以 `[DONE]` 收尾；单测断言帧形状。

### 引擎 ai/agent（T37）

- `HuoshanAssistantController` 新增 `GET /ai/huoshan/conversations/{chatId}/messages`（沿用 `HeadlessApiKeyInterceptor` 内部密钥信道）：
  - `userId` 经 `HuoshanAssistantSession.owner()` 归一化（非法即 PARAMS_ERROR），与 chatId 一起派生确定性 conversationId；
  - 按 conversation_id 查 `chat_message`（`orderByAsc(id)`）→ `ChatHistoryAssembler.assemble()` → `BaseResponse<List<ChatMessageVO>>`；
  - 无行 → 空列表（归属已由 backend 判过；引擎信任模型与 `/chat` 相同：持密钥的调用方可信 + UUID 派生天然按用户隔离）。
- 零 DDL、零新依赖；不动 `conversation` 表与其遗留链路。

### frontend（T38 侧栏与回放、T39 错误态）

- **侧栏（T38）**：`/assistant` 桌面端左侧常驻会话侧栏（列表项：标题 + 时间，当前 chatId 高亮），移动端收进抽屉。进页拉列表；发送成功后重拉（不做本地排序，重拉最可靠）。
- **历史回放（T38）**：点会话 → 拉 messages → 复用现有气泡 + `StepTimeline` 渲染。历史 steps 的 `name` 是工具名，走 `assistantFormat.ts` 现有中文别名映射；`content` 是工具原始响应（已截断），过一遍 `summarizeToolResult` 出一句话摘要，"详情"展开原文。回放若抽出新纯函数，进 `check:assistant-format` 断言。
- **续聊（T38）**：选中历史会话即把该 chatId 写回 sessionStorage 并启用输入框——引擎记忆按 chatId 承载，续聊天然接上下文；范围门卫带历史判断多轮跟进（T25 既有口径）。
- **错误态（T39）**：`assistantSse.ts` 把 `event=error` 分流为独立消息类型（不复用 answer 管道），页面渲染独立错误样式（非助手气泡）。

## 鉴权与安全

- 两个新 backend 端点都在 `/ai/**` 下：不进 `SaTokenConfigure`、显式 `getLoginUser`——`AiPathSaTokenGuardTest` 的两条不变量（`/ai/**` 无 Sa-Token 注解、注解控制器必须被拦截路径覆盖）自动约束新代码。
- 归属判定只在 backend（索引表 `user_id` 比对）；引擎不判归属，信任模型与 `/chat` 完全相同（服务间密钥调用方 + 确定性 UUID 按用户隔离）。
- 列表/读历史是纯 GET 无副作用 → **不需要 ticket**（R5 的票只约束"GET 有副作用"的对话端点，口径自洽）；也不转发用户 satoken/SESSION（引擎读消息不用图库凭据）。
- 日志口径沿用现状：记 conversationId（UUID），不记原始 chatId / userId 明文（与既有"可换行注入"那类输入的处理一致）。

## 已知限制（诚实清单）

1. **旧会话不进列表**：索引自功能上线起积累；历史 `chat_message` 行的归属不可逆推，无法回填。
2. **notice 帧不入历史**：MCP 降级提示（T22）是流内事件、不落 `chat_message`，回放看不到。
3. **步骤详情是截断原文**：历史里步骤 content 截断至 2000 字；live 会话的"详情"是完整原始 JSON——回放保真度低于 live。
4. **标题非 AI 生成**：首条消息截断。
5. **索引与引擎行无一致性约束**：`ai_conversation` v1 只增不删；引擎侧行被清理后历史端点返回空列表，前端按"暂无消息"处理。
6. **EOF 无 `[DONE]` 的"答案 + 错误同屏"语义保留**（引擎侧行为，T39 只改呈现形态与合成路径）。
7. upsert 同步在建流前（单行毫秒级）；若真机测出建流抖动，异步化是局部小改。
