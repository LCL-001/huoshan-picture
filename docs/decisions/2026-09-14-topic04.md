## 决定

转向"MVP 优先"（用户拍板"先做出来能用，再慢慢优化"）：一期范围不变，改为**档位推进**——档 1 headless 打通（T8 的会话类型 / headless SSE 端点 / 服务间 API key / `huoshan:<userId>` 身份映射，**循环不重构**；T7 的 `listSpaces` / `listPictures` / `getTagCategory` 三个只读工具）→ **档 2 用户可见 MVP（本轮终点 = 设计文档验收标准 1 最小形态：T10 backend 代理 + T11 前端助手界面与步骤折叠条）** → 档 3 完整一期（visionTagger、`batchEditPictures` / `batchUploadByUrl`、T9 搜图、T8-hard 循环合并、T12 联调、T13 清理）；**MVP 阶段放宽**：规则 13 独立 review 与规则 9 讲解文档降为里程碑（档 2 收口）一次，重集成测试留 T12，上轮 review 的 P3 继续挂；**不放宽**：密钥不入库 / token 只在请求生命周期、一期不注册删除类工具、工具调用走用户真实 satoken 由图库判 RBAC、门禁红绿灯、`docs:` 单独提交；**R1（取消不关闭上游请求）延后到档 2 之后**（T8 只做超时转显式错误事件、不承诺关闭上游，加超时/取消埋点，接真实 provider 后再定）

## 理由

转向依据：T4-T6.1 已完成的全是地基、无可演示功能，而 T7/T8 现在把"用户可见功能"与"纯内部重构（统一 run/runStream、`run()` 退役）"绑在一条任务里，MVP 打法的核心动作就是把重构留到档 3；R1 不使功能不可用（只是资源/成本），延后不挡"能用"；spec 关键三行已同批更新（档位口径），plan.md 增"MVP 档位与推进顺序"节
