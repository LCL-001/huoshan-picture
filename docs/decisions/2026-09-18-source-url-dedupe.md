# 2026-09-18 URL 导入去重口径（T29）

> 状态：生效。口径表行见 `docs/decisions.md` 2026-09-18。实施与红绿证据见 `docs/plans/records/T29-源地址去重.md`；功能讲解见 `docs/features/F3-批量抓取.md`。本文件写定后不可变（勘误除外）。

## 背景

`uploadPicture` 对 URL 输入（单张 `/picture/upload/url` 与批量抓取）会用**源地址**去查 `picture.url`，而库里 `url` 存的是 **COS 地址**（`host + {日期}_{随机12位}.{后缀}`）——两者不同名空间，这条"图片已存在"检查从写下的那天起就永远命中不了（T28 发现）。后果：同一张图被反复下载、重复转存 COS、在库里留下内容相同的多条记录。

## 决定

1. `picture` 新增 `sourceUrl varchar(1024) NULL`（URL 导入/批量抓取写入来源地址；`MultipartFile` 上传写 NULL）+ 前缀索引 `idx_sourceUrl (sourceUrl(191))`（utf8mb4 下全列索引 4096B 超 InnoDB 3072B 上限）。
2. 判重口径 = **源地址 + 目标空间**：同一源地址在同一空间内只导一次；跨空间、公共图库（`spaceId IS NULL`）与空间之间互不影响；逻辑删除的记录不参与判重（`@TableLogic` 自动过滤），删掉后可重新导入。命中仍拒绝，文案沿用"图片已存在"。
3. 批量抓取的并行前过滤改用同一列（批量一律进公共图库，空间条件是 `IS NULL`），仍是**一次 `IN` 查询**。
4. 替换图片时排除自身（"用同一个源地址替换自己"不能被自己挡住）；用文件替换后**显式清空**旧源地址（MyBatis-Plus 的 `updateById` 不写 null 字段，不清就会一直误挡同地址的重新导入）。
5. 删掉 `getByUrl`（改后无调用者）。
6. **刻意不建唯一索引**：逻辑删除的行会永久占住唯一索引（tag/user 已踩过这个坑），判重靠查询；因此查询用 `getOne(wrapper, false)` 取第一条，避免同地址多行时抛异常。

## 未选方案与理由

- **内容哈希去重**（抓"不同 URL 同一张图"）：需要给 `PictureUploadTemplate` 加"下载后、传 COS 前"的钩子，且要定去重范围与"用户故意要两份"的例外；当前高频场景（同词重跑、重复粘 URL）用源地址即可覆盖，留作后续（它的历史数据可从 COS 回填，晚做不亏；源地址的历史数据补不回来，所以要早做）。
- **Redis `SETNX` + TTL 记录已导入地址**：不动 DDL，但重启/过期后重复照旧，语义退成"近期去重"。
- **命中后复用已有 COS 对象、只插新记录**：改的是产品语义（适合"同一张图进不同空间"），与"同词重跑不该再出来"冲突，未采用。

## 影响的部署顺序（硬约束）

后端**没有 Flyway/Liquibase**，DDL 只能手工执行，且**必须先于新 jar**：URL 导入与批量抓取的判重查询会引用 `sourceUrl`，缺列即 `Unknown column`（文件上传不写该列，不受影响）。步骤与命令见 `deploy/prod-checklist.md` §2.1。

## 已知限制

- 判重按**源地址**而非内容：不同 URL 指向同一张图仍会各存一份。
- T29 之前导入的历史记录 `sourceUrl` 为 NULL、不参与判重：那些图还会被重复导入一次，此后才被记下并拦住（源地址已丢失，无法回填）。
- `MultipartFile` 上传不写来源地址、也不参与判重：用文件重复上传同一张图仍会各存一份。
