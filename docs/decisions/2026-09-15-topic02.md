## 决定

**图库助手模型由 DeepSeek 换成小米 MiMo（`mimo-v2.5`，用户指定）**：① base-url = `https://api.xiaomimimo.com`（协议根；MiMo 文档给的请求地址是 `https://api.xiaomimimo.com/v1/chat/completions`，Spring AI 拼的正是这一段）；② **零代码改动**——MiMo 同时支持 `api-key: xxx` 与 `Authorization: Bearer xxx`，Spring AI 默认发的就是后者；`thinking` 是**顶层**字段，早先为 DeepSeek 加的 `extra-body`（直通请求体顶层）原样可用；③ **主脑与 visionTagger 都用 `mimo-v2.5`**——官方文档写明"**图像、音频或视频输入当前仅 `mimo-v2.5` 支持**"（`mimo-v2.5-pro` 不支持图片），与 DeepSeek 那边"flash 才是多模态"是同一格局；④ **仍显式关思考模式**（`thinking.type=disabled`），但性质变了：MiMo 只是"建议保留历史 `reasoning_content` 以获得最佳表现"、不回传**不会**报错，而 DeepSeek 不回传是**硬 400**——所以在 MiMo 下关思考模式是"更省更快、温度生效、输出更稳"的偏好；⑤ 配置只改那份不入库的 `application-local.yaml`，DeepSeek 那套压成三行备注留在同文件里（切回改三处即可）。

## 理由

**三项冒烟实测全通**（一次性 Spring 上下文用例，跑完即删）：`/v1/chat/completions` 路径可用；带工具的多轮调用通过（模型确实调用了工具并据此作答）；**图像输入对图库 COS 图与第三方 CDN（Pexels）图都可用**——Pexels 那张在 DeepSeek 上曾被 `400 unsupported image` 拒掉，说明 MiMo 的抓取更宽松。**两条业务场景在 MiMo 上端到端复跑通过**（真机链：backend 8123 → 引擎 8124 → 图库 API + MCP 8127）：搜图入库 18.6s（搜到 15 条 → 入库 3/3 成功）、智能整理 53.4s（9 张图挑出 3 张无标图 → `visionTagger` 建议 → 逐张 `batchEditPictures`），落库核对 tags/category 正确。**代价观察**：MiMo 单次调用明显比 deepseek-flash 慢（同一整理场景 53.4s vs 12.6s）；提速度可换 `mimo-v2.5-pro`（但**它不支持图片**，vision 那组得留着 `mimo-v2.5`）或把看图改成并发（F12 已知限制 3）。
