# 循环检测重写为双信号滑窗（T33）

> 自 docs/decisions.md 外移（2026-09-27）；**口径以 decisions.md 表内那一行为准**，本文件保留完整原文。

## 决定

引擎的 ReAct 循环检测（`BaseAgent.isStuck`）**废弃 OpenManus 式"assistant 文本全局计数"**，改为"循环签名 + 滑窗"双信号判定（用户批准方案 2，不做"执行前阻断"）：

- **循环签名**（assistant 子序列，每步一个）：工具调用步 = `tool|名|规范化参数`（多调用按序拼接），纯文本步 = `text|文本`；空文本且无工具调用的决策行无签名；带文本的工具决策行按工具签名判（文本是修辞变化，重复的动作才是信号）。
- **滑窗判定**：最近 4 步（`STUCK_WINDOW=4`）内同一签名出现 ≥2 次（含当前，`duplicateThreshold=2`）判卡死。
- **处置收紧**：`MAX_STUCK_COUNT` 3 → 2——第 1 次纠偏（注入"观察到重复响应…"，只进请求不入库）、第 2 次强停。
- **检测时机**：只在 state 仍 RUNNING 时检测——本步已给出最终回答不再补"检测到循环"（修复真回答后面跟终止文案的双 answer）。

## 为什么

旧实现照抄 OpenManus 的 `is_stuck()`，四个问题：① 空文本的工具决策行让检测失明——"同工具同参数反复调用"这条最常见的死循环形态完全抓不到，只能烧完 20 步预算；② 全局计数把不同上下文里合法重复的短句误判成卡死；③ 精确等值匹配对措辞微差漏报；④ 终止成本高（同一文本约 5 次才强停）且 FINISHED 后仍补发终止文案。

调研对照：LangChain/LangGraph/OpenAI Agents SDK/CrewAI 只做步数硬边界（`max_iterations`/`recursion_limit`/`max_turns`/`max_iter`），内容检测交给用户自定义终止条件——步数预算是兜底而非检测；**Strands（AWS）**用工具调用指纹（name + input）滑窗，窗口内重复 ≥2 在执行前阻断（本仓的"执行前阻断"即此，经用户拍板暂不做）；Inngest 用连续 3 次同工具口径；OpenFang 对工具调用序列做 SHA-256 模式检测（抓 A-B-A 交替循环，20 步对话场景罕见，不做）；spring-ai-alibaba 的 `LoopAgent` 是按条件重复的编排算子，不同类问题。共识 = 工具指纹为主信号、滑窗/连续计数、步数硬边界兜底——旧实现恰好只有最弱的文本信号且用全局计数。

## 影响

- 空文本工具决策行参与检测（主盲区关闭）；不同上下文的合法重复不再误判；措辞微差靠参数/动作信号兜住一部分。
- 强停从"约 5 次重复后"提前到"滑窗两次触发后"，20 步预算浪费从约 1/4 降到约 2 步。
- 已知限制（F13 已知限制 11）：间隔 ≥4 步的慢速交替循环漏报（防误报的代价）；参数键序重排不归一。
- 引擎未重新部署，线上仍是旧口径，随下次发布生效（与 T32 同批）。
