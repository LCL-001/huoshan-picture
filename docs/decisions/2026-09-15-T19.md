## 决定

**T19 搜图 MCP 不可达时的降级（用户 2026-09-15 拍板"做 MCP 降级"）**：① 解析 MCP 工具回调失败（含"取 Bean"与"列工具"两步）⇒ **降级为空数组** + 一条 warn，对话照常进行（沿用 T9"少一个工具照常开对话"口径）；② 失败后**进入 60s 冷却**——冷却期内不再尝试（不重复白等连接超时），到期自动重试、成功即清冷却；③ **不压小 `request-timeout`（默认 20s）**；④ 不做显式健康探测；⑤ 降级原因**不推给前端/用户**（保持静默降级 + 日志）。提交 `731a481`（字据）/ `669794a`（代码）。

## 理由

**红基线（本次一手复跑：当前 jar + 8127 不启）**：HTTP **200** 但体是 `{"code":50000,"data":null,"message":"系统内部异常"}`、耗时 **20.13s**、**无 SSE**、栈顶 `HuoshanAssistantController.java:107`，异常为 `CompletionException(ConnectException)`（SDK 文案 `Client failed to initialize listing tools`）。**20s 这个上界的来源已核实**：`spring.ai.mcp.client.request-timeout` 默认值 20s（spring-ai-autoconfigure-mcp-client-common **1.1.2** 的 `spring-configuration-metadata.json`）。**修复后同形态**：首次对话 **24.1s** 收到 `event=error` + `[DONE]`（约 20s MCP 超时 + 约 4s 黑洞 provider），**紧接着第二次 3.62s**（冷却生效）。**反向对照（8127 起来）**：4.35s、零降级日志；真模型（MiMo `mimo-v2.5`）下 `searchImage` 照常被调用并返回 Pexels 地址（15.15s，`tool`/`answer`/`[DONE]` 三帧，无 error 帧）。**为什么冷却 60s 是常量、不做配置项**：它是"不重复白等"与"服务恢复后自愈"之间的折中上界，不是按环境调优的值；要改需同时改 `McpToolCallbackResolverTest` 里钉住它的那条断言。**为什么不动 `request-timeout`**：这把尺同时约束真实的 `searchImage` 调用（走 Pexels 网络），压小会误伤正常路径；代价是"每个故障窗口的第一次尝试仍要 ≤20s"（只付一次，冷却期内不再付）。**为什么不做健康探测**：它自带一把超时尺、还要在装配前多打一次网络往返，行为不如"失败即降级 + 冷却"可预测。**未做/已知代价**：用户侧看不到"搜图工具本轮被回退"这一事实（模型照常作答；若用户明确要求搜图会得到工具错误）；降级粒度是**整批 MCP 工具**而非单个工具；冷却状态在**进程内**（多实例各自计时，不共享）。
