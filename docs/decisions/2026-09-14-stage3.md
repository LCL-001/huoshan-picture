## 决定

**档 3 T7 工具集口径（写类工具 + 看图打标）**：① **批量编辑的 id 按字符串进 body**（与既有 `listPictures` 的 `spaceId` 同口径），靠图库侧 Jackson 把纯数字字符串强转成 `Long`——位数原样保留，不赌"数字进 JSON 也不丢精度"；② **批量编辑的返回如实表达"只确认提交成功"**：图库 `/picture/edit/batch` 只回一个布尔且按"空间 + id"过滤（不属于该空间的 id **静默跳过**），故工具返回 `requestedCount`（提交了几张）而**不是**"改成了几张"，并带一句 `note` 讲清这件事——工具不替图库承诺逐张成功；③ **`batchUploadByUrl` 必须给 `spaceId`**（图库该端点 `spaceId` 可空 = 落公共图库，助手不开放这条路，避免误落公共区）；④ **看图打标由工具自己解析图片地址**：模型只给图片 id，工具经 `GET /picture/get/vo?id=` 取 `url` 再送模型，**不让模型复制粘贴长 URL**（复制长串是模型最易出错的环节，且图库该端点会按图片归属再做一次空间权限校验）；⑤ **visionTagger 只给建议、不落库**（落库由 `batchEditPictures` 承担且需用户确认，设计文档 L58/L62），返回里带 `note` 明示"尚未写入图库"；⑥ **未配视觉模型（`app.ai.openai.vision.*` 为空）时不挂 visionTagger**——宁可让模型看见"手上没有这个工具"，也不给它一个每次调用都报错的工具；⑦ **看图逐张串行、单次上限 8 张**（每张数秒，串行 8 张 ≈ 数十秒；并发看图留作后续优化）；⑧ 两个写类工具均**单次上限**（批编 50 张 / 入库 20 条）并在超限时**本地拒**（`40000`，零上游请求），入库遇到 `40100/40102` 提前停止并如实报 `skipped`（后面每条必然同样失败，不白烧调用）。

## 理由

①的取舍：图库 DTO 是 `List<Long>`，JSON 数字与数字字符串都能进，但"字符串进出"在后续改动里更不容易被无意破坏（且与既有 `spaceId` 写法一致）；②是"诚实上报"的硬要求——批编的静默跳过年月久了会被当成"改成功了"；④把 URL 搬运从模型手里拿走，是这一期减少幻觉输入的关键一步；⑥的替代方案（挂一个会报错的工具）会让模型陷入"反复重试同一个失败工具"的循环；⑦的延迟量级由代理 read-timeout 6 分钟兜底，但一步数十秒对折叠条的观感不友好——若要优化，走"有界线程池并发看图"（仓内已有 `ParallelSearchTool` 的池化先例）。门禁 **107 例**绿（新增写类工具 11 + 看图打标 8 + 装配 1）。
