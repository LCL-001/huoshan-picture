## 决定

**图库助手模型接入 DeepSeek 官方（`deepseek-flash`，用户指定）**：① **base-url = `https://api.deepseek.com`**（协议根、不带尾部 `/v1`，与 T6 口径一致——Spring AI 自己拼 `/v1/chat/completions`）；② **主脑与 visionTagger 共用同一个模型名 `deepseek-flash`**（= DeepSeek-V4.1-Flash，1M 上下文；官方文档明确：**支持 Tool Calls**，且**图像理解"支持"**——`deepseek-v4-pro` 则不支持图片，故两个用途都选 flash）；③ **思考模式显式关闭**（`extra-body.thinking.type=disabled`）；④ 为传这个厂商私有开关，**新增 `extra-body` 配置能力**（`OpenAiModelProperties.ModelEntry.extraBody` → `OpenAiChatOptions.Builder.extraBody(...)`，仅当非空时附加）；⑤ 密钥与厂商私有参数都只写进 `application-local.yaml`（不入库；`ai/agent/.env` 已被确认**不会被应用读取**——引擎没有 dotenv 加载器，那份文件只是给人看的），`application.yaml` 只留厂商中立的默认值。

## 理由

③的理由有两条，第一条是硬的：DeepSeek 文档明确"**携带 `tools` 的请求，后续每轮都必须完整回传 `reasoning_content`，否则 API 返回 400**"，而 `reasoning_content` 是 DeepSeek 私有字段、**Spring AI 的 OpenAI 客户端不认它**（解析时丢弃、构建请求时不会回传）⇒ 在思考模式下我们的 ReAct 循环**第一轮工具调用之后必炸**；第二条是思考模式下 `temperature`/`presence_penalty`/`frequency_penalty` 全部不生效（文档原文：设置不报错但不生效）。④的必要性：OpenAI 协议没标准化这个开关，Spring AI 的 `OpenAiChatOptions` 提供了 `extraBody` Map 直通请求体顶层，这是唯一不改客户端的路子；把 `thinking` 只写在环境配置里而非通用 `application.yaml`，是为了换厂商时不会把不认识的字段发出去。**待办（需真实密钥）**：`DEEPSEEK_API_KEY` 尚未提供，配置已就位但 `isConfigured()=false`（headless 端点在入口即拒、日志明确报"主脑模型未配置"）；拿到密钥后要做一次真机冒烟，**重点确认 `/v1/chat/completions` 路径**——DeepSeek 文档的 curl 示例用的是不带 `/v1` 的 `/chat/completions`，而 Spring AI 拼的是 `/v1/chat/completions`，这条只能实测。**已做的验证**：一次性 Spring 上下文冒烟（跑完即删）+ 2 条单测确认 yaml 绑定与 `extraBody` 直通（启动日志实测 `baseUrl=https://api.deepseek.com, model=deepseek-flash, extraBodyKeys=[thinking]` × 两组），门禁 **110 例**绿。**真机冒烟（密钥到位后实测，2026-09-14）**：① **`/v1/chat/completions` 路径可用**（Spring AI 默认拼的那个），鉴权、模型名均通；② **带工具的多轮调用实测通过**——模型真的调用了工具（`TOOL CALLS 1`）并据此作答，证明"关思考模式"这条口径是必需且生效的；③ **图像输入：图库自己的 COS 图可用**（`deepseek-flash` 准确描述了画面内容），**而 Pexels 的 CDN 地址被拒**（`400 ... unsupported image`，同一张图本机 `curl` 是 `200` + `image/jpeg`）⇒ 结论：**visionTagger 用图库图片的 `url`（COS）没问题**；第三方 CDN 能否被抓取取决于对方 CDN（Pexels 不友好），但**不影响我们的链路**——T9 场景里 Pexels 地址只是"上传的输入"，入库后图片的 `url` 就是 COS。
