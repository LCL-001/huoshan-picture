## 决定

**生产 CORS 白名单移除 apex 域名（用户拍板；即上条 review 的 P3(h)/(⑪) 收口，代码提交 `1c732db`）**：`application.yaml:100`（**跟踪文件**）的 `app.cors.allowed-origins` 去掉 `https://lincode.online`，保留 `http://localhost:*,http://127.0.0.1:*,https://www.lincode.online`；`application-prod.yaml` 的对应行只留 `https://www.lincode.online`（注释里写明"不列 apex"的理由）。**传递方式（必须记住）**：`application-prod.yaml` 被 `backend/.gitignore:10` 排除（密钥不入库，仓内只有 `application-local.yaml.example`），生产那份的改动**随重新打包的 jar 内嵌生效、不经 git 到达服务器** ⇒ 本次改动要在 prod 生效必须重新 `mvn package` 并部署；若服务器上另有一份手写 prod yaml，需按同口径核对。**同类未改、建议另立任务**：`WebSocketConfig:25` 的 `setAllowedOriginPatterns` 是**硬编码**列表，含 `http://localhost:*` 与 `https://lincode.online`、生产同样生效——WS 握手没有 CORS 可挡，来源校验是它唯一的 CSRF 防线，建议改为按 profile 可配（生产既不含 localhost 也不含 apex）。

## 理由

理由：apex 与 www **同站**（`SameSite` 按 eTLD+1 判定），而本套跨站防护的唯一屏障是"CORS 读限制"（读不到 `/ticket` 与 chat 的响应体），白名单放行 apex 等于把这道屏障对它让开（前提是 apex 上出现非本应用的可控页面）；实测 apex 当前返回与 www **逐字相同的应用**（1394 字节、`identical=True`）、`/api` 在两个 host 上都同源可用、前端生产用相对 base（`request.ts` 的 `BASE_URL=''`）⇒ **这条对应用不是必需的，删掉零代价**，等于把屏障收回成只有 www 一个 origin。门禁实跑 45 例（backend）+ 87 例（ai/agent，pre-commit 钩子顺带）全绿。仍待办：定唯一主机名（www）+ 另一个 301（nginx，不在仓库）。
