## 决定

**待决策：空间列表接口的登录态不吃 sa-token**（档 1 冒烟发现，影响档 2 的 T10）。实测（探针账号真登录，`local,test` 跳验证码）：`POST /space/list/page/vo` 用**新签发的有效 satoken 单独调用回 `40100 未登录`**，仅带 `SESSION` cookie 成功，两者都给成功；对照 `/picture/list/page/vo` 无鉴权即可读公共图库（146 张）、空间维度图片读与词表接口分别走 sa-token / 无鉴权。根因：`SpaceController.java:142` → `UserServiceImpl.getLoginUser`（`:209-221`）读 Spring Session 的 `USER_LOGIN_STATE`，与 sa-token 无关。**后果**：图库助手第一个工具 `listSpaces` 在"只透传 satoken"的现行设计下拿不到任何数据

## 理由

与 2026-09-13 记录「空间接口全部依赖 Sa-Token 登录态」不符（该条把 Spring Session 残余影响限定在"个人资料编辑等自持操作"，但空间**列表**实际依赖它）。**选项 A（推荐）**：给空间列表/详情这类接口加 sa-token 回退（Spring Session 无用户时取 `StpKit.SPACE.getLoginIdDefaultNull()`），既对齐已记决策、又不必把第二把凭据带进引擎；**选项 B**：T10 代理额外转发 `SESSION` cookie、引擎工具透传两把凭据（改动小，但把 Spring Session 引入引擎，而它正是"改密后不失效"的残余风险面）。**A 属改动 图库 backend 鉴权路径，按规则 2 待用户拍板后再动**。**2026-09-14 用户拍板选 B**，理由：A 只解锁"入口"（找空间），空间维度读图走的是加强校验 `checkSpaceViewPermission`（`PictureServiceImpl:768-786`，要求 Spring Session 用户与 sa-token loginId 一致），A 覆盖不到，档 3 的"整理空间 X"仍要回来补；B 一次到位且**图库 backend 业务代码零改动**

## 状态

**生效（B）**
