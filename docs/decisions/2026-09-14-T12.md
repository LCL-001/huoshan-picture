## 决定

**T12 联调发现并修复：记忆回放必须剥掉"未配对的工具调用痕迹"（否则 DeepSeek 严格校验下第二轮工具调用必 400）**：现象——真机跑"帮我整理空间里的图"，第一次 `listSpaces` 成功，紧接着**第二次模型调用直接 400**：`An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`。根因（查 `yu-ai-agent.chat_message` 确证）：本引擎的记忆**只持久化 assistant 的 toolCall 决策行、不持久化工具响应行**（`ChatHistoryAssembler` 的口径注释已写明），所以回放出来的 assistant 消息天生是"带 tool_calls 却没有配对 tool 响应"的非法序列。**修复**：新增 `MessageConverter.toReplayMessages` 作为"**给模型的那条路**"专用转换——工具响应行丢弃、assistant 行只保留文本并去掉 toolCalls、纯决策行（文本为空）整条丢弃；`FlowWindowBasedChatMemory` 的 6 处回放全部改用它，并加 `MessageConverterReplayTest` 钉住行为。**折叠条不受影响**：前端读的是库里原样的 toolCalls/toolResponses 元数据（走 `ChatHistoryAssembler`，与本修复互不相干）。

## 理由

为什么以前没暴露：DashScope 兼容模式**宽松、不校验**这个序列，而 DeepSeek **严格校验**——这是"换厂商必须重跑联调"的实证。为什么不改成"把工具响应也持久化、成对回放"：那要动记忆写入路径（Memory Advisor 只写决策行），改动面与风险都大得多；而回放丢工具痕迹对聊天助手是**可接受且更省 token** 的（模型看到"用户问过什么 + 自己答过什么"，中间工具往返不必回放）。**残留问题**（记入 F12「已知限制」）：同一条用户消息会被 Memory Advisor 多次写入（实测 3 次），属 token 浪费而非正确性问题，本轮未动。门禁 **112 例**绿（新增 2 条守护）。
