## 决定

**会话记忆按指纹去重（修"同一条用户消息被反复入库"）**：现象——`chat_message` 里同一条用户消息有 **3 份**。根因（读 Spring AI 1.1.2 源码 + 一次性复现实验确证）：`MessageChatMemoryAdvisor.before()` 每次模型调用都执行 `chatMemory.add(conversationId, prompt.getUserMessage())`，而 `getUserMessage()` 取的是**请求里最后一条用户消息**；本引擎的 ReAct 循环每轮把整段 messageList 重新提交，最后一条用户消息长期就是那条原始提问（下一步提示第一轮用掉后即被置空）⇒ **每调一次模型就把它再写一遍**。**修复**：新增 `MessageConverter.fingerprint`（类型 + 文本 + 工具调用 id + 工具响应 id），`FlowWindowBasedChatMemory.add()` 先取该会话已存指纹集合、命中即跳过；系统提示词那条分支删掉旧行后必须把对应指纹从集合里移除（否则新行会被误判成"已存过"，系统提示词会整条丢失）。**真机实测**：重跑智能整理，该会话 8 行消息**每条各 1 份**（修前同一条用户消息 3 份）。

## 理由

为什么指纹要带工具调用/响应 id：工具决策行常常**文本为空**、只有 metadata 不同，只按"类型 + 文本"判重会把两步不同的工具调用误合并成一步（折叠条丢步骤）。**取舍**：同一会话里用户问两遍**完全相同**的问题，第二遍不会进记忆（当轮模型仍看得到，跨轮次看不到）——判定可接受，记入 F12「已知限制」。**代价**：指纹集合是每次 add 全量扫该会话的行（与 `compress()` 同量级，add 每轮 2 次），会话很长时属多余读，列为可优化项。**顺带核实**（原本怀疑的另一个 bug 不成立）：`Prompt#getUserMessage()` 取"最后一条"并不导致"无工具问答时用户提问不入库"——真机跑了一次单轮问答，用户消息确实入库。门禁 **118 例**绿（新增 5 条守护）。
