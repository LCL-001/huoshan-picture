## 决定

**T9 搜图 MCP 接入口径**：① **传输方式定 SSE**（MCP 服务 `ai/image-search-mcp-server` 默认 profile 就是 `sse`、端口 8127；stdio 需要引擎在本机 fork 一个 java 进程，部署形态更脆）；② **`spring.ai.mcp.client.initialized: false`**——不在启动时初始化 MCP 客户端，**MCP 服务没起也不拖垮引擎启动**（首次调用时才连），另留 `AI_MCP_CLIENT_ENABLED` 总开关给"不部署 MCP 服务"的环境；③ 搜图工具**只并进图库助手工具集**（控制器用 `ObjectProvider<ToolCallbackProvider>` 取，Bean 不存在就少一个工具、照常开对话），**MyManus 的 `ToolRegistration.allTools()` 一字未动**；④ 服务端工具描述（`search image from web`）与工具返回值（**逗号拼接的图片 URL 串**）**不改**（T9 要求"MCP 服务本体零改动"），改由助手系统提示词交代"这些 URL 交给 `batchUploadByUrl` 入库、不要自己编 URL"。

## 理由

①的理由：SSE 与引擎同机/内网部署最简单，且服务侧已按 sse 配好；②是本条最关键的取舍——MCP 客户端默认 `initialized: true` 会在启动时连服务，服务没起就**整个引擎起不来**，而搜图只是助手的一个工具，不该有这种否决权（代价：配置错误要到首次调用才暴露）；④的理由：把 MCP 服务保持为零改动，适配责任留在引擎侧提示词。**部署耦合（必记）**：MCP 服务要与引擎同机/内网可达；没部署就设 `AI_MCP_CLIENT_ENABLED=false`，否则工具调用会在运行时报连接失败。**实测**（双进程）：MCP 服务 `tools/list` 回 `["searchImage"]`、`tools/call`（query=sunset）回 15 个 `images.pexels.com` 地址；引擎侧一次性 Spring 上下文冒烟确认可装配并调用（跑完即删、不入库——它要 MySQL 与活着的 MCP 服务，绝不能进门禁）。复现步骤：`cd ai/image-search-mcp-server && mvn -B -o package -DskipTests && java -jar target/image-search-mcp-server-0.0.1-SNAPSHOT.jar`（8127），客户端冒烟脚本 `%TEMP%\t9-mcp\mcp-smoke.js`（node，手写 MCP-over-SSE：取 `/sse` 的 endpoint 事件 → POST `initialize`/`tools/list`/`tools/call`），引擎侧则把上面那个一次性 `@SpringBootTest` 的 properties 照抄（`spring.ai.mcp.client.initialized=true` + `sse.connections.image-search.url`）。门禁 **108 例**绿。
