# 2026-09-18 批量抓取落库批量化（T28）

> 状态：生效。口径表行见 `docs/decisions.md` 2026-09-18。实施与红绿证据见 `docs/plans/records/T28-批量抓取批量化.md`；功能讲解见 `docs/features/F3-批量抓取.md`。本文件写定后不可变（勘误除外）。

## 背景

`/picture/upload/batch`（管理员批量抓取）在并行线程里调的是**完整的** `uploadPicture`：每张图各开一个事务入库、各自清一次图片列表缓存。30 张图 = 30 次 `getByUrl` 去重查询 + 30 个事务 + 30 次缓存版本号自增与 30 次失效广播——批量执行期间列表缓存被反复打穿（F4 多级缓存的痛点），而每次入库本身只有单行 INSERT。

用户 2026-09-18 提问："并行时抓到的每张图片不单独入库，而是 allOf 获得所有结果之后再一次批量入库可以吗？"——可以，且拆开后形状更干净：网络阶段（下载 + COS 转存）仍是并行瓶颈，落库阶段收敛成一次。

## 决定

1. 并行线程只做**网络阶段**：下载 + COS 转存 + 构造未落库记录（`preparePicture`，与单张上传共用）；`CompletableFuture.allOf` 之后一个事务 `saveBatch`（本地 JDBC 带 `rewriteBatchedStatements=true`，驱动合并为多值 INSERT），随后**只清一次**列表缓存。
2. 去重提到并行之前：一次 `IN` 查询 + 批内按源地址去重（保留原始序号，命名前缀不因跳过而重排）。
3. **入库阶段整批原子**：任一行落库失败即整批回滚并抛错，同时把这一批已转存 COS、已无记录引用的文件逐个补偿删除（`cleanupPictureFile` 按引用计数兜底）。下载/COS 失败仍逐张跳过，"成功 N 张"的返回口径不变。
4. `rewriteBatchedStatements=true` 只加本地 `application.yaml` 与模板注释；`application-prod.yaml` 不动，prod 随下次发布生效（生效前生产是"一个事务 + N 条 INSERT"，功能正常）。

## 理由

- 收益不在"更快"：瓶颈是 30 次图片下载 + 30 次 COS 上传，这部分并行度不变，DB 省下的是毫秒级。真正值钱的是**缓存失效 30 次 → 1 次**（批量期间列表页不再被反复打穿）、事务 30 → 1、去重查询 30 → 1，以及顺手消掉"同一批里重复的源地址被下载两次、入库两条内容重复记录"。
- 代价是可量化的：入库失败时整批 30 张的 COS 转存作废并被删除，接口报错而不是回一个偏小的成功数。用户明确接受这条语义变更（属规则 3 第④类，已立字据）。

## 证据（可复跑）

- 红：`cd backend && mvn -B test -Dtest=PictureBatchUploadIntegrationTest -DfailIfNoTests=false` → 4 例失败，分别钉住"清缓存 5 次而非 1 次""批内重复源地址入库 3 条而非 2 条""入库失败不抛错"。
- 绿：同命令 → Tests run: 5, Failures: 0。
- 回归：存量替换/额度/权限/词表/缓存集成用例 24 例绿；CI 口径快速子集 77 例绿。
- 配置项取证：`SHOW GLOBAL STATUS LIKE 'Com_insert'` 前后差值 = 1（未生效会是 3）。

## 附带发现（未修，需另开任务）

"已存在即跳过"的检查对 URL 上传路径实际失效：`picture.url` 存的是 COS 地址，而检查传的是源地址，两者不同名空间 ⇒ 单张 `/picture/upload/url` 与批量抓取的去重都不会命中。本次按规则 1 只保持同口径（合并为一次 `IN` 查询）未改语义。
