| 场景 | HTTP status／业务 code | MySQL／Redis 后置条件 |
|---|---|---|
| 同人双登录态绑定 | 200／0 | 邮箱更新，邮箱码消费 |
| Spring Session 有效、token 缺失 | 200／40102 | 邮箱不变，邮箱码未消费 |
| A Session + B 有效 token | 200／40102 | 邮箱不变，邮箱码未消费 |
| 有 token、无 Spring Session | 200／40100 | 邮箱不变，邮箱码未消费 |
| 实际调用 password/reset | 200／0 | 先确认属于 A 的旧 token 映射被撤销 |

| 残余 Session + 被撤销旧 token 换绑 | 200／40102 | 邮箱不变，邮箱码未消费 |

| 新密码登录并绑定 | 均 200／0 | 新 token 映射有效、邮箱更新、验证码消费；B 未改变 |

独立子代理执行后又对脚本做只读复核：Cookie 来自真实 Set-Cookie，请求显式构造，不会被隐藏 cookie jar 补足；撤销前后核对同一 Redis token 映射，未见本次结论的明显假阳性。主线程复核了脚本与完整原始输出，未重复运行再创建账号。

**范围限制：** 直连本地 HTTP、Cookie 凭据通道、一个旧 token；未验 header 通道、多设备全撤销、nginx／TLS 或生产行为。

## T69 补充风险（尚非浏览器结论）

独立子代理指出 P2 同上下文竞争：A 详情未返回时 picture 为空，上传按无 id 新增 B；上传回调显示 B 后，迟到 A 详情仍满足同一路由版本检查，会把页面改回 A，后续保存目标可能混淆。首次编辑进入时该风险此前已存在；跨路由 contextVersion 不能自动处理同一上下文内的竞争。
