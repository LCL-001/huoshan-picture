## 修复内容

- 在 `AddPicturePage.vue` 中增加独立的详情请求代次 `pictureDetailVersion`。
- `getOldPicture` 发起请求时记录详情代次；回包只有同时满足当前路由 `contextVersion` 和当前详情代次才允许写入页面。
- 有效上传成功回调在确认仍属于当前路由后递增详情代次，再写入新图片；因此不会改变路由上下文、不会重建上传组件，也不会误杀下一路由的详情请求。
- 文件上传和 URL 上传共用同一回调，因此两条入口都受到保护。
- 新增脚本命令 `npm run check:picture-upload-context`，永久覆盖文件／URL两种竞态及保存目标。

## 关键复现与修复后结果

原始问题顺序为：详情 A 挂起 → 上传 B 成功 → 释放详情 A；旧实现会把页面 picture／表单退回 A。修复后同样顺序下：

1. 真实 `/api/picture/upload` 返回业务 0，新记录创建成功，请求不带旧 id；
2. 真实 `/api/picture/get/vo` 响应原样交付，延迟 1850ms，小于 Axios 超时安全窗口；
3. 页面仍保持新上传图片的 id 和名称，当前 AddPicturePage 组件 UID 不变；
4. 未执行错误保存，原图数据库快照不变；专项测试另断言后续保存目标为新上传 id。

## 测试覆盖

新增永久断言包括：

- 文件、URL 上传成功优先于未完成详情，且后续保存指向新图片；
- 上传失败不屏蔽正常详情初始化，完整表单仍可保存到 A；
- 已完成上传后切换到新路由，新的详情仍可初始化；
- 旧路由上传成功不能使下一路由的待返回详情失效；
- 同一上下文连续两次上传，第二次结果生效且组件不重建；
- 原有 A→新增、A→B、A→B→A、卸载、旧上传回包及旧保存回包断言继续通过。

## 范围与限制

- 真实浏览器范围是本地 Chrome＋直连 HTTP；不等同于生产 nginx／TLS 验收。
